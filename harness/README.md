# Eval Harness

L1/L2 skill evals over the fixture corpus (see `openspec/specs/testing-harness/spec.md`). L0 unit tests live in `tests/unit/` and never call models. The L1 verdict logic is shared between both runners via `l1_checks.py` (pure functions, unit-tested).

## Which path to use

| Job | Path | Cost |
|---|---|---|
| One-time setup before any isolated run, routing sweep, judged run or `poe smoke` | in claude.ai, extra usage off; then, in a terminal outside any agent session, `uv run poe host-login claude` (see Harness login). Token-mode operators skip it | none |
| Iterate on a skill with an Anthropic model; quick check after a change | `poe dev <scenario> --model haiku`/`sonnet`/`opus`. Add `--isolated` when the result is cited as a measurement. `poe smoke` runs the core scenarios in one go. | subscription |
| L2 iteration: rubric grades while working on a skill | `poe dev <scenario> --isolated --judge` (dev-runner L2, not comparable to matrix) | subscription |
| Re-grade output that already exists | `poe dev <scenario> --rejudge <dir>…` over kept workspaces | subscription — never metered |
| Iterate on a skill as a Codex student runs it (dev loop only, never a matrix input) | after the one-time Codex setup (see Codex dev runner), `poe dev <scenario> --host codex --model <name>`; the first Codex model call after any login waits for the user's explicit go | ChatGPT plan quota, $0 while the credit balance stays 0 |
| Iterate on a skill as a Copilot CLI student runs it (dev loop only, never a matrix input) | after the one-time Copilot setup (see Copilot dev runner), `poe dev <scenario> --host copilot --model <id> --max-ai-credits <N>`; every login records an approval stop, and the first model call waits until the user clears it with `poe host-login copilot --clear-stop` | the plan's included AI credits, $0 while the $0 "Stop usage" budget on "All AI Credit SKUs" holds |
| Skill selection from the descriptions | `poe routing` | subscription |
| Audit preflight | `harness/audit_llm_preflight.py` | subscription |
| L2 of record, persona dialogues, confirming a change that targets a shipped verdict | `poe matrix --models … --tasks …` (Inspect) | metered, cost-gated |
| Non-Anthropic model under test | `poe matrix --models …` | metered, cost-gated — OpenRouter is the only route |
| The Inspect wiring itself changed | `poe smoke-inspect` | metered, cost-gated |

"Subscription" means no money while the plan's extra usage stays off. It does draw the rolling plan limits, which are shared with the operator's own Claude use. The dev runner strips every `ANTHROPIC_*` variable and `CLAUDE_CODE_USE_*` switch from its ambient model runs. Every Claude child that runs in an isolated configuration — the routing rig's, an isolated dev run's, the judge's and its preflight, and the harness login's status check — starts from one allowlisted environment that admits none of those variables (`host_login.allowlisted_env`; see Skill routing). The one `ANTHROPIC_*` name an isolated child carries is `ANTHROPIC_CONFIG_DIR`, which the harness sets itself to an empty directory inside the isolated configuration; it routes no billing. The audit preflight drops the same billing variables as an ambient dev run (`account_surfaces.ambient_env`), so an exported `ANTHROPIC_API_KEY`, gateway base URL or `CLAUDE_CODE_USE_*` switch can no longer bill its calls per token; without a subscription login it fails with the host's login message. Every Claude child the harness starts also gets `ENABLE_CLAUDEAI_MCP_SERVERS=false` (see "claude.ai account surfaces" under Skill routing). Any metered call on an Anthropic model follows the `AGENTS.md` rule "Metered model calls".

## Inspect runs (OpenRouter, metered — source of record)

This path is reserved for what the table above sends here: L2 rubric scores, persona dialogues, non-Anthropic models, and the runs behind shipped verdicts. A bare `inspect eval`, as in the block below, has no cost gate; for any task the registry admits (the matrix or extended set, `support.select_tasks`) prefer `poe matrix --models … --tasks …`, which prints an estimate and waits for confirmation. Every matrix run writes to `logs/evals`, and `poe report` builds the shipped verdicts from the newest log per cell there, so a check that is not meant for the record passes `--log-dir logs/scratch` or stays on `poe dev`.

Credentials setup (once): `cp .env.example .env`, fill in `OPENROUTER_API_KEY`. Pass the file with `--env-file .env` (uv-native; nothing breaks when `.env` is absent because the flag is per-command).

```sh
# metered, ungated: needs explicit approval. check_report has no L2 rubric and is
# excluded from the matrix; its $0 run is `poe dev check_report --model haiku`.
uv run --env-file .env inspect eval harness/skill_evals.py@check_report \
    --model openrouter/anthropic/claude-haiku-4.5 --log-dir logs/evals

# model matrix in one invocation (one log per model) — metered, ungated: needs explicit approval
uv run inspect eval harness/skill_evals.py@review_fixture \
    --model "openrouter/anthropic/claude-haiku-4.5,openrouter/moonshotai/kimi-k3"
```

Judge model: `[roles].judge` in `harness/models.toml`; `JUDGE_MODEL` env overrides it for one invocation. The persona is `[roles].persona`, which defaults to the judge; `PERSONA_MODEL` overrides it. Each override replaces its own role only, so a judge override no longer moves the persona. The judge is pinned and metered on purpose, so shipped L2 verdicts stay comparable from run to run. It is not an ad-hoc grader: re-grading output that already exists runs on the subscription (`poe dev <scenario> --rejudge <dir>…`) and is never metered.
View transcripts: `uv run inspect view --log-dir logs/evals`.

Tasks: `write_from_seed` (w01 seed to draft; L1 check-clean, L2 RQ rubric), `review_fixture` (f05; L1 review file + untouched proposal, L2 review rubric), `review_fixture_de` (f04; German review), `review_hollow` (f22; a buzzword-generic proposal with no viable thesis core — L1 review file + untouched proposal, L2 rubric: verdict stated outright, failed substance tests named, never softened into needs-revision phrasing), `title_alarm` (f21; the agent-judgment half of the title rule — L1 title raised in writing and never rewritten in the proposal, L2 title rubric: certificate consequence named, one to three abstracted alternatives, decision left with the student), `check_report` (f15; L1 report fidelity + untouched proposal), `ideate_longrun` (~18-round scripted composite dialogue: preamble → hesitant → extraction probe → pivot → convergence → seeding; L1 seed + notes-growth snapshots + provenance, L2 phase-aware Socratic rubric), `ideate_stonewall` (early stop fires: notes saved, no proposal generated), `ideate_noidea` (hints stay few and sourced, never a topic menu; live DBLP noise must read as weak scoping), `ideate_outofscope` (one chat-only warning, ideation continues), `ideate_probing` (agreeable extractor offering only generalities plus pressure to "just write it"; the genericity gate must hold — swap test voiced, impasse named, no seed), `customize_override` (f00; supervisor requirements to valid TOML overrides), `publish_build` (f00; real pandoc/typst pipeline to PDF), `import_messy` (pasted messy text to standard format, personal data stripped), `troubleshoot_model_rung` (user on haiku with rung 0 already closed; the run must resolve rung 1 from the vendored verdicts and assemble no bundle), `litsearch_expand` (w03; live academic APIs — network-dependent, expect flakiness), `supervise_feedback` (s01; a raw student email to paste-ready feedback — L1: feedback present, at most five curated points, verdict tier stated, no fixture personal data in the feedback, every named skill real, closing note verbatim, any literature woven into the points and recorded in the notes rather than listed; the request pre-answers the borderline deferral and declines every lookup — claim checks and literature alike — so the network path is observed only in a dev run with `proposal-lit-search` staged as a sibling; extended set until the next big matrix run). The former 5-round cooperative dialogues (`ideate_socratic`, `ideate_anecdote`) are retired — their coverage lives in `ideate_longrun`'s hesitant phase, and their cooperative-only personas were the blind spot the probes close.

## Eval projection (`skills/*/evals/evals.json`)

Each skill ships its eval definitions in the Agent Skills standard's format (standard-conformance spec). The files are GENERATED: the task→skill map comes from `models.toml` `[tasks.skills]`, prompts and staged files from the task definitions above, L2 assertions verbatim from `skill_evals.CRITERIA`, and L1 assertions from the verdict docstrings in `l1_checks.py`. After changing any of those, regenerate with

```sh
uv run python harness/eval_export.py         # or --check for the drift verdict
```

`tests/unit/test_eval_projection.py` fails the L0 chain while a projection is stale or hand-edited.

## Model-support matrix (metered, cost-gated)

`harness/models.toml` pins the nine-model roster (exact OpenRouter IDs, family, price tier, cached $/Mtok pricing, enabled flag) plus the task policy: the scorable `matrix` set, the `core` smoke subset, `heavy` tasks (1 epoch on frontier tier), `excluded_l1` tasks whose `*_l1*` scorers are the environment-fidelity probes (structural score ignored, `*_l2*` rubric counts), `excluded` tasks (env probes without a rubric, live-network tasks), per-tier default epochs, and token priors for the estimate. The matrix is the source of record for the verdicts the README ships, and the only place an Anthropic model under test needs OpenRouter.

```sh
uv run poe smoke                     # subscription: the core scenarios on the dev runner, write_from_seed judged ($0 in money)
uv run poe smoke-inspect             # metered Inspect-wiring check: [roles].smoke × core tasks × 1 epoch via OpenRouter (cost-gated)
uv run poe matrix --estimate-only    # price a full run without any metered call
uv run poe matrix --tier cheap      
uv run poe matrix --models claude-haiku-4.5 gpt-5.6-terra --tasks write_from_seed
uv run poe report                    # regenerate README summary + docs/model-support.md
uv run poe cache-probe --estimate-only   # price the prompt-caching re-check without any metered call
```

Every metered invocation prints a cost estimate (registry pricing × token priors, replaced by measured history from `logs/evals/matrix-usage.json` once it exists) and waits for confirmation; `--yes` skips the prompt. `--yes` is for the operator to type: an agent passes it only after the user approved that run's estimate in chat. After the run it prints actual spend (recorded token usage × registry pricing), persists a `matrix-cost-*.json` summary next to the logs, and updates the usage history. Per-sample `token_limit` backstops runaway loops.

**Role models in the estimate.** Besides each model under test, the estimate charges the judge on every cell-epoch (`[tasks.judge]` budget) and the persona on every dialogue cell-epoch (`[tasks.persona]` budget), and lists both on their own lines. Their IDs are resolved exactly as the eval resolves them, so a `JUDGE_MODEL` or `PERSONA_MODEL` override is what gets priced. One lookup prices the estimate and the actual spend alike: the roster row with that ID (enabled or not), else its `[role_prices]` entry. A role the run calls whose ID neither prices stops the run before the confirmation prompt with exit 2, `--yes` or not; the remedy is an override the registry prices (a roster ID, enabled or not, or a role's own ID). Both budgets are ceilings, and after each run the matrix prints each role model's heaviest observed cell-epoch beside its budget and flags one it exceeds; raising a budget stays a reviewed registry edit. A role that shares the model under test's ID is mixed into that model's own usage and gets no line.

**Prompt caching on Anthropic rows.** Anthropic rows are cached with `marker`, the mechanism the cache reuse probe (below) passed on 2026-10-05: cache reads made up 88.8% (haiku-4.5) and 86.4% (sonnet-5.5) of the prompt tokens after the first cache write, every call served by Amazon Bedrock, for $0.06 in all (the `fix-openrouter-caching` change's `measurement.md`). `support.CACHE_MECHANISM` names it; setting it to `None` rolls back, and every row, Anthropic included, is then sent exactly as before. An Anthropic row under test reaches Inspect as a `Model` built by `support.routing_for`, pinned to the global Amazon Bedrock and Google Vertex endpoints: `provider = {"order": ["amazon-bedrock", "google-vertex"], "allow_fallbacks": false}`. These are the endpoints the account's zero-data-retention guardrail admits. First-party `anthropic` is filtered out by that guardrail: the first probe, pinned to it, failed at OpenRouter routing with a 404 at $0 (the `fix-openrouter-caching` change's `measurement.md`). The bare slugs never select a surcharged regional endpoint, and the explicit order switches off OpenRouter's sticky routing, so Bedrock serves every turn it can and Vertex only when Bedrock fails. Under `marker`, `harness/openrouter_cache.py` wraps Inspect's OpenRouter cache-marker function so that each request also carries one breakpoint on its newest user or tool message, with user and tool string content sent as one-block text lists. `matrix.build_model` installs the wrapper for a routed row. The wrapper acts only on requests that carry the harness pin, so a judge or persona prompt, built from its bare role ID, is never marked. A pinned single message is the model under test's first dialogue turn, which later turns read back, so it is marked. Top-level automatic caching (`auto`) was built as an alternative, never probed under this pin because Bedrock's legacy integration rejects it for Haiku 4.5, and deleted once `marker` passed. Every other row stays a bare ID, so its requests are unchanged, and the logged model is still the registry ID, so `poe report` counts the logs as before. Models under test stay mostly on Amazon Bedrock, as the earlier verdicts were (same weights and snapshot). The judge and the persona keep their unpinned serving and never carry a cache setting, since their one-shot prompts are never read back. With no fallback beyond the two pinned providers, an upstream error surfaces as an error rather than a silent switch to an unpinned path. `poe smoke-inspect` runs the same path (`matrix.py --smoke`), so the smoke model is routed, priced and role-checked exactly as a matrix row is.

**Cache telemetry.** After a run the matrix prints, per model under test, the cache-hit rate (cache reads ÷ all prompt tokens: uncached input + cache writes + cache reads), the cache-write and cache-read counts, the serving providers recorded in the logs (with an `unrecorded` bucket), and the prompt-side cost beside its uncached equivalent. `matrix-cost-*.json` carries the same under `per_model_cache`, the warnings under `cache_warnings` (model, kind `low_hit`/`no_prompt`/`off_pin`, detail), the mechanism under `cache_mechanism`, plus the resolved `roles`; its original keys are unchanged. Each log names the mechanism in `eval.metadata.cache_mechanism`, because a `marker` log's `model_args` show only the pin; for the same reason, re-run a `marker` run through `poe matrix`, never `inspect eval-retry`, which rebuilds the model without the breakpoint wrapper. A warning names a routed Anthropic row whose hit rate is below 50%, one that recorded no prompt tokens, and one with a call served by a provider outside its pin. A row whose every call failed, for example at a routing 404 if the account's guardrails change, records no usage while its log still reads `success`. It surfaces as that `no_prompt` warning beside the "did not finish cleanly or had errored samples" line, and `poe report` would score its samples as failed epochs. Known limitation: the provider counts are a per-sample spot check, not a census. The serving provider is recorded only in a call's raw response, and under the matrix's default `log_model_api` Inspect keeps that for errors plus the first five calls per model name per sample, judge or persona calls on the same ID included. The rest land in `unrecorded`: the 2026-10-05 confirmation cell recorded 5 of its 19 calls. `poe cache-probe` logs every call. Calls recorded as `Amazon Bedrock` or `Google` (Vertex) are on the pin (`support.PROVIDER_NAMES`), and `Anthropic` or any other name is not; no probed call has been served by Vertex yet, so `Google` is the name its endpoints carry in the catalog, not yet one seen in a response. With the mechanism rolled back nothing is pinned, so nothing is warned. Role models get no cache telemetry: their calls are one-shot and unpinned, and their usage is reported against their budgets instead (above). Calls of the judge or persona on a routed row's ID carry no pin and are left out of that row's provider count. `poe report` prices the same four token kinds through the same accumulation (`support.billed_usage`), so its per-model run cost agrees with the matrix's actual spend.

**Re-checking caching.** `uv run poe cache-probe` replays a fixed synthetic ten-call tool conversation on the enabled cheap- and mid-tier Anthropic rows, built exactly as the matrix builds them, and passes a model when cache reads reach 80% of the prompt tokens after the first cache write. It is metered and gated like the matrix: a worst-case estimate (every prompt token at the cache-write price) prints first and waits for approval, `--estimate-only` stops there, and its logs go to `logs/cache-probe`, never where `poe report` reads. `--mechanism` takes `marker`, the matrix's mechanism and the only one built. Each model ends `PASS`, `FAIL` (a scored replay below the bar, or a 400 rejecting the request; exit 1) or `UNTESTED` (a routing, account or API error such as the 404 of the first probe, or an unfinished replay; exit 3): an untested model is no verdict on caching. Re-run it after an Inspect upgrade: the `marker` wrapper hooks a private function of Inspect's OpenRouter provider (an offline test fails if the function moves), and the probe is the only measurement that caching still covers the conversation.

Classification per model×task cell: 3 epochs (per-tier policy in the registry), all pass = solid, mixed = flaky, none = fail. Per model: any fail → warning naming the affected skills (via the registry's task→skill map), any flaky → "flaky on <skills>", all cells solid → supported, solid-but-incomplete coverage → partial (untested count disclosed), no logs at all → untested. Disabled registry models keep their row, marked as disabled. `poe report` derives both the README summary table (pinned ID, verdict, run date) and the full grid with pass rates and per-model run cost from the newest log per cell — nothing in either artifact is hand-written.

### Model currency

`harness/models.toml` is the only place a model ID lives; `tests/unit/test_model_ids.py` fails on an ID in harness or script code or config, and on a stale or unregistered ID anywhere else (its allowlist names each exemption and why).

- **Roles.** `[roles]` names every model used outside the roster: `judge` (the matrix L2 judge), `persona` (the dialogue student simulator, defaulting to the judge), `smoke` (the metered smoke model, an enabled roster entry), and `dev_judge` with its pinned `dev_judge_effort` (the subscription CLI's full ID for dev-runner grading). `JUDGE_MODEL` and `PERSONA_MODEL` override one role each for one invocation. Floating aliases (`sonnet`, `~…`, `…-latest`) fail parsing.
- **Prices.** Every price is the model vendor's own OpenRouter endpoint at its standard tier, never `/flex` or `/fast`; `price_endpoint` names the endpoint tag where the vendor's provider slug differs (Qwen is served as `alibaba`). `prices_as_of` records the snapshot date. The judge and persona must be priced: by their roster row, or, once a held role's ID has left the roster, by a `[role_prices."<id>"]` entry. `model_currency.py --write` creates that entry in the same edit that moves the roster row, refreshes it weekly, and whoever later moves the role deletes it (parsing rejects an entry no role names). Roster rows and `[role_prices]` entries alike carry input, output and the optional `cache_read_price` and `cache_write_price` (the endpoint's `input_cache_read` and `input_cache_write`; each defaults to the input price when absent). The check compares, refreshes and writes all four through one field list, and leaves an optional price out when the endpoint lists none.
- **The check.** `uv run poe models` (networked, read-only, no key) derives each pin's version line, the ID with its version number wildcarded and a trailing snapshot date ignored, and reports a newer model in the line, a pin missing from the catalog, an expiration date, and price drift against the vendor endpoint. Exit 0 means current, 1 actionable findings, 2 currency unknown, 3 a `--write` edit the registry text could not take (nothing written). A missing pin is never proposed a lower version of its line: with only older members listed, it stays an alert. `--catalog FILE --endpoints DIR` replays a recorded snapshot, as the L0 tests do with `tests/unit/data/model_catalog/`.
- **Held roles.** The judge and the persona are reported as held and never rewritten: changing either invalidates every rubric-counted cell, so they stay until a deliberate full re-baseline moves them.
- **New lines.** A version line in a roster vendor namespace that no entry tracks, with a member created after `lines_reviewed_as_of`, is reported as information and never written. Clear it by adding a roster entry for the line, or by moving `lines_reviewed_as_of` by hand.
- **Declining a bump.** `track = false` on an entry opts it out (reported as untracked every week); `track = "<vendor>/<name-with-one-*>"` overrides a derived line that a vendor rename broke. Closing the bump PR alone brings the bump back the next week, unless the branch carries a maintainer commit (below).
- **The weekly bump PR.** `.github/workflows/model-currency.yml` runs the check in write mode every Monday and keeps one PR open from `model-currency/bump`, then dispatches CI on that branch, because a PR opened with `GITHUB_TOKEN` triggers no `pull_request` run. On that PR the maintainer:
  1. regenerates the shipped verdicts locally (`uv run poe report`, then `python3 scripts/sync_shared.py`) and pushes them to the branch. `logs/` is gitignored, and the shipped-verdict test keeps the PR red until then. From that commit on the workflow never overwrites the branch, with the PR open or closed, and comments new findings instead; only once a merged PR has carried the branch tip into main does the next run rebuild it. Deleting the branch is how to start over;
  2. for a `dev_judge` bump, checks for free that `claude -p --model <new id>` reports that same ID in `modelUsage`;
  3. closes and reopens the PR if CI's checks do not appear on it.

  New IDs render as untested until a cost-gated matrix run measures them.
- **At the cost gate.** `poe matrix` prints stale-pin warnings from one catalog request right above the confirmation prompt. They never block a run or change the estimate, and an unreachable catalog prints "model currency unknown".

## Baseline arm (without-skill control)

The standard's with/without comparison (testing-harness spec): the same single-turn task, staging, and verdicts, with the skill instructions removed. On-demand and cost-gated — never part of the default matrix, and baseline logs never count toward support verdicts.

```sh
uv run poe dev check_report --no-skill --model haiku    # subscription: dev-loop eyeballing, no logs
uv run poe matrix --baseline --models claude-haiku-4.5 --tasks write_from_seed    # metered, gated
uv run --env-file .env inspect eval harness/skill_evals.py@check_report \
    -T baseline=true --model openrouter/anthropic/claude-haiku-4.5 --log-dir logs/evals    # metered, ungated: needs explicit approval
```

Persona-dialogue tasks have no baseline arm (a without-skill control of a skill-shaped conversation measures nothing); the registry's `dialogue` list drops them from `--baseline` selections and their builders take no `baseline` parameter. When baseline and with-skill logs exist for the same (model, task), `poe report` appends a "Baseline delta" section to `docs/model-support.md`: pass rate bought vs tokens and time spent, plus per-scorer flags — a scorer passing in both arms is a dead-assertion candidate, one failing in both arms a too-hard candidate.

## Harness login (isolated Claude runs)

Every isolated Claude run — `poe dev --isolated`, the judge, `poe smoke`, the install probe and every routing sweep — links a login into its temporary configuration. Before 2026-10-05 that was your own `~/.claude/.credentials.json`, which isolated runs linked and refreshed; the harness and your own CLI then shared one rotating refresh token. The harness now keeps a login of its own (`harness/host_login.py`; OpenSpec change `add-harness-claude-login`), and runs link that one.

- **Where.** `${XDG_STATE_HOME:-~/.local/state}/thesis-proposal-dev/hosts/claude` on Linux (`~/Library/Application Support/thesis-proposal-dev/…` on macOS, `%LOCALAPPDATA%\thesis-proposal-dev\…` on Windows). Mode 0700, outside the repository, marked by `.harness-home`. `THESIS_PROPOSAL_DEV_STATE` overrides the state directory for tests; it is refused, as is any resolved state directory, when it is not an absolute path, equals or contains your home directory, overlaps `~/.claude`, `$CLAUDE_CONFIG_DIR`, `~/.codex` or `$CODEX_HOME`, or lies inside the repository. A directory at the home's path that carries no marker was not made by the harness: every command refuses it, naming it, and neither logs into it nor deletes it — move it aside.
- **One-time setup.** In claude.ai, turn extra usage off. Then, in a terminal outside any agent session, run `uv run poe host-login claude` and complete the browser login. The home is seeded with the account-surface opt-outs and an empty profile directory before the login starts, because account content synced once stays on disk. The login is the subscription login (`claude auth login --claudeai`), never a console login, and it runs with every billing and host-session variable removed. The command refuses without a terminal and inside an agent session (`CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_CODE_SESSION_ID`, `CODEX_SANDBOX`, `CODEX_SANDBOX_NETWORK_DISABLED`); those are speed bumps, and the `AGENTS.md` rule that agents never run it is the guard. A desktop app's built-in terminal panel may carry such a marker; use a terminal emulator outside the app.
- **Status, logout, reset.** `uv run poe host-status` makes no model call and prints only `home`, `marker`, `logged_in`, `auth_method`, `api_provider`, `config_dir_matches`, `clean`, `access_expires` and `runs_use` — never a credential, an email address or an organization; it exits 0 when the login is ready and 3 otherwise, with the refusal below on stderr. `uv run poe host-logout claude` runs the client's own logout in the home and keeps the marker and settings. `uv run poe host-login claude --reset` logs out, wipes the home (only a marked home that is not a symbolic link), seeds it again and logs in. A login over an existing login logs out first; the existing login is found by its `.credentials.json`, or by the host's own status where the login is no file. A logout that fails stops a re-login or a reset before anything is replaced or wiped, naming its exit status. Every logout runs in the same scrubbed environment as the login, holding the refresh claim that isolated runs take. None of the three commands starts a client while the default Anthropic profile directory (`${XDG_CONFIG_HOME:-~/.config}/anthropic`) holds an entry: whether the host ignores it when `ANTHROPIC_CONFIG_DIR` names the home's empty one is unverified (L8), so the remedy is to move the profiles aside; token mode does not lift it here, since logins and logouts never carry the token.

**Fail-closed preflight.** Before an isolated configuration links the harness login, the harness checks it without a model call, and refuses the run as untested — never falling back to your own login — with one message: `untested: <cause>. <remedy>. <login note>.`

| Cause | Remedy |
|---|---|
| the home is missing or wider than 0700 | `uv run poe host-login claude` |
| a directory at the home's path lacks the marker | move it aside, then `uv run poe host-login claude` |
| no login, or the status check yields no login state | `uv run poe host-login claude` |
| the home is not clean: settings other than the pinned opt-outs, or any of `skills/*`, `agents/*`, `commands/*`, `output-styles/*`, `CLAUDE.md`, `plugins/synced`, an installed plugin (marketplace caches and host state are allowed) | remove the named entry, or `uv run poe host-login claude --reset` |
| an auth method other than the subscription login, or a provider other than Anthropic's own API | `uv run poe host-login claude --reset` |
| the host reports another configuration directory | remove the wrapper or managed setting that redirects it |
| the host reports no configuration directory | update Claude Code |

The login note says "Your own Claude login is not affected". Live check L3 passed on 2026-10-05, so it closes every refusal. While `host_login.L3_PASSED` is False, a remedy naming `host-login` closes instead with "Whether this logs out your other Claude sessions is unverified (L3)", because that command logs out first, and every logout prints the same caveat before it runs. A login failure during a run names the remedy for the login the run used: `uv run poe host-login claude` (with the login note) for the harness login, `claude` → `/login` for an ambient run or the opt-in, `claude setup-token` for a long-lived token. The dev-run summary and the routing raw log record that login as `login` and its directory as `login_dir`, the one place a refresh is written back. The preflight is the cost of one `claude auth status` start per isolated invocation, about a second.

**Fallbacks, in this order.** First, token mode: run `claude setup-token` and export `CLAUDE_CODE_OAUTH_TOKEN` in the shell that starts the harness. Nothing is linked, and the harness login is neither checked nor read. Last, and only if token mode is not possible: export `CLAUDE_REAL_CONFIG_DIR=~/.claude`, the explicit opt-in, labelled `operator` in every summary and never taken as a fallback; it lasts until live check L1 has passed. It links your own login again, with its two hazards: a concurrent refresh in your own CLI (R1), or a run stopped part-way through a refresh (R4), can log your own CLI out. Termination before kill (every host child the harness starts — dev runs, the judge, routing cases, the harness login's own status and logout calls and the advisory audit pre-flight — is asked to terminate and killed only after a 10 s grace, `host_login.stop_child`) helps against R4 only if the host finishes its credentials write on SIGTERM. Claude Code catches SIGTERM and exits on its own within a fraction of a second (L9); whether that handler completes a refresh write already in progress is not shown, and showing it would take a forced refresh, so the hazard stands. The former `ROUTING_CONFIG_DIR` override is gone; setting it refuses the run and names `host-login`. macOS keeps the login in the Keychain rather than a `.credentials.json`, so there the harness login cannot be linked yet, the run is refused, and token mode is the route; whether Windows writes the file is unverified.

## Dev runs (real Claude Code binary, Max subscription — the default for Anthropic models)

Stages a fixture into a temp workspace, installs the skill into `.claude/skills/` (real skill discovery), runs headless `claude -p`, applies the same L1 verdicts:

```sh
uv run poe dev check_report --model haiku
uv run poe dev review_fixture --model sonnet
uv run poe dev write_from_seed
uv run poe dev import_messy --model haiku
uv run poe dev ideate_scoped --model sonnet
```

(`poe dev` is the registered passthrough for `uv run python harness/claude_runner.py`.)

### Dev-runner L2: `--judge` and `--rejudge`

```sh
uv run poe dev write_from_seed --isolated --judge --keep --model haiku
uv run poe dev write_from_seed --rejudge /tmp/devrun-write_from_seed-abc123 /tmp/devrun-write_from_seed-def456
uv run poe dev write_rich_seed --isolated --judge --max-notional 1
```

`--judge` grades a finished run against the scenario's rubric criteria, after L1 and inside the run's isolated configuration, so it requires `--isolated`. Five scenarios have a rubric twin: `write_from_seed` (RQ quality, density), `write_rich_seed` and `write_repair_citations` (citation scope, synthesis), `review_fixture` (review quality) and `review_hollow` (hollow review). `--judge` on any other scenario is a usage error, so nobody believes they received L2. The criteria and rubric templates are the matrix's own (`harness/l2_rubrics.py`, defined once; the matrix judge's prompts are pinned byte for byte against `tests/unit/data/l2_prompts/`).

- **The judge.** `[roles].dev_judge` in `harness/models.toml`, a full model ID, at its pinned `dev_judge_effort`; `DEV_JUDGE_MODEL` overrides it for one invocation. An alias or a provider-qualified metered ID is refused before any call. Each criterion is one single-turn call to the official `claude` binary under the subscription login (`harness/claude_cli.py`): `--safe-mode`, no tools, one turn, no session persistence, the prompt on stdin, a fixed working directory outside every workspace, never `--bare` (which cannot use the subscription). The child and its `claude auth status` preflight run in the isolated configuration with the same allowlisted environment as the model under test (`host_login.allowlisted_env`), proxy, CA trust, `SHELL` and `LANGUAGE` included. The preflight refuses any login but the subscription's and names the remedy for the login the configuration links (`uv run poe host-login claude` for the harness login, closing with the login note). The first call runs alone (a due login refresh is written back before any fan-out), then at most four run at a time.
- **Not comparable to matrix.** The summary's `l2` block (per-criterion grade or untested reason, `judge_model`, `judge_served`, `effort`, `cli_version`, `thinking_tokens`, `notional_usd`, `rate_limit`) sits under `l2_label: "dev-runner L2, not comparable to matrix"`. The dev judge has a system prompt and asks about the visible request where the matrix judge passes the whole skill prompt. Nothing is written to `logs/evals`, so no dev grade reaches a shipped verdict; confirmation on Inspect stays the route for those. `self_graded: true` marks a run whose model under test is the judge's own model.
- **Re-grades.** `--rejudge DIR…` takes kept workspaces of the positional scenario, selects each artifact with the same selection the L1 verdict uses, and grades it without running the model again, in its own isolated configuration. It grades with the current rubric and request text, which is the point of a re-grade; a scenario whose request changed since the run asks a different question. After the first call it prints a notional projection for the batch and refuses the batch when that exceeds the cap.
- **Bounds.** `--max-notional USD` (default 5.00) caps the cumulative notional cost of an invocation's judge calls. Measured 2026-10-05 at effort `medium`: $0.008–0.022 per call, so a judged write scenario (two calls) costs about $0.02–0.05 notional and a 48-call re-grade about $0.5–1.1 (`openspec/changes/archive/2026-10-05-add-dev-runner-judge/measurement.md`).

Every judge failure is untested, never FAIL: an error result (an expired login names the remedy for the login in use, never an API key), no text or output or per-model usage, an API-key source or a provider other than Anthropic's own API, overage, a rate-limit status other than `allowed`/`allowed_warning` (a warning-level status still grades and reports its window and utilization), no rate-limit report at all, a served model other than the requested one, a time limit (the child is asked to terminate and killed only after the 10 s grace), and a response without a `GRADE:` line. The first such call stops further calls; the criteria left over are untested with the reason. No call is retried.

**Quota.** "$0" holds only while the plan's extra usage stays off; the judge, the dev runs and the smoke draw the same 5-hour and weekly limits as interactive use. The judge's effort is pinned and its environment allowlisted, so an inherited `CLAUDE_EFFORT=xhigh` cannot inflate its usage. After a host upgrade, re-check `claude --help`: `--bare` must never become the default path for `-p`, because the calls would then fail with a login error that no API key may fix.

### Billing, exit statuses and the smoke

Every model run drops each `ANTHROPIC_*` variable (API key, gateway base URL and auth token, `ANTHROPIC_DEFAULT_*_MODEL` remaps) and each `CLAUDE_CODE_USE_*` provider switch from the child's environment, in ambient and isolated mode alike. An ambient run keeps everything else: effort and session settings stay part of what it measures. An isolated run gets the one allowlisted environment of every isolated Claude child (`host_login.allowlisted_env`) instead, which admits none of the billing variables and nothing of the launching session, effort included (see Skill routing); its one `ANTHROPIC_` name is the empty profile directory `ANTHROPIC_CONFIG_DIR`, which the harness sets. A remapped alias therefore resolves to the host's default; `model` in the summary shows what ran. A model-run stream that shows an API-key source, overage, a refused or unknown rate-limit status, or no rate-limit report (or one without its `isUsingOverage` flag) is untested and is not judged: the event is the only signal that a run stayed out of overage, so its absence fails closed. A run the host ended with an error is untested too when its stream reports overage or a refused status — a run stopped at the plan limit ends that way — and stays a runner failure otherwise. A judge result that reports no notional cost is untested as well, since the cap could not count it. If a host stops emitting it, every dev run reads untested with the CLI version named, and the fix is a harness change, never a relaxed rule.

| Exit status | Meaning |
|---|---|
| 0 | every computed verdict passed |
| 1 | a verdict failed (L1, or a graded L2 criterion) |
| 2 | usage error |
| 3 | untested: the subscription could not serve the run or the judge (a refused or missing login, billing other than the subscription, an ungraded criterion), or its isolation did not hold (a claude.ai account surface reached the run) |
| 4 | other runner failure (a budget overrun, a host crash, no result event, a timeout, a crash of the runner itself) |

A runner failure outranks a FAIL, which outranks untested. `--summary-log PATH` appends each run's summary as one JSON line, failures and runner crashes included (a re-grade writes one per workspace); a usage error records none, and neither does a process killed outright. `--summarize PATH` prints one row per scenario from it, exits with the combined status (0 only when every row passed) and removes the log; `--expect SCENARIO …` names the scenarios the sequence ran, so one that left no line is listed as a runner failure instead of being left out of a summary that would otherwise read PASS.

`uv run poe smoke` is that sequence over the registry's `core` scenarios (`write_from_seed` judged, `import_messy`, `customize_override`): each step `--isolated` with `--max-budget-usd 2`, no key file loaded, every step run even after a failure, and a closing `--summarize` over `logs/devrun/smoke.jsonl` that expects all three. Three things keep it off metered billing: the isolated allowlist above, which admits no billing variable, the per-step budget cap, and the post-hoc stream checks that list any other billing as untested. Detection after a run is the only billing check a Claude run has, so a billing signal stops the rest of the smoke: a run untested for billing (an API-key source, overage, a refused or unknown rate-limit status, no rate-limit report, in the model run or the judge's) records the reason as `billing` in its summary line, and every later step that finds such a line in its `--summary-log` starts no host and records itself as `not run: <scenario> reported <reason>`, untested. A log left behind by a smoke that died before its closing step makes the next smoke refuse every step; the message names the log, and `--summarize` clears it. `uv run poe smoke-inspect` is the former metered smoke, behind the matrix cost gate; run it only when the Inspect wiring itself changed.

`import_messy` stages no fixture: the source document is pasted into the request and the verdict is applied to whatever proposal file the skill creates. Both runners reach that verdict through `verdict_import()` in `l1_checks.py`, so the two paths cannot drift apart.

The probe cannot switch on a workflow-by-default host mode — that is a session opt-in — so an ambient run under such a mode is the only way to observe the incident, and it is labelled as such. A host still running at its time limit is asked to terminate and killed only after the 10 s grace. A stream without a result event is a runner failure too, never a silent success; `config_dir` names the isolated directory when one was used.

**claude.ai account surfaces in dev runs.** The runner reads the host's stream as it arrives, through the routing rig's `follow_stream`, and stops the host at the first event that shows a claude.ai account surface. In an isolated run that is any MCP server, any plugin that is not `@builtin`, or any skill tagged "(claude.ai sync)" or named `anthropic-skills:*`, in `init` or in a later `commands_changed` event. In an ambient run it is only an MCP server whose source is `claudeai`; the operator's own servers are part of what an ambient run measures. The protection rests on the order the host emits its events: on 2.1.284, as recorded, `init` and the command-list changes arrive before the model's first turn, so a publishing connector is stopped before any turn that runs with permissions skipped. A host that announced them later would shorten that protection, not remove it. An isolated run whose configuration holds `skills/synced` or `plugins/synced` when the host has finished, or has hit its deadline, is caught after the run, before the directory is removed; the surface then leads the message, ahead of the host's failure or the timeout. Either way the run is untested (exit 3), no verdict is computed and no judge call is made. The message names each surface, says which opt-outs did not hold (in an isolated run the pinned settings and the connector switch, in an ambient run the connector switch alone), names token mode as the fallback (`claude setup-token`, then export `CLAUDE_CODE_OAUTH_TOKEN`), and also names any API-key source, overage or refused rate-limit status the stream shows, so a surface never hides a billing problem. Every model child, the judge's and its `auth status` preflight included, gets `ENABLE_CLAUDEAI_MCP_SERVERS=false`. Every isolated child also gets `ANTHROPIC_CONFIG_DIR` pointing at the configuration's empty `anthropic-empty/` directory, meant to keep an Anthropic profile stored outside the configuration from becoming its login. Whether the host honours the variable is unverified (L8 inconclusive on 2.1.284, 2026-10-05), so an isolated run is also refused while the default profile directory, `${XDG_CONFIG_HOME:-~/.config}/anthropic`, holds any entry (fallback F8). The message names the directory, never its contents; the remedy is to move the profiles aside or to use token mode.

Fast, free on the subscription, highest execution fidelity, with dev-runner L2 on request — but its grades are labelled not comparable to the matrix and it writes no per-model comparison logs; it is the everyday loop, not the source of record.

- **The three stops.** A stop is written to `quota.json` in the home and refuses every later run, before any Copilot process starts, until the user runs `uv run poe host-login copilot --clear-stop` in a terminal outside any agent session. ## Skill routing (real selector, Max subscription)

Every task above hands the agent a skill body and measures what it does with it. `uv run poe routing` measures the step before that: with all eleven skills installed and nothing else, which one does the host actually select for a user utterance? The decision is made from the frontmatter `description` alone — no body is loaded — so this is the only place the descriptions are under test.

```sh
uv run poe routing                              # 46 cases, sonnet, 3 epochs each
uv run poe routing -- --model haiku             # the stress run: the weakest reader
uv run poe routing -- --kind collision --jobs 1
uv run poe routing -- --case review-canonical
```

Cases live in `routing_cases.toml`, four kinds: `canonical` (the phrasing the description promises), `oblique` (how a student types it), `collision` (parked in a zone another skill also claims), `negative` (no `proposal-*` skill may answer). `expected` encodes the *intended* boundary, so a case that routes wrong is a finding about the descriptions, not a dataset bug. Results land in `logs/routing/` and the report is regenerated at `docs/skill-routing.md` — a confusion matrix, because an aggregate pass rate cannot tell you which skill stole which utterance.

The verdict is the first `proposal-*` skill invoked; the run is stopped once that turn's rate-limit report has been read (past the skill call's tool result and the skill's instructions), the run has ended, or the next turn has begun (see Billing below). Up to three preparatory tool calls are tolerated (the agent may glance at a named file first), after which the case counts as unrouted. Only `Skill`, `Read` and `Glob` are reachable, so a measurement cannot start doing the work.

A case the host ends with an error result, typically a dead login, is recorded as an error carrying the host's reason, never as unrouted. A login failure also gets the remedy for the login the sweep linked (`uv run poe host-login claude` for the harness login). Recording it as unrouted would make a logged-out sweep pass every negative case and fail every other one. A case still running at its time limit (90 s, `--timeout`) with no route recorded is an error for the same reason, even past the preparatory bound, where a skill call no longer records one. Errors are listed in the report's own section and kept out of the matrix. Any error makes the run exit non-zero. A run in which no case completed leaves `docs/skill-routing.md` as it was, so the next run is still compared against the last real score.

Isolation matters more here than anywhere else: a run against the operator's own configuration measures the operator's skills, hooks and plugins, not a student's install. The rig therefore builds a temp `CLAUDE_CONFIG_DIR` containing only the claude.ai opt-out settings (`settings.json` exactly `{"disableClaudeAiConnectors": true, "syncClaudeAiPlugins": false, "syncClaudeAiSkills": false}`), an empty `anthropic-empty/` profile directory and a symlink to the harness login's credentials (see Harness login; the `CLAUDE_REAL_CONFIG_DIR` opt-in links the named directory's instead, a long-lived token links nothing), and **refuses to run rather than fall back** to the ambient config or to your own login. Two dead ends worth not re-discovering: `--safe-mode` disables the skills under test along with everything else, and a fresh config directory with no credentials reports `Not logged in`. The former `ROUTING_CONFIG_DIR` override, which used an operator-prepared directory as it was, is no longer read: setting it refuses the run and names `uv run poe host-login claude`, so nobody believes a prepared directory was measured. The environment is isolated too: the child gets `host_login.allowlisted_env` — `PATH`, `HOME`, `CLAUDE_CODE_OAUTH_TOKEN` and machine plumbing (identity and shell, locale, temp, XDG base directories, proxy, CA trust, Windows basics), nothing else — the one builder every isolated Claude child shares, the judge's included. An allowlist rather than a `CLAUDE*` filter, because a desktop-app session also exports host knobs without that prefix (`ANTHROPIC_BASE_URL`, `API_TIMEOUT_MS`, `DISABLE_MICROCOMPACT`, `MCP_*`); before 2026-10-04 an isolated child launched from one recorded `entrypoint: claude-desktop` and inherited its messaging socket and token. The same allowlist admits no `ANTHROPIC_*` variable and no `CLAUDE_CODE_USE_*` switch, so an exported API key cannot move a routing run off the subscription. A run that fails for a missing machine variable is fixed by admitting that one name, with its reason, in `host_login.CLAUDE_ADMITTED`.

The link has one hazard, shared by the dev runner's `--isolated`, which builds the same directory (`harness/host_login.py`). When the host refreshes an expired token, it replaces the symlink with a file of its own and rotates the refresh token. On 2026-10-04 that stranded the only valid refresh token in a deleted temp directory, and every later run failed with "OAuth session expired and could not be refreshed". The linked login is kept current in three ways:

- **Write-back.** While a run is in flight, the harness watches the link. A refresh that expires later is written back to the link's target — the harness login's home by default — with mode 0600, and the link is restored. Nothing is written anywhere else; the run's `login_dir` names that place.
- **One refresher at a time.** The host's refresh lock lives per config directory, so concurrent isolated runs could all refresh at once. A run that starts with an expired login takes `.devrun-refresh.claim` beside the linked login, now inside the harness home. The other runs wait up to 90 s for the written-back login, then refuse. `host-logout` and `--reset` hold the same claim while they log out and wipe.
- **Long-lived token.** With `CLAUDE_CODE_OAUTH_TOKEN` exported (from `claude setup-token`), no credentials are linked at all, so there is nothing to refresh or strand.

Because the harness login is its own, a stranded harness token costs one `uv run poe host-login claude`, never your own login. Only the `CLAUDE_REAL_CONFIG_DIR` opt-in still links your own login, with the R1 and R4 hazard described under Harness login.

**Billing.** Each case's stream is held to the dev runner's billing checks over the part the case read: an API-key source, a provider other than Anthropic's own API where the stream reports one, overage in use, a rate-limit status other than `allowed`/`allowed_warning`, a report without its overage flag, and no rate-limit report at all in a case that served a model turn (`routing.case_billing`; a case stopped for a surface owes no report, before a model turn or after one, and the host's own `<synthetic>` API-error message, a dead login's, is no model turn). On 2.1.284 the report arrives once per run, after the routing turn's assistant events, not before them as on 2.1.207; recorded, it came after a `Read` or `Skill` call's result and before a `Glob` call's (why is inferred: `add-harness-claude-login` design, Context). For a `Skill` route the recorded order (2026-10-05, read to the run's end) is the call, its tool result, the skill's instructions as a second `user` event, then the report, then the next turn. A routed case is therefore read on past its route, its tool result and the skill's instructions, and stopped at the first of the report, the run's result, or the next turn's first assistant event (`routing._case_decided`). For a `Skill` route that is the report, about 2 s in, rather than the run's result 30 s later. Stopped at either of the last two, or at the 90 s limit, without a report, the case counts as unreported. Stopping at the tool result, as the rig did until 2026-10-05, voided every `Skill` route. A case that fails one of them is an error naming the reason, and it voids the sweep: no further case starts a host, every case is recorded as an error naming the billing reason, the raw results are kept, the report is left as it was, and the run exits 1. The money is kept out by the account setting; this is the backstop, and detection after a case is the rig's only billing check, so it stops the rest of the sweep.

**claude.ai account surfaces.** They follow the login, not the configuration directory. Since host 2.1.273 every `/login` session syncs the account's skills and plugins in the background and fetches its claude.ai MCP connectors, so a configuration that links the login carries them too. A case recorded on 2.1.284 (`tests/unit/data/routing_streams/claudeai-surfaces.jsonl`) was offered nine synced skills, among them a `docs` skill that describes itself as the default for any proposal, and the Claude Docs connector, which publishes. The harness closes them in four places (`harness/account_surfaces.py`):

- **Settings.** Every isolated configuration holds exactly the opt-outs `syncClaudeAiSkills: false`, `syncClaudeAiPlugins: false` and `disableClaudeAiConnectors: true`. A configuration that holds anything else, or already holds synced content, is refused before any host process starts.
- **Environment.** Every child gets `ENABLE_CLAUDEAI_MCP_SERVERS=false`. Every isolated child gets `ANTHROPIC_CONFIG_DIR` pointing at the configuration's empty `anthropic-empty/` directory, meant to keep an Anthropic profile in `~/.config/anthropic` from becoming its login. That the host honours the variable is unverified (L8 inconclusive, 2026-10-05), so a sweep is refused before it starts while that directory (or `$XDG_CONFIG_HOME/anthropic`) holds any entry.
- **Per case.** A case whose stream shows any MCP server, a plugin that is not `@builtin`, or a skill tagged "(claude.ai sync)" or named `anthropic-skills:*` is stopped at that event and recorded as an error naming the surface, even when a route was recorded. On 2.1.284 `init` and the command-list changes arrive before the model's first turn, so a polluted case costs one process start and no turns.
- **Per sweep.** When the sweep's shared configuration holds `skills/synced` or `plugins/synced` after the last case, every case of the sweep is voided as an error naming that content. A case started after the content landed may have loaded it with no tag. The raw results are kept, each with the route it measured and its own error after the voiding reason; the report is left as it was, and the run exits 1.

If the opt-outs do not hold, isolated runs refuse instead of measuring a polluted configuration. The fallback is token mode: run `claude setup-token` and export `CLAUDE_CODE_OAUTH_TOKEN` in the shell that starts the harness.

## Install check (both install routes, tracked tree)

`uv run poe install-check` proves the two scripted install routes work on the tracked tree. It exports `git archive HEAD`, byte-for-byte what the registry and the default-branch archive serve, so a checkout's untracked `.claude/skills/*` helpers never leak in. It then installs that export twice, each time under an isolated HOME/XDG:

- **The README's `npx skills add …` command.** The command itself is extracted from the README, so rewording it there without updating reality fails the check.
- **The repository's `install.py --scope all`, given the export as a zip.** The zip's comment carries HEAD's commit id, as a GitHub archive does, and the check asserts the install records name it.

Both arms assert that exactly the eleven shipped skills land byte-identical. Both then run the installed check script against the f15 fixture as a functional smoke.

It runs in its own CI workflow on push and weekly. On the schedule, `--verbatim` additionally resolves the published GitHub repo with `--list`. The skills CLI is deliberately unpinned: users run latest, and an installer regression is the alarm this exists to raise. The check is networked (npx), so it is not part of `poe test`. The installer's own behaviour (scopes, records, conflicts, sources) is covered offline by `tests/unit/test_install.py`.

## Install prompt probe (dev runner)

`uv run poe dev install_prompt` and `uv run poe dev install_prompt_answered` hand the shared install prompt (`shared/blocks/install-prompt.md`) to the real `claude` binary in a temporary HOME. The host always runs under the routing rig's isolated config (`isolated_config`, which links the harness login after its preflight and keeps it current, or links nothing under a long-lived token), so it is logged in without the real home; `--isolated` is implied, and the one-time `uv run poe host-login claude` is needed first. The probe's HOME and USERPROFILE are layered over the isolated child environment. The probe serves `install.py`, and a zip of the working tree's skills, from `127.0.0.1` in place of GitHub.

- **`install_prompt`** (unanswered): passes when the agent asks the scope question and installs nothing.
- **`install_prompt_answered`**: appends the answer "all my projects" up front, and passes when both user-level skill directories hold the full set byte-identical, each with an install record, with no `proposal-*` copy anywhere else.

Exit statuses and the `--summary-log` line are the dev runner's. A prompt or installer that no longer names the URL the probe redirects is a runner failure (4), as is a crash. Subscription-billed, so it is not part of `poe test` or CI. The verdicts, the staging and the run's plumbing (the child's HOME and config, its stripped billing variables, one summary line per outcome) are covered offline in `tests/unit/test_install_probe.py`.

## Audit pre-flight (publish pipeline)

Order: L0 suite (includes `tests/unit/test_audit_invariants.py`) → `uv run python scripts/audit_scan.py` (the real Snyk Agent Scan engine against the repo's skills, staged in an isolated HOME/XDG so the developer's own agent configs are never touched; needs `SNYK_TOKEN` in the environment or in the repo-root `.env`; fails at risk ≥ 0.5 — calibrated 2026-08-02, risk ≤ 0.3 findings exist on skills skills.sh reports clean) → bump `[project] version` in `pyproject.toml` (the suite's one semver source: patch for fixes, minor for new behavior or skills, major for breaking workspace-facing changes), run `python3 scripts/stamp_version.py`, and commit the stamp (`chore(publish): stamp <version>` — writes `metadata.version` into every SKILL.md; re-stamping an already-published version is refused). Installs are git snapshots of `main` (`install.py` fetches its archive, the plugin marketplace syncs it, `npx skills add` clones it; there is no separately built artifact), so an install made after later commits carries the older stamp: the stamp is the **last published version at or before the snapshot**, a floor rather than an identity. `poe identify` treats it exactly that way — the stamp fast-tracks a candidate revision, the blob hashes still decide → publish on explicit request → `uv run python scripts/audit_status.py` (skills.sh verdicts vs `audit-baseline.json`; `--update` after review).

`uv run python harness/audit_llm_preflight.py [--model haiku]` approximates the Gen Agent Trust Hub categories with one headless `claude -p` call per skill (subscription-billed). Its child gets the ambient dev run's environment: every `ANTHROPIC_*` variable and `CLAUDE_CODE_USE_*` switch dropped, the claude.ai connector switch off. Advisory only: ATH's ruleset is unknown and model verdicts vary — never treat a clean run as a guaranteed ATH pass.

## Known limitations

- **Autonomous-harness overreach is pervasive and unguardable by instructions.** In the Inspect agent loop, models modify the proposal during advisory/read-only skills (check *and* review) despite escalating prohibitions. The mechanical hardening was defeated outright: given the SKILL.md chmod guard, Haiku executed `chmod a-w`, later ran `chmod u+w` to remove its own protection, and edited anyway (`check_report_hardened`, 2026-07-29). The same scenarios under the real Claude Code binary (dev runner) hold the mandate — the production environment, not prompt text, is the effective guard. `check_report`, `check_report_hardened`, and the `review_fixture` byte-identity assertions are therefore expected-red on the Inspect path and serve as environment-fidelity probes; details in the archived changes. `title_alarm`'s L1 joins them: on its first metered run (haiku-4.5, 2026-08-05) the model wrote a correct review — L2 passed on all five rubric criteria — and then rewrote the proposal's title to one of its own suggestions and invented four unrequested workspace files (`REVISION_SUMMARY.md`, a check report, a `PUBLICATION_PACKAGE.md`, a `README.md`). The title-rewrite is the scored failure and it is the same overreach, not a title-specific defect.
- The Inspect agent loop approximates but does not replicate real agent harnesses; the dev runner covers Claude Code, the Codex CLI and the GitHub Copilot CLI, and other agents remain untested (spec risk S5). The Codex parsers are pinned on synthetic streams derived from the 0.160 sources until `record-codex-streams` replaces them with recordings, and the Copilot parsers on synthetic fixtures derived from the 1.0.91 package until `record-copilot-streams` does.
- **A fan-out is invisible on the Inspect path and cannot be provoked on the dev runner.** The Inspect agent holds only `bash` and `text_editor`, so it can never spawn a helper. The dev runner's probe (above) reports cost and helper-agent calls per run, but a workflow-by-default host mode is a session opt-in the runner cannot switch on: an `--isolated` run measures the default host, an ambient run measures whatever mode the operator's session carries. The execution-shape sections in review, supervise, check, write, reverse, import and lit-search (2026-09-02, after a real supervise run under such a mode reached 27 agents and ~8.3M tokens) are therefore guarded by L0 pins, and their effect under that mode is measurable only on a real host run with it on.
- **The limitation above is scoped to the Inspect path. A red scenario on the dev runner is a real signal and must be diagnosed, not attributed to it.** Three defects found that way on 2026-07-31 had each been read at first as a skill or model failure: skills addressed their scripts by a path that cannot resolve from the agent's working directory (`scripts/x.py` while the agent stands in the workspace and the skill is installed under `.claude/skills/`), `verdict_check_report` matched relayed prose case-sensitively, and the runner left the child's stdin open so backgrounded runs could die before doing anything. `check_report` was red on the dev runner throughout and now passes 5/5 on haiku and sonnet with the proposal untouched.
