## Why

A proposal's family is now one closed set of files under one handle (tighten-proposal-family), and a review records the research questions it judged (mark-review-currency). Those two changes removed the causes of the incident in which one proposal ended up as ten files under two prefixes. What they left is the listing itself: every family member sits beside every other proposal's members, a rename moves up to a dozen files and edits the links to them, and the family names repeat the handle in each file (`ml-code-review-review.md`). The maintainer settled the layout in a grill-me on 2026-10-14: **every proposal lives in a folder of its own, and the flat layout goes away entirely**, with no layout key and no reading of old names. The only existing workspace is the maintainer's own, which they migrate by hand.

The research for this change also confirmed a defect that already affects `[paths] proposals` workspaces and would affect every proposal under folders: pandoc resolves `img/` links against its working directory, so `publish.py` run from anywhere but the proposal's directory produces LaTeX PDFs and Word documents with the figures silently missing. The typst tier is unaffected because typst resolves paths relative to the `.typ` file.

## What Changes

- **BREAKING: one folder per proposal.** A proposal lives in `<location>/<slug>/`, where `<location>` is still `[paths] proposals` (default `.`, the workspace root) and the folder's name is the slug under the existing slug rules. `bug-report`, `img` and hidden names never name a proposal folder. A slug-shaped folder counts as a proposal folder only when it holds `<dir>.md`, a `notes.md` carrying the notes file's five section headings, or a `harvest.md`; any other folder (a user's `meetings/` or `literature/`) is invisible to the skills.
- **BREAKING: names inside the folder.** Files that leave the folder keep the handle: `<slug>.md`, `<slug>.pdf`/`.docx`/`.typ`/`.tex`, and the hand-in export `<slug>.handout.md` (a dot, replacing `<slug>-handout.md`). Files that stay are named by role: `notes.md`, `review.md`, `feedback.md`, `harvest.md`, figures `img/<name>.<ext>` without a slug prefix, and kept files `<label>.<ext>`. The labels `notes`, `review`, `feedback`, `harvest`, `handout` and `img`, and the slug itself, are reserved.
- **BREAKING: the flat layout is removed.** No skill treats a file outside a proposal folder as a proposal or companion, and no old file name is read. `ideation.notes.md` no longer exists: ideation creates `idea/notes.md` at once (`idea-2/`, … when taken), renames the folder to a provisional slug when a topic phrase exists, and to the final slug at seeding.
- **Renaming becomes a folder move.** A rename moves `<old>/` to `<new>/` (target checked first, nothing overwritten, the result verified so a move into a folder that appeared meanwhile is caught, stop and report on failure), then `<old>.md` to `<new>.md`. Role-named files and figures need no change, so no link is edited. Built outputs and the hand-in export under the old slug stay in the folder as previous outputs, named to the user with a rebuild offered. Ideation's automatic rename to a provisional slug never ends a session when it fails; it is retried at seeding.
- **Submissions are sources.** A professor's saved submission, a standard-format `.md` at the workspace root included, is read as a source document: `proposal-supervise` copies it into a new proposal folder and leaves the original as it was.
- **`proposal-check` reports the layout.** `proposal-misplaced` (error) names `<location>/<slug>/<slug>.md` when the proposal is anywhere else, measured from the working directory, which is the workspace root (design D17); a new error, `proposal-folder-mismatch`, fires when the folder's name differs from the proposal's file name. `companion-orphaned` is redefined for folders: a `review.md`, `feedback.md` or `<dir>.handout.md` in a slug-shaped folder that holds no proposal, notes file or harvest record (design Q2), and family-shaped files and `img/` at the location root. Design D21 adds the workspace root to that scan, a proposal folder moved into another one, and a second proposal inside a folder, recognized by its title, subtitle and metadata block (design Q5). A new warning, `build-definition-unused`, names a build definition at the location root or the workspace root, where publish never looks. The report gains a line naming which `guidelines.md` governed the run, by position only (beside the proposal, working directory, explicit, none), never by path.
- **Unchanged rules, new consequences.** Scripts still run from the workspace root, where `api-keys.env`, `guidelines.md` and `bug-report/` live. Publish still looks for a build definition only beside the proposal (now: in its folder) and never falls back. Publish still writes its `.gitignore` beside the proposal, now inside the folder.
- **`proposal-troubleshoot`** looks up companions by role inside the folder, records them under their role names, and redacts the proposal's stem, which also removes the folder name from every path, the notes file's Log excerpt included below the most disclosing level; of the notes file it stores the Log section alone, and nothing when there is none (design decision log, 2026-10-15). `bug-report/` stays at the workspace root, and the reduced reproduction inside it is a workspace of its own, `bug-report/repro/input/input.md` checked from `bug-report/repro/`.
- **Fixed: figures in LaTeX and Word exports.** `publish.py` passes `--resource-path` set to the proposal's folder, so figures embed whatever the working directory, and relays pandoc's `[WARNING]` lines on a successful build instead of discarding them. A folder path containing the platform's path-list separator is built with the folder as pandoc's working directory instead (design D11). The changelog gets a separate *Fixed* entry, drafted in design D11.
- **Shared block and prose.** `shared/blocks/workspace-files.md` carries the new role table and folder rules once; the about 66 per-skill mentions, the import mandate, nine pinned sentences and three execution-shape pins follow it.
- **Fixtures and harness.** Every proposal fixture (`f*`, `w*`) is restructured into workspace shape, `tests/fixtures/<fixture>/<slug>/<slug>.md` with role-named companions, and its `expected.json` recalibrated against `check.py`; the import-source PDFs become `submission.pdf` at their fixture's root, outside the folder. Before any fixture moves, every test and runner calls the check from the workspace root and resolves fixture files through one helper, and every corpus walker, the typst CI script included, is held to the oracle count. Draft selection, the family verdicts and the runners' workspace listings follow the folders. Six new dev-runner scenarios cover ideation from scratch (three turns, judged on the recorded moves), import with figures, publish with figures on the typst, the LaTeX and the Word tier (judged on tier evidence; where hidden tools stay reachable the LaTeX and Word runs are recorded untested and the L0 figure test carries those tiers, design Q7), and a kept file on request; with the existing rename and review scenarios they make up the six flows run on the subscription, haiku and sonnet, one at a time. The supervise readiness scenario stages its submission at the workspace root and runs once on sonnet.
