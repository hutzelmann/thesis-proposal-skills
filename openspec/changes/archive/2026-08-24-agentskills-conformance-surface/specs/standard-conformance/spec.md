## Purpose

Keeps the published skills conformant with the Agent Skills standard (agentskills.io) and keeps the repository honest about where and why it deliberately diverges.

## ADDED Requirements

### Requirement: Per-skill eval definitions shipped as a generated projection
Every skill that the harness tests SHALL ship an `evals/evals.json` in the standard's eval format — test prompts, expected outputs, input files, and assertions — generated from the harness's own task definitions by repository tooling. The file SHALL be marked as generated, SHALL be covered by a drift check in the default test chain like other generated copies, and SHALL never be the source of truth: a harness task change flows into the projection, never the reverse.

#### Scenario: Harness task changes
- **WHEN** a task's prompt, fixture binding, or verdict expectations change in the harness
- **THEN** the affected skill's `evals/evals.json` is regenerated by the tooling, and the drift check fails until it is

#### Scenario: Projection edited by hand
- **WHEN** an `evals/evals.json` is edited directly
- **THEN** the drift check fails, pointing at the harness as the place to make the change

#### Scenario: Visitor reads a published skill
- **WHEN** someone inspects an installed or published skill
- **THEN** its eval definitions are readable in the standard's format without access to this repository's harness

### Requirement: External conformance validator as a canary
The default test chain SHALL run the standard's reference validator, at a pinned version, over every skill directory, alongside the repository's own stricter checks. Updating the pin SHALL be a reviewed change, so movement in the standard arrives as a visible diff rather than silently.

#### Scenario: Skill violates the standard's format rules
- **WHEN** a skill's frontmatter or layout breaks a rule the reference validator checks
- **THEN** the conformance task fails even if the repository's own checks pass

#### Scenario: Standard evolves
- **WHEN** the pinned validator version is bumped and the new version rejects a previously accepted skill
- **THEN** the failure surfaces in the default chain and is resolved by a reviewed change, either conforming or recording a deliberate divergence

### Requirement: Documented conformance stance with a deliberate-divergence list
The repository's user-facing README and agent-facing instructions SHALL name the standard being followed, state how conformance is validated, and enumerate every deliberate divergence with its reason. A divergence not on the list SHALL be treated as a defect, not a choice.

#### Scenario: Contributor encounters a divergence
- **WHEN** a contributor finds repository behavior that contradicts the standard
- **THEN** the divergence list either names it with its reason, or the contradiction is a bug to fix

#### Scenario: Limits mirror the standard
- **WHEN** a repository check enforces a numeric limit taken from the standard
- **THEN** the check names the standard as the source, so the two cannot drift apart unnoticed
