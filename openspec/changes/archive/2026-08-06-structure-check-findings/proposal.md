## Why

`check()` in `skills/proposal-check/scripts/check.py` is one 252-line procedure with 72
local variables, 64 branches and 140 statements, appending strings into two parallel lists.
It is the only file in the repository still carrying a complexity exemption, and the two
changes before this one deferred to it by name.

The size is the visible problem; the contract is the real one. A finding exists only as
English prose in a `list[str]`, and everything downstream reads it by grepping that prose:
`harness/l1_checks.py` filters errors by `line.startswith("- ERROR:")` and tolerates a
reference shortfall by searching for the substring `"references — at least"`; the 25 fixture
oracles pin findings as `errors_contain` fragments like `"boolean literal"`. Rewording a
message to make it clearer to a student can therefore break the harness, and a check that
stops firing entirely still passes any oracle whose fragment happens to appear in another
message. The report is written for a human and parsed by machines, and it cannot serve both
well.

## What Changes

- **A finding becomes a value.** A frozen `Finding` dataclass carries `level`
  (`error` / `warning`), `rule` (a stable kebab-case identifier such as
  `duplicate-reference-id`), and `message` (the prose a student reads). The rule identifier
  is the contract; the message stays free to be reworded.
- **`check()` splits into rule functions.** Each takes the parsed proposal and the effective
  configuration and returns `list[Finding]`. A registry lists them in report order, so the
  rendered report keeps its current sequence. Each rule becomes directly testable without
  driving the whole script.
- **`--json` output mode.** Emits the digest, the exit code, and the findings as objects.
  The human report is unchanged, byte for byte: the same two buckets, the same wording, the
  same deferred-to-the-agent note. Consumers that want structure ask for structure.
- **Oracles gain rule identifiers.** Every `expected.json` grows a `rules` list beside its
  existing `errors_contain` fragments, and `test_fixture_oracles.py` asserts on both: the
  identifiers pin *which checks fired*, the fragments keep pinning *how the message reads*.
  The two together close the gap where a fragment matched the wrong finding.
- **The harness stops grepping prose.** `disallowed_errors` gains a rule-based path, so the
  reference-shortfall tolerance is expressed as a rule identifier rather than as a substring
  of an English sentence.
- **The last complexity exemption goes.** `[tool.ruff.lint.per-file-ignores]` becomes empty
  and is removed.

The proposal file format, the guidance data, and every rule's *behaviour* are untouched. No
finding is added, removed, or re-levelled; a proposal that passes today passes after this
change, with the same exit code and the same text.

## Capabilities

### Modified Capabilities

- `skill-check`: adds a requirement that every mechanical finding carries a stable
  identifier and that the script can emit findings as structured data, alongside the
  existing human report.

## Impact

- `skills/proposal-check/scripts/check.py` (the sync source) and its two generated copies in
  `proposal-import` and `proposal-write`, regenerated by `scripts/sync_shared.py`.
- `harness/l1_checks.py`: `disallowed_errors` and the two `*_ALLOWED_ERRORS` tuples.
- All 25 `tests/fixtures/*/expected.json` oracles, and `tests/unit/test_fixture_oracles.py`.
- `pyproject.toml`: the final `per-file-ignores` entries removed.
- Still stdlib-only and Python ≥ 3.11: `dataclasses` and `json` are both standard library,
  so the user-side constraint in `AGENTS.md` holds.
