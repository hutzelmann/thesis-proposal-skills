# Record the polish routing boundary

## Why

`2026-10-05-route-polish-to-write` left two loose ends.

- **The boundary it moved is guarded only in prose.** `proposal-write`'s description now ends "…including to get it ready for a supervisor". The readiness moment belongs to `proposal-review`, which owns "ready for their supervisor" and "before handing it to a supervisor". The owned-trigger table records "polishing pass" for write, but nothing records the readiness split itself, and the skill-packaging requirement "One owner per contested trigger term" asks for exactly that. Write's description also enters a situation review owns without saying so. Under "A skill that declines a contested situation names the one that owns it", it has to name `proposal-review` for the readiness question.
- **The README's haiku row says less than the measurement found.** `measurement.md` (2026-10-05-route-polish-to-write) shows that haiku loads `proposal-write` for a polishing request in 3 of 3 dev runs, where write is the only installed skill. On the routing rig, with all eleven skills installed as in a student's workspace, the polish case still reaches no skill: 0/3 before the edit and 0/3 after. That change added no README note, because its fallback rule was tied to the dev-runner result. A haiku user with the full set therefore gets no warning that a polishing pass will most likely run without the write skill.

## What Changes

- **Owned-trigger table** (`tests/unit/data/trigger_terms.json`):
  - "get it ready for a supervisor" → `proposal-write`. Write's description contains the phrase and review's does not, so the L0 claimant check now fails if review, or any other skill, takes it over.
  - A `_comment` line records the split by intent. A request to change the text so the proposal is ready is write's. The question whether it is ready stays review's.
- **`proposal-write` description** (`skills/proposal-write/SKILL.md`). One sentence is appended, in the form `proposal-check` already uses for its review boundary: "Not a readiness verdict — for whether it is ready, use proposal-review." The user-approved wording before it is unchanged. The description grows from 403 to 475 characters (budget 500), and the combined metadata from 4,266 to 4,338 (budget 4,500).
- **Haiku model note**, through its source.
  - The README model-support table is generated by `poe report`, and a model's free-text caveat reaches it only through the `note` field of its `harness/models.toml` entry (testing-harness: "A registry note SHALL appear in the model's summary-row notes"). The haiku entry gains that note, with a comment citing the measurement.
  - The note says that with all skills installed, polishing and editing requests are not reliably routed to `proposal-write` (0/3 on the routing rig, 2026-10-05), so such passes need sonnet or opus.
  - `poe report` was rerun against the eval logs that produced the shipped table. The only change is the haiku row of the README. `docs/model-support.md` and `shared/model-support.json` regenerate byte-identical, because neither carries notes.
