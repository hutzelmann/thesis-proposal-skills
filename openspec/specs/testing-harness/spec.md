# testing-harness Specification

## Purpose
Automated verification that all skills work as specified across models: a three-layer test pyramid with deterministic fixtures and model-graded rubrics.

## Requirements

### Requirement: Three-layer pyramid
Testing SHALL provide: L0 unit tests for all shipped scripts (no model calls, CI-safe); L1 structural tests running each skill against fixture workspaces per model with deterministic artifact assertions; L2 rubric tests grading semantic quality via model judges (analytical RQ phrasing, Socratic compliance, review actionability, German quality).

#### Scenario: Script regression
- **WHEN** a check-script rule breaks
- **THEN** an L0 test fails without any model involvement

#### Scenario: Semantic regression
- **WHEN** a model under test produces implementation-goal research questions
- **THEN** the L2 rubric scores it below threshold and the run fails

### Requirement: Multi-turn ideation testing
Ideate SHALL be tested in multi-turn dialogues against student personas on the metered path. The dialogue suite SHALL comprise one long composite run and several short adversarial probes, replacing cooperative-only coverage:

- **Long composite run**: a scripted persona drives roughly eighteen rounds through distinct phases — administrative preamble, hesitant idea development, an extraction probe (a direct request for finished research questions), a topic pivot, convergence, and seeding. Phase boundaries are scripted so graders can attribute failures. Between rounds the harness SHALL assert workspace state mechanically: the notes file appears once a topic exists and grows across the dialogue, and no proposal file exists before convergence.
- **Short probes**: a stonewalling persona whose non-contributions must trigger the early stop (state saved to notes, no proposal file); a no-idea persona for whom floated hints must name their source and never form a topic menu; an out-of-scope persona whose insistence must yield exactly one chat-only warning and a clean seed; and a probing persona — agreeable, vague, extraction-minded, offering only generalities while pushing for a finished proposal — whose run must end without a seeded proposal: the swap test voiced, the impasse named after persistent genericity, state saved to notes, and no specifics generated by the assistant.

Two instruments SHALL grade student-originated content and tutoring quality:

- **Provenance check**: a pure function in the shared verdict module that takes the transcript and the seeded file and verifies the substantive content terms of the working title and candidate research-question directions occur in student turns — a term the student never voiced in any turn counts against the run. First utterance is deliberately not the criterion: good tutoring crispens the student's phrasing, so the assistant may voice the sharp term first and the student adopts it. It SHALL be exercisable by L0 tests without a model call.
- **Uptake rubric**: the L2 Socratic rubric SHALL judge, per phase, that assistant turns build on the student's preceding turn, ask at most one question, contain no praise padding, tell only conventions (never idea content), and confine direct administrative questions to the two bookends — the preamble block and the closing seeding step, which the rubric SHALL recognize as sanctioned direct questions.

#### Scenario: Long run graded per phase
- **WHEN** the long composite dialogue completes
- **THEN** the transcript is judged phase by phase, and a collapse at the extraction probe (assistant supplies finished research questions) fails that phase

#### Scenario: Notes growth asserted mechanically
- **WHEN** the long run passes its topic-establishing phase
- **THEN** the harness finds a notes file in the workspace and its size or content grows by the pivot phase, without any model judging this

#### Scenario: Stonewaller triggers early stop
- **WHEN** the stonewalling persona deflects three consecutive exchanges
- **THEN** the run passes only if the assistant named the impasse, the notes file records the state, and no proposal file was created

#### Scenario: Prober never receives a generic proposal
- **WHEN** the probing persona agrees with everything, contributes only generalities, and repeatedly asks the assistant to just write it down
- **THEN** the run passes only if no proposal file was seeded, the notes file records the state, and the transcript shows the swap test voiced before the impasse

#### Scenario: Generic content fails provenance
- **WHEN** a seeded file's research-question directions use substantive terms that never occurred in any student turn
- **THEN** the provenance check fails the run without model involvement

#### Scenario: Bookend questions pass the rubric
- **WHEN** the assistant opens with the administrative block and closes confirming dates
- **THEN** the Socratic rubric does not count these as violations

### Requirement: Inverted-hybrid runners
Authoritative runs — the model matrix, release gates, and the judge and persona models those runs grade with and converse with — SHALL execute over metered API providers with native multi-model comparison and spend caps. Subscription-based CLI runs serve as the cheap everyday dev loop and are not the source of record. That includes the dev runner's own rubric judge: its grades SHALL be labelled as dev-runner results that are not comparable to matrix results, SHALL NOT be written where the support report reads its logs, and SHALL NOT stand in for an authoritative cell. CI executes only L0 and lint by default; metered eval runs are budget-capped.

Every L1 verdict SHALL be defined once as a pure function in the shared verdict module, taking plain values and returning a pass flag with an explanation, and both runners SHALL reach a scenario's verdict through it rather than reimplementing the assertions. Because the verdicts are pure, each SHALL be exercisable by L0 tests without a model call.

A verdict that asserts a produced file is in the standard format SHALL establish that by running the mechanical check over it and judging the reported errors, never by inspecting the text for characteristic substrings. Errors that follow from information the scenario's input did not carry MAY be tolerated, and the tolerated set SHALL be explicit. Where a defect makes the file unbuildable but is invisible to the mechanical check — which extracts narrowly rather than parsing YAML — the verdict SHALL assert it directly, and SHALL be narrow enough to admit the shapes that do build.

The dev-runner scenario set SHALL cover the import skill. It SHALL therefore support scenarios that stage no proposal file and instead supply a source document in the request, and that assert against a file the skill creates — whose name the skill chooses — rather than one staged in advance.

Wherever a scenario's skill is licensed to choose the produced file's name — including scenarios that stage a seed the skill may replace with a fresh `<slug>.md` — the verdict SHALL locate the produced proposal in the workspace rather than assume a staged filename. The selection SHALL be a pure function in the shared verdict module, exercisable by L0 tests without a model call, and both runners SHALL grade the file it selects.

#### Scenario: Release gate
- **WHEN** a release-gating eval is run
- **THEN** it executes on the metered authoritative path with per-model logs, not on the subscription dev runner

#### Scenario: Dev-runner grade is not a source of record
- **WHEN** a dev run is graded by the subscription judge
- **THEN** its summary labels the grades as dev-runner L2, not comparable to the matrix, and no file the support report reads has been written or changed

#### Scenario: Verdict reached from both runners
- **WHEN** a scenario's L1 assertions are evaluated on the metered path and on the dev runner
- **THEN** both call the same shared verdict function and reach the same pass flag for the same produced artifact

#### Scenario: Import iterated without metered spend
- **WHEN** import guidance is being iterated on
- **THEN** the dev runner can exercise the import skill end to end, pasting the source document into the request and judging the file the skill creates

#### Scenario: Structurally broken output rejected
- **WHEN** a produced file contains the expected substrings but leaves the metadata block unclosed and the reference list malformed
- **THEN** the verdict fails on the mechanical check's errors rather than passing on the substrings

#### Scenario: Unbuildable file the mechanical check cannot see
- **WHEN** a produced file places a TODO marker as a bare line inside the metadata block, so the document converter rejects the block while the mechanical check reports no error
- **THEN** the verdict fails on that defect

#### Scenario: Marker shapes that do build are accepted
- **WHEN** the same marker appears as the value of a key, quoted or unquoted
- **THEN** the verdict does not fail, because those shapes parse

#### Scenario: Tolerated shortfall
- **WHEN** the source document carries fewer references than the guidance requires
- **THEN** the reference-count error alone does not fail the verdict, because the skill must not invent sources

#### Scenario: Verdict logic covered without a model
- **WHEN** an L1 verdict's failure modes are tested
- **THEN** L0 tests call the pure verdict function directly and no model is invoked

#### Scenario: Draft written to a fresh filename
- **WHEN** a write scenario's model creates a new `<slug>.md` instead of editing the staged seed in place
- **THEN** the verdict grades the created file, not the untouched seed

### Requirement: Publish filter regression coverage
The harness SHALL cover the publish skill's pandoc filters with regression tests, including at least one fixture whose research-question list contains an in-text citation; the filter output MUST contain the citation resolved rather than an unprocessed citation key. Tests requiring external converters SHALL be skipped cleanly when those tools are absent.

#### Scenario: Citation inside a research question
- **WHEN** the rq-filter regression test runs with pandoc available
- **THEN** the typst output wraps each research question and contains no unresolved citation keys

### Requirement: Session-derived fixtures
Fixtures MAY be curated from real skill-session output when the session used a synthetic topic. Such fixtures MUST be audited against the committed session log, MUST NOT contain personal data, and follow the same oracle rules as invented fixtures.

#### Scenario: Fixture curated from a demo session
- **WHEN** a session-derived fixture is added to the corpus
- **THEN** its content traces to a committed session log, contains no personal data, and ships with an `expected.json` oracle

### Requirement: Fixture corpus with oracles
Fixtures SHALL follow the fixture blueprint: synthetic proposals covering both languages, both levels, all quality tiers, every mechanical check rule (tripped at least once and passed at least once), every methodology branch, clean controls, and workflow states — each with an `expected.json` ground-truth oracle consumed by L1/L2. Fixtures MUST NOT contain content from real proposals; personal data in fixtures is obviously fake.

#### Scenario: New check rule added
- **WHEN** a new mechanical rule enters the check skill
- **THEN** at least one fixture trips it and one passes it, encoded in their oracles

### Requirement: Prose-relaying verdicts match without regard to case

A verdict that judges whether a skill relayed given content into its chat answer SHALL match case-insensitively. Sentence capitalisation is a property of prose, not of the finding being relayed, so a correct relay SHALL NOT fail on it.

#### Scenario: Relay begins a sentence with the finding

- **WHEN** the skill reports a finding as "Duplicate reference id `Lee24Index`" and the oracle records it as "duplicate reference id"
- **THEN** the verdict counts it as relayed

#### Scenario: Finding genuinely absent

- **WHEN** the skill's answer never mentions a finding the oracle records
- **THEN** the verdict does not count it, and enough missing findings still fail the scenario

### Requirement: Export paths are verified by building real documents

Automated verification SHALL build real documents on every export path the publish skill can resolve, over the full fixture corpus, and SHALL assert that each build completes and produces its declared outputs. A test that only exercises path selection, argument assembly, or offline helpers SHALL NOT be treated as coverage of a build path.

Such a test SHALL drive the shipped build entry point rather than reassembling the converter invocation, so that a defect in how the shipped code constructs that invocation is caught rather than reproduced.

#### Scenario: A broken tier fails the suite

- **WHEN** a change makes one output tier unable to produce a document
- **THEN** the export verification fails for that tier, naming it, without any model involvement

#### Scenario: Selection logic alone is not coverage

- **WHEN** the only test touching a tier verifies which engine would be chosen
- **THEN** that tier counts as unverified, because no document was produced

### Requirement: CI provides the document toolchain

Continuous integration SHALL provide the converter and engines the export verification needs, so those tests execute rather than skip. Toolchain provisioning SHALL use pre-built published images at pinned versions, so a failing run always indicates a change in this repository rather than an upstream update. Where an image cannot host the test runner, the export path it covers MAY be exercised by a script, and that script's invocation SHALL be guarded against divergence from the shipped build path by a test requiring no toolchain.

#### Scenario: Toolchain absent locally

- **WHEN** a contributor without the toolchain runs the suite
- **THEN** the build tests skip and the rest of the suite passes, while CI still executes them

#### Scenario: Script and shipped build diverge

- **WHEN** the shipped build path gains a converter filter that a CI build script does not
- **THEN** the divergence guard fails, independently of whether any toolchain is installed

### Requirement: Notes files excluded from draft selection
The shared draft-selection function SHALL treat files ending in `.notes.md` as non-proposal markdown, alongside the existing non-proposal names, so no verdict ever grades a notes file as the produced proposal. The exclusion SHALL be covered by L0 tests without a model call. Fixtures MAY ship notes files; a notes file carries no `expected.json` oracle obligations of its own.

#### Scenario: Notes file never selected as the draft
- **WHEN** a scenario workspace contains `energy-attack.notes.md` and `energy-attack.md`
- **THEN** draft selection returns `energy-attack.md` even when the notes file sorts first

#### Scenario: Exclusion tested without a model
- **WHEN** the L0 suite runs
- **THEN** a unit test exercises the `.notes.md` exclusion through the pure selection function

### Requirement: Title-alarm coverage
The corpus SHALL carry at least one fixture whose title trips several title tells at once, with the tells encoded in its `expected.json` oracle, alongside the existing fixtures whose titles trip none. The agent-judgment half of the title rule — recognising that a proper noun names a tool carried as the instrument, and offering abstracted alternatives — is not reachable by any offline test, so it SHALL be covered by a metered L2 eval task scoring whether the skill raises the title, names the certificate consequence, and offers alternatives without silently rewriting the title.

#### Scenario: Bad-title fixture
- **WHEN** the corpus is exercised against the deterministic check
- **THEN** the bad-title fixture reports its title tells as warnings, matching its oracle, and the run does not fail on them

#### Scenario: Clean-title control
- **WHEN** a fixture whose title names a contribution and its object is checked
- **THEN** no title warning is emitted and its oracle records none

#### Scenario: L2 title alarm scored
- **WHEN** the metered title eval runs against a proposal whose title carries a tool name as the instrument
- **THEN** the score reflects whether the skill raised the title, named the certificate consequence, and offered abstracted alternatives rather than replacing the title unannounced

### Requirement: Support classification exported as data

The support classification the matrix produces SHALL be exportable as machine-readable data alongside the human-readable report, keyed by model and task, so it can be vendored into a skill that must consult it without network access or repository access. The export SHALL distinguish an untested cell from a failing one, because a skill treating "never measured" as "passes" would clear a model it knows nothing about.

#### Scenario: Verdicts exported after a matrix run

- **WHEN** the classification is regenerated from eval logs
- **THEN** a machine-readable export is produced alongside the report, keyed by model and task

#### Scenario: Cell never measured

- **WHEN** a model and task combination has no eval result
- **THEN** the export marks it untested rather than passing

### Requirement: Report offer discipline covered by tests

The uniform failure-path report offer SHALL have negative coverage: the offline suite SHALL fail when a skill's offer wording drifts from the set's, and the model-facing evals SHALL cover that a skill completing normally with findings does not offer a report. A false positive here is more damaging than a miss, because an offer on every ordinary run teaches users to ignore it.

#### Scenario: Skill reports findings on a flawed fixture

- **WHEN** a diagnostic skill runs against a fixture whose oracle expects findings
- **THEN** the eval fails the run if the skill offers a bug report

#### Scenario: Offer wording drifts in one skill

- **WHEN** one skill's offer wording no longer matches the set's
- **THEN** the offline suite fails naming that skill

### Requirement: Externally submitted reproduction seeds

A reproduction seed submitted with a bug report MAY enter the fixture corpus, subject to provenance rules distinct from session-derived fixtures: no committed session log backs it, so it SHALL be verified to contain no real proposal content and no personal data, SHALL be confirmed to still trigger the reported defect before entry, and SHALL receive an `expected.json` oracle encoding the corrected behavior rather than the observed one.

#### Scenario: Submitted seed accepted

- **WHEN** a submitted reproduction seed is verified synthetic and still triggers the defect
- **THEN** it enters the corpus with an oracle encoding the behavior the fix must produce

#### Scenario: Submitted seed no longer reproduces

- **WHEN** a submitted seed does not trigger the defect on the current revision
- **THEN** it is not added, and the report is answered with the revision that already fixed it

#### Scenario: Submitted seed carries real content

- **WHEN** a submitted seed contains recognizable real proposal content or personal data
- **THEN** it is rejected from the corpus regardless of its diagnostic value

### Requirement: Substance-verdict coverage
The fixture corpus SHALL contain at least one hollow control: a proposal that passes every mechanical check with zero errors and zero warnings while failing at least the guidance's swap, delta, and executability tests — generic well-sounding text naming no object of study and no delta beyond its citations. Its oracle SHALL encode the check-clean state, so the fixture doubles as proof that "mechanically clean" carries no substance signal. Naming those three tests is a statement about this fixture, not about how many tests exist.

A metered review task over the hollow control SHALL assert: the review file opens with the verdict "no viable thesis core"; at least two failed substance tests are cited by name; the proposal file is byte-identical after the run. The verdict-line assertions SHALL be a pure function in the shared verdict module, exercisable by L0 tests without a model call. A model-graded scorer SHALL additionally judge that the review states what kind of work would change the verdict and that no finding is softened into needs-revision phrasing.

#### Scenario: Hollow control stays check-clean
- **WHEN** the mechanical check runs over the hollow fixture
- **THEN** it reports zero errors and zero warnings, exactly as the fixture's oracle encodes

#### Scenario: Review task fails on a soft verdict
- **WHEN** the review of the hollow fixture opens with "needs revision" or omits the failed-test names
- **THEN** the L1 verdict fails the run without model involvement

#### Scenario: Verdict logic covered without a model
- **WHEN** the verdict-line function's failure modes are tested
- **THEN** L0 tests call it directly on crafted review texts and no model is invoked

### Requirement: Proposal-prose density scoring
The write task producing a full draft SHALL carry a model-graded scorer that judges the draft body against the information-density rule: scene-setting openers, truisms, restatements of the obvious, and sentences that would fit any thesis in the area fail the grade. The scorer SHALL follow the harness's rubric-template contract and the `*_l2*` naming the support classifier reads.

#### Scenario: Padded draft fails the density grade
- **WHEN** a produced draft opens sections with generic scene-setting sentences
- **THEN** the density scorer grades the sample incorrect, naming the filler

#### Scenario: Dense draft passes
- **WHEN** every sentence of the draft carries thesis-specific information
- **THEN** the density scorer grades the sample correct regardless of section length

### Requirement: Tone criteria in artifact rubrics
The review-quality rubric SHALL include the voice-block conduct rules: the graded review contains no praise of the student or their draft, no self-congratulation by the agent, and neutral constructive wording throughout. The Socratic dialogue rubric's existing no-praise-padding criterion SHALL remain.

#### Scenario: Praising review fails the rubric
- **WHEN** a graded review opens by complimenting the student's excellent proposal before its findings
- **THEN** the review-quality judge grades the sample incorrect on the tone criterion

### Requirement: Pinned model registry
Matrix runs SHALL take their model roster exclusively from a tracked registry file pinning exact provider-qualified model IDs (the version visible in the ID), each with family, price tier, cached input/output pricing, and an enabled flag. A registry entry MAY carry a free-text note recording a caveat about the model's standing in the matrix — for example that the harness cannot drive it — which SHALL default to empty when absent. The roster SHALL cover at least three model families (Anthropic, OpenAI, open-weight) at cheap and frontier price points. Changing a model version SHALL require editing the registry, never a runtime "latest" resolution, so successive runs stay comparable.

The registry SHALL record the date its prices were copied from the provider's catalog. Prices SHALL be taken from the model vendor's own endpoint at its standard service tier. An entry MAY name the endpoint its prices come from. It SHALL do so when the vendor's provider name differs from its catalog namespace, or when the vendor serves no endpoint of its own.

The registry SHALL also carry a roles table naming every model the harness uses outside the roster:

- the rubric judge of matrix runs;
- the dialogue persona, which SHALL default to the judge when absent;
- the metered smoke model, which SHALL name an enabled roster entry;
- the subscription dev-runner judge, together with its pinned effort level.

Every roster and role ID SHALL be a pinned full ID. A floating alias SHALL make registry parsing fail and name the offending entry. Floating aliases are a bare family name, a `~`-prefixed ID, and an ID ending in `-latest`. The judge's ID SHALL appear only in the roles table; the judge's per-run token budget MAY stay with the task configuration.

Every metered role, that is the judge and the persona, SHALL be priced by the registry: by the roster entry with its ID, or, when no roster entry carries that ID, by a price-only role-price entry under the same price basis and date. A registry whose judge or persona cannot be priced SHALL fail parsing and name the role. A role-price entry that no role names, or that duplicates a roster entry, SHALL fail parsing. All harness price lookups SHALL go through this one resolution.

Harness code SHALL take these IDs from the registry. An environment override MAY replace one role for one invocation, and SHALL NOT carry over to any other role.

#### Scenario: Roster comes from the registry
- **WHEN** a matrix run is started with a tier filter
- **THEN** exactly the enabled registry models of that tier are exercised, under their pinned IDs

#### Scenario: Disabled model skipped
- **WHEN** a registry entry sets enabled to false
- **THEN** matrix runs omit it without failing

#### Scenario: Note is optional
- **WHEN** a registry entry carries no note
- **THEN** the registry parses and the model's rendered notes are unchanged

#### Scenario: Role changed in the registry only
- **WHEN** the judge role is set to a different pinned ID in the registry and no override is present
- **THEN** the rubric scorers and the cost estimate both use the new ID without any code edit

#### Scenario: Floating alias rejected
- **WHEN** a roster entry or a role names `sonnet`, `~anthropic/claude-sonnet-latest`, or any ID ending in `-latest`
- **THEN** registry parsing fails and names the offending entry

#### Scenario: Judge named twice
- **WHEN** the task configuration still carries a judge model ID beside the roles table
- **THEN** registry parsing fails and points to the roles table

#### Scenario: Smoke model outside the roster
- **WHEN** the smoke role names an ID that is not an enabled roster entry
- **THEN** registry parsing fails

#### Scenario: Persona defaults to the judge
- **WHEN** the roles table names a judge and no persona
- **THEN** the persona resolves to the judge's ID

#### Scenario: Judge override does not move the persona
- **WHEN** an invocation overrides the judge from the environment and does not override the persona
- **THEN** the persona keeps the registry's persona role

#### Scenario: Held judge priced after leaving the roster
- **WHEN** the roster entry that carried the judge's ID has been re-pinned and a role-price entry for that ID exists
- **THEN** the registry parses, and the cost estimate prices the judge from the role-price entry

#### Scenario: Unpriced metered role rejected
- **WHEN** the judge or persona names an ID that neither a roster entry nor a role-price entry carries
- **THEN** registry parsing fails and names the role

#### Scenario: Orphaned role price rejected
- **WHEN** a role-price entry names an ID that no role names, or an ID a roster entry also carries
- **THEN** registry parsing fails and names the entry

### Requirement: Cost-gated matrix execution
Before issuing any metered call, a matrix run SHALL print a cost estimate derived from registry pricing and SHALL wait for explicit operator confirmation; an explicit non-interactive flag MAY bypass the prompt. Besides each model under test, the estimate SHALL cover the role models the run will call: the rubric judge on every cell-epoch and the student persona on every dialogue-task cell-epoch, each at a per-cell-epoch token budget taken from the registry. Role model IDs SHALL be resolved exactly as the evaluation resolves them, environment overrides included, so the model that is priced is the model that runs. Every model SHALL be priced through the registry's one price resolution: by its roster entry when the roster carries its ID, and otherwise by its role-price entry. The estimate and the post-run actual spend SHALL use this same resolution. When a role model resolves to an ID that neither a roster entry nor a role-price entry prices, the run SHALL stop before the confirmation prompt, name the unpriced ID, and make no metered call; the non-interactive flag SHALL NOT bypass this stop. After the run it SHALL report actual spend per model and in total, computed from recorded token usage and registry pricing, and persist it alongside the run logs. Uncached input, output, cache reads and cache writes SHALL each be charged at their own registry price. A roster entry or role-price entry MAY carry a cache-write price; one without it SHALL be charged its input price for cache writes. The report and the persisted summary SHALL also carry, per model under test, the cache-hit rate (cache-read tokens divided by all prompt tokens, that is uncached input plus cache writes plus cache reads), the cache-read and cache-write token counts, and the serving providers recorded in the run's logs. The run SHALL warn when the cache-hit rate of an Anthropic-family model under test whose requests are routed for caching falls below 50%, or when any of its recorded calls was served by a provider outside those its routing pins; a call served by any provider in the pin's list SHALL NOT be warned. A log MAY record the serving provider for only some of its calls; a call without one SHALL be counted as unrecorded and SHALL NOT be warned. After the run it SHALL also print each role model's observed token usage per cell-epoch beside the registry budget, and flag any budget that the observation exceeds.

#### Scenario: Estimate shown and declined
- **WHEN** the operator declines the pre-run confirmation
- **THEN** no metered call has been made and the run exits cleanly

#### Scenario: Actual cost reported
- **WHEN** a matrix run completes
- **THEN** per-model and total actual cost are printed and persisted with the run's logs

#### Scenario: Judge override priced
- **WHEN** the operator overrides the judge with a registry model priced above the default judge
- **THEN** the estimate charges every cell-epoch's judge budget at the override's registry pricing, not the default judge's

#### Scenario: Persona priced on dialogue tasks only
- **WHEN** a selection contains one dialogue task and one single-turn task
- **THEN** the persona budget is added to the dialogue task's cell-epochs and to no others

#### Scenario: Unpriced role model stops the run
- **WHEN** a role model resolves to an ID that has no registry pricing, with or without the non-interactive flag
- **THEN** the run exits non-zero before the confirmation prompt, names the unpriced ID, and has made no metered call

#### Scenario: Held judge priced from its role-price entry
- **WHEN** no roster entry carries the judge's ID, a role-price entry does, and no override is set
- **THEN** the estimate charges the judge budget at the role-price entry's pricing, the run reaches the confirmation prompt without an unpriced-role stop, and the actual spend prices the judge's usage, cache writes included, from the same entry

#### Scenario: Cache writes priced
- **WHEN** a run's recorded usage includes cache-write tokens
- **THEN** the actual cost charges them at the model's cache-write price, or at its input price where its roster entry or role-price entry carries none

#### Scenario: Cache telemetry persisted
- **WHEN** a matrix run that included an Anthropic-family model under test completes
- **THEN** the printed report and the persisted summary carry that model's cache-hit rate, its cache-read and cache-write token counts, and the serving providers recorded for it

#### Scenario: Caching regression warned
- **WHEN** an Anthropic-family model under test, routed for caching, has a cache-hit rate below 50% in a completed run
- **THEN** the run prints a warning naming the model and its measured rate

#### Scenario: Serving outside the pin warned
- **WHEN** a routed Anthropic-family model under test pins an ordered list of providers, and its recorded calls were served by the second provider in that list and by one provider outside it
- **THEN** the run warns about the provider outside the list, naming it, and does not warn about the second provider in the list

### Requirement: Epoch-based support classification
Each scorable model×task cell SHALL run a fixed number of epochs (default three) and classify by pass rate: all passes solid, mixed flaky, none fail. Per model, the verdict SHALL be: supported when all scorable cells are solid; flaky with the affected skills named when any cell is flaky; a warning naming the failing skills when any cell fails. Tasks red-by-design on the metered path (environment-fidelity probes) and network-dependent tasks SHALL be excluded from classification; a task MAY contribute only its rubric score where its structural score is excluded. Heavy dialogue tasks MAY run reduced epochs on frontier-tier models for budget reasons, and the report SHALL disclose reduced-epoch cells.

#### Scenario: Flaky cell names the skill
- **WHEN** a model passes a task in some epochs and fails it in others
- **THEN** the model's verdict is flaky and names that task's skill

#### Scenario: Environment-fidelity probe not scored
- **WHEN** a task known to be red-by-design on the metered path fails for every model
- **THEN** no model's verdict is affected by that task's structural score

### Requirement: Generated model-support report
A report generator SHALL derive, from the newest run logs only, (1) a summary table in the repository README between generated-section markers — one row per registry model with its pinned ID, verdict, warnings, and the run timestamp — and (2) a full model×task grid document with per-cell pass rates and per-model run cost. Regeneration SHALL be idempotent and SHALL replace only the marked README region. Models never exercised in the available logs SHALL appear as untested rather than silently omitted. A registry note SHALL appear in the model's summary-row notes, after any verdict-derived notes, so a model whose measurements were invalidated (for example, a harness incompatibility) is presented as untested with the reason visible rather than as bare untested or as failing.

#### Scenario: README region replaced in place
- **WHEN** the report generator runs twice on the same logs
- **THEN** the README outside the markers is byte-identical and the marked region is identical between runs

#### Scenario: Untested model visible
- **WHEN** a registry model has no cells in the available logs
- **THEN** the summary row shows it as untested instead of dropping it

#### Scenario: Registry note rendered
- **WHEN** a registry model carries a note and no measured cells
- **THEN** its summary row reads untested and its notes carry the registry note verbatim

#### Scenario: Note appended after verdict notes
- **WHEN** a registry model carries a note and its logs also produce verdict-derived notes
- **THEN** the row's notes carry the verdict-derived notes first and the registry note after them

### Requirement: Matrix logic covered without model calls
Registry parsing, classification banding, verdict derivation, cost estimation arithmetic, and README marker splicing SHALL be pure functions covered by L0 tests that invoke no model.

#### Scenario: Classification tested offline
- **WHEN** the L0 suite runs

### Requirement: Isolated measurement environment
A routing run SHALL execute against an isolated host configuration containing only the skills under measurement — no operator-specific skills, hooks, plugins, or agents — so that results reproduce on any machine and describe a user's install rather than the developer's. A run that cannot establish that isolation SHALL fail with a message naming what is missing, and SHALL NOT fall back to the ambient configuration.

An isolated configuration — the routing rig's, or the dev runner's in isolated mode — SHALL authenticate in one of two ways. If a long-lived token is in the environment, the configuration SHALL hold no credentials of its own. Otherwise it SHALL hold a link to the operator's stored login, never a copy.

While such a link exists, a login refresh the host performs inside the isolated configuration SHALL reach the stored login. The host refreshes by replacing the link with a file of its own. When the replacement expires later than the stored login, the harness SHALL write it to the stored location with owner-only permissions, within a second of the replacement, and SHALL check once more when the run ends. Credentials that do not expire later SHALL never be written. Credential values SHALL NOT be printed, logged, or kept anywhere other than the stored location and the isolated configuration.

The host serializes refreshes only within one configuration directory. A run that starts while the stored login has expired, or is about to, SHALL therefore first hold an exclusive refresh claim beside the stored login. A run that finds the claim held SHALL wait a bounded time for the refreshed login, then proceed with it. If the wait ends without one, the run SHALL refuse with a message naming the cause. A claim left behind by a run that ended without releasing it SHALL stop blocking after a bounded age.

A login the host rejects only once a case is running cannot be detected before the run starts. A routing case that the host ends for that reason SHALL produce no routing verdict, and its recorded error SHALL carry the host's reason and the re-login instruction the dev runner gives for the same failure.

#### Scenario: Ambient configuration excluded
- **WHEN** the operator's own configuration defines additional skills or session hooks
- **THEN** the routing run is unaffected by them

#### Scenario: Isolation cannot be established
- **WHEN** the isolated configuration cannot authenticate or cannot be created
- **THEN** the run exits with a diagnostic and produces no routing verdicts

#### Scenario: Login rejected during a case
- **WHEN** the host ends a routing case with an error result saying it failed to authenticate
- **THEN** the case produces no routing verdict, and its error carries the host's reason and tells the operator to run `claude` and enter `/login`

#### Scenario: Refresh inside an isolated run reaches the stored login
- **WHEN** the host replaces the linked credentials with a login that expires later than the stored one
- **THEN** the stored login holds the refreshed credentials with owner-only permissions, and the isolated configuration links to it again

#### Scenario: Older credentials never written back
- **WHEN** the host's replacement expires no later than the stored login
- **THEN** the stored login is left unchanged

#### Scenario: Concurrent runs with an expired login
- **WHEN** two isolated runs start while the stored login has expired
- **THEN** only one holds the refresh claim, and the other waits until the refreshed login is written back and starts with it

#### Scenario: Refresh never arrives
- **WHEN** a run waits on a held claim and the bounded wait ends with the stored login still expired
- **THEN** the run refuses with a diagnostic naming the held refresh, and the ambient configuration is not used

#### Scenario: Abandoned claim
- **WHEN** a claim is older than its bounded age
- **THEN** the next run that needs a refresh takes the claim over

#### Scenario: Long-lived token in the environment
- **WHEN** the environment carries a long-lived host token
- **THEN** the isolated configuration holds no credentials, and the stored login is neither linked nor written

### Requirement: Route determined by the first skill invocation
A case's route SHALL be the first invocation of a `proposal-*` skill observed in the run, and the run SHALL be terminated as soon as that route is recorded. Preparatory non-skill tool calls SHALL be tolerated up to a bounded number, and a case that exceeds that bound or its time limit SHALL be recorded as unrouted rather than retried. Skill invocations after the first SHALL NOT change the recorded route.

A case the host ends with an error result before any `proposal-*` invocation SHALL be recorded as an error carrying the host's reason — its subtype, its errors or result text, and the cost and turns so far — and SHALL NOT be recorded as unrouted. Unrouted is a finding about the descriptions; a host failure says nothing about them, and a negative case would pass on it.

### Requirement: Routing reported as a confusion matrix

### Requirement: Dev-runner cost and helper-agent telemetry

The dev runner SHALL read the host's event stream rather than its plain text output, and SHALL save that stream into the run's workspace so a kept workspace carries the run's tool calls and narration for later reading. Beside each run's L1 verdict it SHALL report:

- the model the host served, by the full ID the host reports, beside the name the run requested, and the host CLI version;
- the run's cost, number of turns and duration;
- the input and output token counts, with the cache read and cache write counts;
- the helper-agent tool calls observed (`Agent`, `Task`, `Workflow`);
- for scenarios that produce a supervise feedback, the feedback body's word count, excluding URLs and the closing note;
- for a run graded by the subscription judge, each rubric criterion's grade, the judge's served model ID, its effort and CLI version, its thinking tokens, and the cumulative notional cost of the judge calls, all under a label saying the grades are dev-runner L2 and not comparable to the matrix.

A dedicated verdict function SHALL pass when a run spawned no more helper agents than its scenario allows — none unless the scenario declares an allowance, which a supervise scenario does for its single verifier — and SHALL name the spawning calls when it exceeds the allowance. The runner SHALL report it as a separately labelled advisory verdict that does not change the scenario's exit status.

For the supervise scenarios the verifier is part of the scored L1 verdict, not only of the advisory probe: a run SHALL fail when it spawned no helper whose task carries the skill's verifier brief, and when its review's verification section does not state who verified. The headless host offers a subagent tool, so a run that checks inline has skipped the verifier rather than fallen back.

Because the runner starts the host without permission prompts, it SHALL deny the host's outward-facing tools on every run — publishing artifacts and their comments or data, messaging other sessions, push notifications, remote triggers, scheduling, and design sync — so that no test run can publish, send or schedule anything, whatever the model decides. The routing rig SHALL deny the same tools, from the same list.

The runner SHALL accept a hard budget cap passed through to the host, and SHALL label each run as measuring the ambient host configuration or an isolated one prepared for the run, naming the isolated directory.

The runner SHALL remove from the model-under-test child's environment every variable that can route the host's billing away from the subscription login, in ambient and isolated mode alike: every `ANTHROPIC_`-prefixed variable, which covers the API key, the gateway base URL and its auth token, and every `CLAUDE_CODE_USE_` cloud-provider switch. In ambient mode it SHALL leave every other inherited variable in place, so that the operator's effort and session settings remain part of what an ambient run measures. In isolated mode the child SHALL receive the isolated child environment instead (requirement: Isolated child environment), whose allowlist admits none of those billing variables and no effort or session setting of the launching process, so that an isolated run measures the default host.

Failures SHALL be reported as follows:

- a host result event marked as an error — a budget overrun among them — SHALL end the run as a runner failure whose message carries the host's subtype, its errors, and the cost and turns so far;
- when that error is a failure to authenticate, the message SHALL also tell the operator that the stored login is no longer valid and must be renewed by running `claude` and entering `/login`;
- a non-zero host exit without such an event SHALL report the host's stderr;
- a stream with no result event SHALL be a runner failure, never a silent success with empty telemetry.

The runner's exit status SHALL distinguish four outcomes, so that only a failed verdict reads as a failure of the skill:

- every verdict the run computed passed;
- a verdict failed — L1, or a graded L2 criterion;
- the run is untested because the subscription could not serve it. That covers a login the host rejected; a stream reporting overage use, a refused or unknown rate-limit status, or an API-key source; a stream that reports no rate-limit status at all, so overage cannot be ruled out; and a judge call that produced no grade;
- any other runner failure.

The chat the verdicts read SHALL be the result event's final text and nothing else. All of this logic SHALL be covered by L0 tests against recorded and synthetic event streams:

- the verdicts;
- the event parsing and the telemetry;
- the command the runner builds and the judge command;
- the judge's child environment and the model-under-test child's environment;
- the stream checks that mark a call unavailable;
- the exit-status mapping;
- the summary it prints.

The telemetry and final-text readers SHALL be pinned against a recorded result event of the host, so a host field rename fails a test rather than blanking the line.

#### Scenario: Ambient run keeps the operator's settings

### Requirement: Scoping-vocabulary containment measured against a non-aligned idea
The harness SHALL exercise research-group scoping with at least one scenario whose student idea is plausible for the stated program and touches none of the scoping fixture's research areas, and at least one whose idea overlaps exactly one area of a multi-area fixture. A scenario whose student idea restates one of the fixture's research areas SHALL NOT be the only coverage of the scoping fetch: vocabulary bleed and legitimate adoption are indistinguishable in such a run, so it measures the fetch but not the containment.

The scoping fixture's vocabulary SHALL be carried in two distinct sets, because one term cannot serve both roles: a chat-visibility set whose appearance in the transcript proves the fetch happened, and a containment set whose appearance in any produced file or issued literature query fails the run. Group, university, and program names remain leaks wherever the existing scoping requirements already place them.

Containment SHALL be decided by a pure function in the shared verdict module that takes the dialogue transcript, the produced workspace files, and the queries the run issued, and fails a run for any containment term absent from every student turn but present in a produced file or a query. It SHALL be exercisable by L0 tests without a model call.

#### Scenario: Adjacent idea keeps the profile out
- **WHEN** the scoping scenario's student idea touches none of the fixture's research areas and the run seeds a proposal
- **THEN** the run passes only if no containment term appears in the seed file, the notes file, or any literature query the session issued

#### Scenario: Partial overlap contains the rest
- **WHEN** the student's idea overlaps one research area of the multi-area fixture
- **THEN** the vocabulary of the non-overlapping areas fails the run if it reaches a produced file, while the overlapping area's terms are judged by whether a student turn voiced them

#### Scenario: Student-voiced term is not a leak
- **WHEN** a containment term occurs in a student turn before it appears in a produced file
- **THEN** the containment function does not count it against the run

#### Scenario: Fetch still proven visible
- **WHEN** a scoping scenario completes
- **THEN** the chat-visibility set is still required in the transcript, so a run that made no outbound request fails rather than passing vacuously

### Requirement: Off-topic-reference resolution covered
The fixture corpus SHALL carry a proposal whose `references:` block holds two uncited entries that are each well-formed and academically legitimate, and whose correct resolutions are opposite: one that a claim already in the proposal needs, and one that is topically adjacent but which no research question, delta statement, or method step needs. The mechanical finding SHALL be identical for both, so that only reading the proposal distinguishes them — a fixture carrying just the second would be passed by a run that removes every uncited entry on sight, which is the same failure to judge in the other direction. Its `expected.json` oracle SHALL record that the check reports both entries as uncited and reports nothing about the relevance of either, pinning the formalization boundary: relevance stays agent judgment.

The harness SHALL exercise a writing pass over that fixture and SHALL fail the run when the pass resolves an uncited-reference finding by adding a sentence that cites the entry without a research question, delta statement, or method step depending on it. Citing the needed entry at the claim that needs it SHALL pass; removing the unneeded entry with a recorded reason, and leaving it uncited with a stated reason, SHALL both pass.

#### Scenario: Carrier sentence fails the run
- **WHEN** a writing pass over the fixture produces a new sentence whose only function is to cite the otherwise-uncited entry
- **THEN** the run fails, naming the sentence

#### Scenario: Removal with a reason passes
- **WHEN** a writing pass removes the unneeded entry from `references:` and records it in Excluded Literature with a one-line reason
- **THEN** the run passes

#### Scenario: The needed entry is cited, not removed
- **WHEN** the fixture's other uncited entry supports a claim the proposal already makes
- **THEN** a pass that removes it fails the run, and a pass that cites it at that claim passes

#### Scenario: Check stays silent on relevance
- **WHEN** the mechanical check runs over the fixture
- **THEN** it reports the entry as uncited and reports no finding about whether the entry is relevant, as the oracle records

### Requirement: Substance-test names consistent across guidance, skills, specs and pins
An offline test SHALL assert that the substance tests named in the prose guidance are exactly the set cited wherever the guidance's tests are referred to by name or by count — the skill bodies that judge substance, the verbatim pins that quote a phrase naming them, and the specifications that enumerate them. A site that names a test the guidance does not, omits one the guidance names, or states a count that disagrees with it SHALL fail the offline suite.

Specifications SHALL be checked only while no change is in flight: a specification is rewritten from a change's delta when that change is archived, so between implementation and archive it describes the previous set by design, and failing the suite for that window would make the gate something to route around.

Two constructs SHALL NOT be reported as drift, because neither is a claim about the set: an enumeration explicitly marked as partial, such as a verdict citing only the tests that actually failed; and a number that states an evidence bar — how many tests must fail — rather than how many exist.

This test is a prerequisite for changing the set: it SHALL be in place before a test is added to or removed from the guidance, so that every dependent site fails loudly in the same change rather than drifting silently.

#### Scenario: Test added to the guidance alone
- **WHEN** a substance test is added to the prose guidance and a dependent skill body still enumerates the previous set
- **THEN** the offline suite fails and names the file that disagrees

#### Scenario: Count drifts in a pinned sentence
- **WHEN** a pinned sentence states a number of substance tests that no longer matches the guidance
- **THEN** the offline suite fails

#### Scenario: Evidence bar is not a set size
- **WHEN** a specification states that at least three substance tests must fail decisively
- **THEN** the offline suite does not read that number as a claim about how many tests exist

#### Scenario: Specification stale while its change is in flight
- **WHEN** the guidance names a new set and the change carrying that delta has not been archived
- **THEN** the offline suite skips the specifications and still checks the guidance, the skill bodies, and the pins

#### Scenario: All sites agree
- **WHEN** guidance, skill bodies, specifications, and pins name the same set
- **THEN** the offline suite passes without a model call

### Requirement: Citation-practice coverage
The fixture corpus SHALL carry two synthetic fixtures for citation practice, each with an `expected.json` oracle calibrated against the mechanical check:
- an idea seed whose references block holds at least ten entries, one of them central enough to a theme that a draft could lean on it for several sentences;
- a proposal draft that already carries the overcitation pattern: the same key on at least three consecutive sentences of one paragraph, an identical multi-key group repeated on adjacent sentences, and a contribution paragraph that summarises one source sentence by sentence.

Neither fixture SHALL contain content from a real proposal. The over-citing draft's oracle SHALL record the repeated-citation warning, and every other proposal fixture's oracle SHALL record its absence. This makes the draft the trip case and the rest of the corpus the pass case for that rule.

The harness SHALL exercise a writing pass that drafts from the seed and a writing pass over the draft, both as dev-runner scenarios and as Inspect tasks. Each run SHALL be judged by an L1 verdict that is a pure function in the shared verdict module, testable without a model call. The verdict SHALL fail when two adjacent sentences carry the same non-empty set of citation keys, comparing within a paragraph and across consecutive items of one list. Sentences whose key sets differ pass. A paragraph break, a heading or a table row resets the comparison. The verdict's sentence and block boundaries SHALL be those of the check's repeated-citation rule, pinned to it by L0 tests. For the pass over the draft, the verdict SHALL additionally fail when a reference the input cites is cited nowhere in the output, so that deleting citations is never a way to pass.

Each Inspect task SHALL carry two model-graded scorers following the rubric-template contract and the `*_l2*` naming the support classifier reads:
- citation scope: every sentence's source is recognisable, no publication is repeated on consecutive sentences while source and topic are unchanged, and no sentence continues a source without a citation or a back-reference cue;
- synthesis: prior work is grouped and compared by theme rather than summarised one source after another.

#### Scenario: Repeated key fails the run
- **WHEN** a produced draft cites the same key on two adjacent sentences of one paragraph
- **THEN** the L1 verdict fails the run, naming the line

#### Scenario: Source switch passes
- **WHEN** adjacent sentences carry different key sets, such as one key and then that key with a second
- **THEN** the L1 verdict does not fail on them

#### Scenario: Deletion is not a repair
- **WHEN** a writing pass over the repetitive draft removes every citation of a reference the input cited
- **THEN** the L1 verdict fails the run, naming the reference

#### Scenario: Verdict logic covered without a model
- **WHEN** the verdict's failure modes are tested
- **THEN** L0 tests call it directly on crafted proposal texts and no model is invoked

#### Scenario: Over-citing draft trips the warning
- **WHEN** the mechanical check runs over the over-citing draft
- **THEN** it reports the repeated-citation warning, as the draft's oracle records, and reports no error

#### Scenario: Uncued deletion fails the scope grade
- **WHEN** a draft keeps one citation per paragraph but leaves the following sentences without a back-reference to the source
- **THEN** the citation-scope scorer grades the sample incorrect

### Requirement: Model identifiers live only in the registry
An L0 test SHALL scan the tracked tree for model identifiers. It SHALL recognize the identifier shapes of the vendor families the harness has used, and the version line of every registry entry.

- **Code and configuration:** the harness and repository scripts, the project configuration, and the CI workflows SHALL carry no model identifier.
- **Any other tracked file:** it MAY name a model only by an identifier that resolves to a current roster entry or role. A resolving identifier is in one of these spellings:
  - provider-qualified;
  - without the provider prefix;
  - the subscription CLI's form, which has dashes between version digits and an optional trailing date.

An explicit allowlist SHALL exempt these, each entry with its reason:

- the registry itself;
- change records under the OpenSpec changes directory;
- the main specifications, whose scenarios carry illustrative identifiers, receive them when a change is archived, and change only through a change record;
- generated report outputs, including the generated region of the README;
- generated eval projections;
- model-identifier normalization test data, including an eval scenario whose subject is the model identifier a user reports.

An allowlist entry MAY cover a category of files, a whole file, or a single identifier within one file. An entry that tolerates a violation another change will remove SHALL name that change. Such a parked entry SHALL fail the test once it exempts nothing, and so SHALL an entry for a single identifier, so that a resolved exemption cannot linger. Category entries such as generated outputs and the main specifications stay in place even when their files currently name only current models.

#### Scenario: Hardcoded default rejected
- **WHEN** a harness module introduces a provider-qualified model ID as a default value
- **THEN** the L0 suite fails, naming the file, the line and the identifier

#### Scenario: Stale example rejected
- **WHEN** a documentation file names a model whose version line the registry pins at a different version
- **THEN** the L0 suite fails, naming the identifier and the current pin of that line

#### Scenario: Unregistered model rejected
- **WHEN** a documentation file names a model that no roster entry or role tracks
- **THEN** the L0 suite fails, naming the identifier

#### Scenario: Subscription spelling accepted
- **WHEN** a tracked issue template names `claude-sonnet-5-5` and the registry pins `anthropic/claude-sonnet-5.5`
- **THEN** the guard accepts the identifier

#### Scenario: Exhausted parked entry
- **WHEN** a parked allowlist entry, or an entry for a single identifier, no longer exempts any violation
- **THEN** the L0 suite fails, naming the entry so it can be removed

#### Scenario: Archived scenario names an outgoing model
- **WHEN** an archived change has synced a scenario naming a model into a main specification, and a later bump re-pins that model's line
- **THEN** the guard does not flag the specification

### Requirement: Shipped verdicts list exactly the registry roster
An L0 test SHALL fail when the generated verdict data or the README model-support summary lists a model set different from the registry roster. Outgoing IDs SHALL count as extra and incoming IDs as missing. A roster edit therefore cannot reach the default branch until the report has been regenerated from the run logs.

#### Scenario: Roster bumped without regeneration
- **WHEN** a registry entry's ID is replaced and the report has not been regenerated
- **THEN** the L0 suite fails, naming the outgoing ID as extra and the incoming ID as missing

### Requirement: Model currency check
A checker SHALL compare every roster pin and every role against the provider's public model catalog. It SHALL use no credentials and only the standard library. For each pin it SHALL derive a version line: the identifier with its version number wildcarded and any trailing snapshot-date token ignored. Variants carrying a `:` suffix SHALL be excluded.

An entry MAY override its line with an explicit pattern, or opt out of tracking. An opted-out entry SHALL be reported as untracked, never silently omitted. Subscription-form role IDs SHALL be mapped to catalog IDs: dashes between version digits become dots, a trailing date is dropped, and the vendor namespace is added.

The checker SHALL report each of the following as a structured finding:

- a newer model in the line, newer meaning a higher version, or the same version created later;
- a pin missing from the catalog;
- a non-empty expiration date;
- price drift beyond a fixed relative tolerance against the vendor's own endpoint, for roster entries and role-price entries alike.

It SHALL also report, as informational findings that are never written, the version lines in any vendor namespace the registry uses that no registry entry or role derives and that have a member created after the registry's line-review date. The registry SHALL record that date, and only a maintainer's edit SHALL move it.

Its output SHALL be human-readable by default and JSON on request.

A write mode SHALL apply newer-in-line bumps and refreshed prices to the registry, and update the price date. It SHALL edit lines so that comments and notes are preserved, and running it a second time SHALL change nothing. It SHALL NOT rewrite the matrix judge or the persona role. It SHALL report them as held, because changing either invalidates every rubric-counted cell until a full re-baseline. When it re-pins a roster entry whose outgoing ID a held role still names, it SHALL add a role-price entry for that ID in the same edit, so the held role stays priced. It SHALL NOT change the line-review date. Its logic SHALL be covered by L0 tests over a recorded catalog snapshot, without network access.

#### Scenario: Newer model in the line
- **WHEN** the roster pins `openai/gpt-5.6-sol` and the catalog lists `openai/gpt-6-sol` and `openai/gpt-6.1-sol`
- **THEN** the checker reports `openai/gpt-6.1-sol` as the newest model in the line

#### Scenario: Variants and siblings are not successors
- **WHEN** the catalog lists `:batch` variants, `-pro` or `-prime` siblings, and `~`-prefixed floating aliases next to a pinned model
- **THEN** none of them is reported as a newer model

#### Scenario: Dated snapshot of the same version
- **WHEN** the catalog lists a dated snapshot of the pinned version that was created after the pinned entry
- **THEN** the checker reports the dated snapshot as newer

#### Scenario: Floating pin detected
- **WHEN** a pinned ID is absent from the catalog while a dated sibling of the same version is listed
- **THEN** the checker reports the pin as missing and proposes the dated sibling

#### Scenario: Subscription role mapped
- **WHEN** the dev-runner judge role is `claude-sonnet-5-5` and the catalog lists a newer Sonnet
- **THEN** the checker reports the newer model and proposes its subscription-form ID for review

#### Scenario: Judge held
- **WHEN** a newer model exists in the matrix judge's line
- **THEN** the checker reports it as held and the write mode leaves the judge and persona roles unchanged

#### Scenario: Held judge's roster entry re-pinned
- **WHEN** the write mode re-pins the roster entry that carries the judge's ID
- **THEN** the judge role keeps its ID, a role-price entry for that ID is added in the same edit, and the edited registry parses

#### Scenario: New line in a roster vendor namespace
- **WHEN** the catalog lists `anthropic/claude-fable-5.1`, created after the line-review date, and no registry entry or role tracks the Fable line
- **THEN** the checker reports the Fable line as an informational finding naming `anthropic/claude-fable-5.1`, exits as it would without it, and the write mode adds no roster entry

#### Scenario: Reviewed new line
- **WHEN** the maintainer moves the line-review date past the newest member of a reported line
- **THEN** the checker no longer reports that line

#### Scenario: Write is idempotent
- **WHEN** the write mode runs twice against the same catalog snapshot
- **THEN** the second run changes no byte of the registry

#### Scenario: Catalog unreachable
- **WHEN** the catalog request fails
- **THEN** the checker exits with a distinct "currency unknown" status and writes nothing

### Requirement: Weekly model-bump pull request
A CI workflow SHALL run the currency check in write mode weekly and on manual dispatch. When the registry changes, it SHALL keep exactly one open pull request from a fixed branch, creating it or updating it. It SHALL use only the repository's built-in token, with the least permissions this needs.

Pull requests opened with that token trigger no pull-request workflows. The workflow SHALL therefore start the regular CI workflow on the bump branch itself.

It SHALL NOT overwrite the bump branch once the branch carries a commit from anyone else; it SHALL comment on the pull request instead. When main already satisfies every finding, it SHALL close a pull request that is no longer needed.

The pull request description SHALL:

- list every finding, including any role-price entry added for a held role;
- list the new lines in the registry's vendor namespaces as a roster decision for the maintainer;
- instruct the maintainer to regenerate the model-support report locally from the run logs and to re-run the shared-copy sync before merging;
- state that new IDs render as untested until a cost-gated matrix run;
- flag a bump of a subscription role for a check that the CLI resolves the new ID to itself.

Report-only findings, new lines included, SHALL appear in the run summary. A new line alone SHALL NOT open a pull request or fail the run. A pin that is missing or expiring without a writable successor SHALL fail the scheduled run.

The workflow SHALL NOT call any model, read any secret beyond the built-in token, or merge.

#### Scenario: New model published
- **WHEN** the weekly run finds a newer model in a roster line
- **THEN** a pull request from the fixed branch carries the registry edit and a description with the regeneration instructions, and the regular CI workflow runs on that branch

#### Scenario: Pull request already open
- **WHEN** a bump pull request is open and a later run finds further changes
- **THEN** the same pull request is updated and no second one is opened

#### Scenario: Maintainer has pushed to the bump branch
- **WHEN** the bump branch carries a commit not made by the workflow
- **THEN** the workflow leaves the branch untouched and comments the new findings on the pull request

#### Scenario: Nothing to bump
- **WHEN** the check finds no writable change
- **THEN** no pull request is opened, and an open one that main has made obsolete is closed

#### Scenario: Pin about to disappear
- **WHEN** a pinned model carries an expiration date and no newer model exists in its line
- **THEN** the scheduled run fails and its summary names the pin

### Requirement: Currency warning at the cost gate
Before asking for cost confirmation, a matrix run SHALL print stale-model warnings from the same currency check. The warnings SHALL come from a single unauthenticated catalog request with a short timeout. A failed request SHALL print a "model currency unknown" warning. The warning SHALL NOT block the run, alter the estimate, or change the exit status.

The L0 suite SHALL disable the checker's network access for every test by default, so that no test touches the network, including a test that runs a matrix invocation without mentioning the catalog. Tests that assert warnings SHALL substitute a recorded catalog.

#### Scenario: Stale pin warned before confirmation
- **WHEN** a matrix run selects a model whose line has a newer catalog entry
- **THEN** the warning naming the newer model is printed before the confirmation prompt, and the estimate is unchanged

#### Scenario: Offline gate
- **WHEN** the catalog cannot be reached
- **THEN** a "model currency unknown" warning is printed and the run proceeds to the usual confirmation

#### Scenario: L0 test without a catalog substitute
- **WHEN** an L0 test runs a matrix invocation and substitutes nothing for the catalog request
- **THEN** no network request is made, and the gate prints the "model currency unknown" warning

### Requirement: Subscription text roles (dev runner)

The dev runner's text-only role, its rubric judge, SHALL run through the unmodified official host CLI under the operator's subscription login. The judge SHALL be one single-turn text call per rubric criterion, issued under the following constraints.

**Invocation:**

- The model is named by the full model ID that the registry's roles table assigns to the dev judge, never by an alias. An ID that names a metered provider SHALL be refused before any call.
- The effort is passed explicitly, from the same roles table.
- Host customizations are disabled, no tools are offered, the call is limited to one turn, and no session is persisted.
- The host's minimal mode SHALL NOT be used, because it bypasses the subscription login.
- The prompt is delivered on standard input. The content under grading travels only in the prompt and is never written into a measured workspace.
- The child runs in a fixed working directory outside every measured workspace.

**Environment and login:**

- The child environment SHALL be built from an allowlist. No API key, no gateway or provider-routing variable, no inherited effort setting and no host-session variable reaches the child.
- The one credential that MAY reach the child is the subscription's own long-lived login token, when the operator has exported one. The isolated configuration relies on that token, and it is passed through unread. Apart from that token, the harness SHALL NOT read, copy or forward a credential.
- Before the first call of an invocation, the runner SHALL confirm that the host is logged in with the subscription login: the stored login, or the subscription's long-lived token. Otherwise it SHALL stop with the re-login instruction (`claude`, then `/login`). The remedy for a missing login SHALL never be an API key.
- Judging SHALL require the isolated configuration, inside which the stored login is kept current.
- The first judge call of an invocation runs alone. Later calls run at most four at a time across the process.

**Failing closed.** A judge call SHALL count as unavailable, never as a failing grade, when any of the following holds:

- the host's result is marked as an error;
- the result has no text, zero output tokens or no per-model usage;
- the host reports a rate-limit status other than `allowed` or `allowed_warning`;
- the stream carries no rate-limit report at all, so overage cannot be ruled out;
- overage is in use;
- the session used an API-key source;
- the call was served through a provider other than Anthropic's own API;
- the served model differs from the requested one;
- the call exceeds its time limit, in which case the child process SHALL be killed;
- the response carries no grade line.

An unavailable call SHALL stop further judge calls in the same invocation.

**Bounding and records:**

- The runner SHALL keep a cumulative notional-cost total of the judge calls and SHALL stop issuing calls once an operator-set cap is reached; criteria left ungraded then count as untested.
- Before a batch re-grade fans out, the runner SHALL print a notional estimate projected from the first call's measured cost. It SHALL NOT start the batch when the projection exceeds the cap.
- Each call SHALL record the host CLI version, the effort, the served model, its thinking tokens and its notional cost. A warning-level rate limit SHALL be reported with its window and utilization.

**Rubrics:**

- The dev judge and the matrix judge SHALL read the same rubric templates and criteria. Each rubric template and criterion SHALL be defined once, and the prompts the matrix judge sends SHALL stay byte-identical to the prompts it sent before that sharing existed.
- The dev judge's question SHALL be the visible user request. Where the matrix judge's question is an oracle list rather than the request, both judges SHALL use the same list.
- Kept dev-runner workspaces SHALL be re-gradable without re-running the model under test.

**Smoke:**

- The registered smoke task SHALL run the core scenarios on the dev runner in isolated mode, loading no key file. Its spend SHALL be kept off metered billing in three ways:
  - no billing variable reaches any host process it starts;
  - each scenario's model run carries a hard budget cap;
  - a scenario whose stream shows billing other than through the subscription (an API-key source, overage, or no rate-limit report) is reported untested, never passed.
- The smoke task SHALL continue past a failing scenario and end with a summary naming each scenario's outcome, exiting non-zero unless every scenario passed.
- The former metered smoke SHALL remain available as a separate registered task. It takes its model from the registry's roles table and runs behind the matrix cost gate.

#### Scenario: Judge command pinned
- **WHEN** the judge command is built for the registry's dev-judge ID and effort
- **THEN** it names that full ID, passes that effort, disables host customizations, offers no tools, limits the call to one turn, persists no session, requests the event stream, carries none of the graded content among its arguments, and never carries the minimal-mode flag

#### Scenario: Metered ID refused as dev judge
- **WHEN** the dev-judge role names a provider-qualified metered ID or an alias
- **THEN** the runner refuses before any call and names the role

#### Scenario: Credentials and session settings never forwarded
- **WHEN** the launching environment carries an API key, a gateway base URL with an auth token, a provider-routing switch, an effort setting and host-session variables
- **THEN** none of them is present in the judge child's environment, while the path, home, locale, temporary-directory and configuration-directory variables are, and so is the subscription's long-lived login token when one was exported

#### Scenario: API-key login refused
- **WHEN** the preflight finds the host logged in by any method other than the subscription login
- **THEN** no judge call is made, and the runner stops with the re-login instruction and the untested status

#### Scenario: Expired login during judging
- **WHEN** a judge call's result is marked as an error saying the login expired and could not be refreshed
- **THEN** the criterion is untested, the message carries the host's reason and the re-login instruction, and no further judge call is made

#### Scenario: Overage refuses the grade
- **WHEN** a judge call's stream reports overage in use, even with a grade line in the result
- **THEN** the grade is discarded and the criterion is untested

#### Scenario: Unreported rate limit refuses the grade
- **WHEN** a judge call's stream carries a grade line but no rate-limit report
- **THEN** the grade is discarded, the criterion is untested, and the reason says that overage could not be ruled out

#### Scenario: Warning-level rate limit still grades

#### Scenario: Served model differs

#### Scenario: Concurrency bounded

- **THEN** at most four child processes run at any moment, and the first call of the invocation completed before any other started

#### Scenario: Time limit kills the child

- **THEN** the child process is no longer running, and the criterion is untested

#### Scenario: Notional cap reached

- **THEN** no further judge call is made, and the remaining criteria are reported untested with the cap named

#### Scenario: Batch projection over the cap

#### Scenario: Matrix judge prompt unchanged

#### Scenario: Smoke continues past a failure

#### Scenario: Smoke cannot bill silently
- **WHEN** the smoke task is started from an environment that exports an API key
- **THEN** no host process it starts receives the key, every scenario's model run carries a budget cap, and a scenario whose stream nevertheless reports an API-key source is listed as untested in the closing summary

#### Scenario: Metered smoke behind the gate

### Requirement: Prompt caching on Anthropic matrix rows
Matrix requests for an Anthropic-family model under test SHALL be issued so that prompt caching covers the growing conversation, not only the static system and tool prefix. They SHALL be served by a fixed, ordered list of pinned upstream providers with fallbacks beyond that list disabled, the first listed provider serving whenever it is available, so that successive turns reach the cache they wrote. The pinned providers SHALL be ones the operator account's routing guardrails, such as zero data retention, admit; the harness SHALL NOT require relaxing those guardrails. These routing and caching settings SHALL apply to Anthropic rows only, and requests for every other family SHALL be unchanged. The model ID recorded in a run's log SHALL equal the registry ID, so the logs of a cached run count toward the generated report exactly as before. The rubric judge and the student persona SHALL keep their serving configuration: this requirement neither moves nor re-routes them. No one-shot request, that is a rubric-judge or student-persona prompt that no later call extends, SHALL be given a conversation cache breakpoint, because it would pay the cache-write premium without ever reading the cache back; a request of the model under test heads a conversation whose later turns read it back, even when it consists of a single message. The caching mechanism in use SHALL be one that the cache reuse probe has passed on the Anthropic rows it covers. Until a mechanism has passed, Anthropic-family requests SHALL be issued without the provider pin and the caching settings, exactly as for every other family.

#### Scenario: Other families unchanged
- **WHEN** a matrix run includes an OpenAI-family model and an Anthropic-family model
- **THEN** only the Anthropic model's requests carry the provider pin and the caching settings, and the OpenAI model's requests are built exactly as before

#### Scenario: Logged model ID equals registry ID
- **WHEN** an Anthropic row runs with its routing and caching settings
- **THEN** the run's log records the registry ID as its model, and the report generator counts that log for the row

#### Scenario: One-shot prompt gets no breakpoint
- **WHEN** a judge request consists of a single user message
- **THEN** no conversation cache breakpoint is added to it

#### Scenario: No mechanism passed yet
- **WHEN** a matrix run includes an Anthropic-family model and no caching mechanism has passed the cache reuse probe
- **THEN** that model's requests carry neither the provider pin nor the caching settings

### Requirement: Cache reuse probe
The harness SHALL provide a metered probe that replays a fixed, synthetic multi-turn tool conversation for each selected Anthropic registry model and caching mechanism. The conversation's content SHALL be independent of the model's replies, the probe SHALL build the model the same way the matrix does, and it SHALL record the cache usage of every call. Before its first metered call the probe SHALL print a worst-case cost estimate derived from registry pricing, with every prompt token charged at the cache-write price, and SHALL wait for explicit operator confirmation, as a matrix run does. A mechanism SHALL pass on a model only when cache-read tokens make up at least 80% of all prompt tokens, summed over the calls after the first call that writes the cache. The result SHALL state the measured share, the serving providers recorded, and the actual cost. The pass/fail decision and the worst-case estimate SHALL be pure functions covered by L0 tests that invoke no model.

#### Scenario: Probe declined
- **WHEN** the operator declines the probe's confirmation
- **THEN** no metered call has been made and the probe exits cleanly

#### Scenario: Below threshold fails
- **WHEN** cache reads make up 60% of the prompt tokens on the calls after the first cache write
- **THEN** the mechanism fails on that model and the explanation names the measured 60% and the 80% threshold

#### Scenario: No cache write fails
- **WHEN** no call of the replay writes the cache
- **THEN** the mechanism fails and the explanation says that no call wrote the cache

#### Scenario: Reuse at threshold passes
- **WHEN** cache reads make up at least 80% of the prompt tokens on the calls after the first cache write
- **THEN** the mechanism passes on that model

### Requirement: Isolated child environment
An isolated host child SHALL receive an environment built from an allowlist. This covers every routing-rig run and the model-under-test child of every dev-runner run in isolated mode. It SHALL NOT receive the launching process's environment with only the configuration directory overridden. One function, shared by both runners, SHALL build that environment. The dev judge's child also runs in an isolated configuration, but its environment is governed by the requirement "Subscription text roles (dev runner)", not by this one.

The allowlist SHALL admit only:
- `PATH` and `HOME`;
- `CLAUDE_CODE_OAUTH_TOKEN`, the long-lived OAuth token variable;
- variables that describe the machine rather than configure the host: user identity and login shell, locale, temporary directories, XDG base directories, proxy and certificate-trust settings, and the process basics Windows requires.

The configuration-directory variable SHALL be set to the isolated directory, replacing any inherited value.

Every other variable SHALL be dropped. That includes:
- the variables a launching desktop-app or SDK session sets to bind a child to itself: entrypoint, session identifiers, messaging socket and token, host auth refresh, and OAuth scopes;
- the variables that tune the host: effort, tool enablement, compaction, timeouts, API endpoint, and MCP connection settings;
- variables that no list names yet. A host that adds one would otherwise leak it into measurement without any sign.

A runner in ambient mode SHALL keep passing the operator's environment to the child, less only the billing variables the dev runner removes from every model-under-test run (requirement: Dev-runner cost and helper-agent telemetry).

Building the isolated environment SHALL print nothing, and no runner output SHALL carry the value of any variable, admitted or dropped. L0 tests with synthetic values SHALL cover how the environment is built and both places that use it.

#### Scenario: Desktop session variables dropped
- **WHEN** a runner is launched from a desktop-app session that exports its entrypoint, session identifiers, messaging socket and token, auth-refresh flag, and OAuth scopes
- **THEN** the isolated child's environment carries none of them, and its configuration directory is the isolated one

#### Scenario: Host tuning outside the host's own prefix dropped
- **WHEN** the launching environment sets the API base URL, an API timeout, a compaction or auto-updater switch, or MCP connection settings
- **THEN** the isolated child receives none of them

#### Scenario: Unknown variable dropped
- **WHEN** the launching environment holds a variable that no list names
- **THEN** the isolated child does not receive it

#### Scenario: Long-lived token kept
- **WHEN** `CLAUDE_CODE_OAUTH_TOKEN` is set in the launching environment
- **THEN** the isolated child receives it unchanged, together with `PATH` and `HOME`

#### Scenario: Machine plumbing kept
- **WHEN** the launching environment sets locale, temporary-directory, proxy, or certificate-trust variables
- **THEN** the isolated child receives them unchanged

#### Scenario: Ambient run keeps the operator's environment
- **WHEN** the dev runner runs without isolated mode
- **THEN** the child inherits the operator's environment, its effort and session variables included, except the billing variables

#### Scenario: Judge child outside this requirement
- **WHEN** an isolated dev run is graded by the dev judge
- **THEN** the judge's child gets the environment that "Subscription text roles (dev runner)" prescribes, and only the model-under-test child is held to this allowlist

#### Scenario: No values printed
- **WHEN** the isolated environment is built from an environment holding a messaging token
- **THEN** nothing is printed, and the token's value appears in no output
