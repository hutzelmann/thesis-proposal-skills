# testing-harness Specification

## Purpose
Automated verification that all skills work as specified across models: a three-layer test pyramid with deterministic fixtures and model-graded rubrics.

## Requirements

### Requirement: Three-layer pyramid
Testing SHALL provide: L0 unit tests for all shipped scripts (no model calls, CI-safe); L1 structural tests running each skill against fixture workspaces per model with deterministic artifact assertions; L2 rubric tests grading semantic quality via model judges (analytical RQ phrasing, Socratic compliance, review actionability, German quality).

#### Scenario: Script regression
- **WHEN** a check-script rule breaks
- **THEN** an L0 test fails without any model involvement

#### Scenario: Semantic regression
- **WHEN** a model under test produces implementation-goal research questions
- **THEN** the L2 rubric scores it below threshold and the run fails

### Requirement: Multi-turn ideation testing
Ideate SHALL be tested in multi-turn dialogues against student personas on the metered path. The dialogue suite SHALL comprise one long composite run and several short adversarial probes, replacing cooperative-only coverage:

- **Long composite run**: a scripted persona drives roughly eighteen rounds through distinct phases — administrative preamble, hesitant idea development, an extraction probe (a direct request for finished research questions), a topic pivot, convergence, and seeding. Phase boundaries are scripted so graders can attribute failures. Between rounds the harness SHALL assert workspace state mechanically: the notes file appears once a topic exists and grows across the dialogue, and no proposal file exists before convergence.
- **Short probes**: a stonewalling persona whose non-contributions must trigger the early stop (state saved to notes, no proposal file); a no-idea persona for whom floated hints must name their source and never form a topic menu; an out-of-scope persona whose insistence must yield exactly one chat-only warning and a clean seed; and a probing persona — agreeable, vague, extraction-minded, offering only generalities while pushing for a finished proposal — whose run must end without a seeded proposal: the swap test voiced, the impasse named after persistent genericity, state saved to notes, and no specifics generated by the assistant.

Two instruments SHALL grade student-originated content and tutoring quality:

- **Provenance check**: a pure function in the shared verdict module that takes the transcript and the seeded file and verifies the substantive content terms of the working title and candidate research-question directions occur in student turns — a term the student never voiced in any turn counts against the run. First utterance is deliberately not the criterion: good tutoring crispens the student's phrasing, so the assistant may voice the sharp term first and the student adopts it. It SHALL be exercisable by L0 tests without a model call.
- **Uptake rubric**: the L2 Socratic rubric SHALL judge, per phase, that assistant turns build on the student's preceding turn, ask at most one question, contain no praise padding, tell only conventions (never idea content), and confine direct administrative questions to the two bookends — the preamble block and the closing seeding step, which the rubric SHALL recognize as sanctioned direct questions.

#### Scenario: Long run graded per phase
- **WHEN** the long composite dialogue completes
- **THEN** the transcript is judged phase by phase, and a collapse at the extraction probe (assistant supplies finished research questions) fails that phase

#### Scenario: Notes growth asserted mechanically
- **WHEN** the long run passes its topic-establishing phase
- **THEN** the harness finds a notes file in the workspace and its size or content grows by the pivot phase, without any model judging this

#### Scenario: Stonewaller triggers early stop
- **WHEN** the stonewalling persona deflects three consecutive exchanges
- **THEN** the run passes only if the assistant named the impasse, the notes file records the state, and no proposal file was created

#### Scenario: Prober never receives a generic proposal
- **WHEN** the probing persona agrees with everything, contributes only generalities, and repeatedly asks the assistant to just write it down
- **THEN** the run passes only if no proposal file was seeded, the notes file records the state, and the transcript shows the swap test voiced before the impasse

#### Scenario: Generic content fails provenance
- **WHEN** a seeded file's research-question directions use substantive terms that never occurred in any student turn
- **THEN** the provenance check fails the run without model involvement

#### Scenario: Bookend questions pass the rubric
- **WHEN** the assistant opens with the administrative block and closes confirming dates
- **THEN** the Socratic rubric does not count these as violations

### Requirement: Inverted-hybrid runners
Authoritative runs SHALL execute over metered API providers, with native multi-model comparison and spend caps. Authoritative runs are the model matrix, the release gates, and the judge and persona models those runs grade with and converse with.

Subscription-based CLI runs serve as the cheap everyday dev loop and are not the source of record. The dev runner drives several host CLIs, each behind its own adapter (requirement: Dev-runner host adapters). A run on any of its hosts is a dev-loop result, and so is a grade from the dev runner's own rubric judge. Every such result:

- SHALL be labelled with its host as a dev-runner result that is not comparable to matrix results, for example "dev-runner (codex), not comparable to matrix";
- SHALL NOT be written where the support report reads its logs;
- SHALL NOT stand in for, or fill, an authoritative cell.

The dev runner SHALL refuse a summary-log path inside the directory the support report reads. CI executes only L0 and lint by default, and metered eval runs are budget-capped.

Every L1 verdict SHALL be defined once, as a pure function in the shared verdict module. It takes plain values and returns a pass flag with an explanation. Every runner SHALL reach a scenario's verdict through it rather than reimplementing the assertions: the metered path, and the dev runner on each of its hosts. Because the verdicts are pure, each SHALL be exercisable by L0 tests without a model call.

A verdict that asserts a produced file is in the standard format SHALL establish that by running the mechanical check over it and judging the reported errors. It SHALL never inspect the text for characteristic substrings instead.

- Errors that follow from information the scenario's input did not carry MAY be tolerated, and the tolerated set SHALL be explicit.
- Some defects make the file unbuildable but are invisible to the mechanical check, which extracts narrowly rather than parsing YAML. The verdict SHALL assert such a defect directly, and SHALL be narrow enough to admit the shapes that do build.

The dev-runner scenario set SHALL cover the import skill. It SHALL therefore support scenarios of this kind:

- they stage no proposal file;
- they supply a source document in the request instead;
- they assert against a file the skill creates, whose name the skill chooses, rather than one staged in advance.

Some scenarios license the skill to choose the produced file's name, including those that stage a seed the skill may replace with a fresh `<slug>.md`. In every such scenario, the verdict SHALL locate the produced proposal in the workspace rather than assume a staged filename. The selection SHALL be a pure function in the shared verdict module, exercisable by L0 tests without a model call, and every runner SHALL grade the file it selects.

#### Scenario: Release gate
- **WHEN** a release-gating eval is run
- **THEN** it executes on the metered authoritative path with per-model logs, not on the subscription dev runner

#### Scenario: Dev-runner grade is not a source of record
- **WHEN** a dev run is graded by the subscription judge
- **THEN** its summary labels the grades as dev-runner L2, not comparable to the matrix, and no file the support report reads has been written or changed

#### Scenario: Verdict reached from both runners
- **WHEN** a scenario's L1 assertions are evaluated on the metered path and on each of the dev runner's hosts, Codex among them
- **THEN** every one of them calls the same shared verdict function and reaches the same pass flag for the same produced artifact

#### Scenario: Import iterated without metered spend
- **WHEN** import guidance is being iterated on
- **THEN** the dev runner can exercise the import skill end to end, pasting the source document into the request and judging the file the skill creates

#### Scenario: Structurally broken output rejected
- **WHEN** a produced file contains the expected substrings but leaves the metadata block unclosed and the reference list malformed
- **THEN** the verdict fails on the mechanical check's errors rather than passing on the substrings

#### Scenario: Unbuildable file the mechanical check cannot see
- **WHEN** a produced file places a TODO marker as a bare line inside the metadata block, so the document converter rejects the block while the mechanical check reports no error
- **THEN** the verdict fails on that defect

#### Scenario: Marker shapes that do build are accepted
- **WHEN** the same marker appears as the value of a key, quoted or unquoted
- **THEN** the verdict does not fail, because those shapes parse

#### Scenario: Tolerated shortfall
- **WHEN** the source document carries fewer references than the guidance requires
- **THEN** the reference-count error alone does not fail the verdict, because the skill must not invent sources

#### Scenario: Verdict logic covered without a model
- **WHEN** an L1 verdict's failure modes are tested
- **THEN** L0 tests call the pure verdict function directly and no model is invoked

#### Scenario: Draft written to a fresh filename
- **WHEN** a write scenario's model creates a new `<slug>.md` instead of editing the staged seed in place
- **THEN** the verdict grades the created file, not the untouched seed

#### Scenario: Codex dev run labelled by host
- **WHEN** a dev run on the Codex host completes
- **THEN** its summary records the host and the label "dev-runner (codex), not comparable to matrix". No file the support report reads has been written or changed, and no matrix cell takes its result

#### Scenario: Summary log where the support report reads
- **WHEN** a dev run on any host is given a summary-log path inside the directory the support report reads
- **THEN** the runner exits with a usage error before staging and writes nothing there

### Requirement: Publish filter regression coverage
The harness SHALL cover the publish skill's pandoc filters with regression tests, including at least one fixture whose research-question list contains an in-text citation; the filter output MUST contain the citation resolved rather than an unprocessed citation key. Tests requiring external converters SHALL be skipped cleanly when those tools are absent.

#### Scenario: Citation inside a research question
- **WHEN** the rq-filter regression test runs with pandoc available
- **THEN** the typst output wraps each research question and contains no unresolved citation keys

### Requirement: Session-derived fixtures
Fixtures MAY be curated from real skill-session output when the session used a synthetic topic. Such fixtures MUST be audited against the committed session log, MUST NOT contain personal data, and follow the same oracle rules as invented fixtures.

#### Scenario: Fixture curated from a demo session
- **WHEN** a session-derived fixture is added to the corpus
- **THEN** its content traces to a committed session log, contains no personal data, and ships with an `expected.json` oracle

### Requirement: Fixture corpus with oracles
Fixtures SHALL follow the fixture blueprint: synthetic proposals covering both languages, both levels, all quality tiers, every mechanical check rule (tripped at least once and passed at least once), every methodology branch, clean controls, and workflow states — each with an `expected.json` ground-truth oracle consumed by L1/L2. Fixtures MUST NOT contain content from real proposals; personal data in fixtures is obviously fake.

#### Scenario: New check rule added
- **WHEN** a new mechanical rule enters the check skill
- **THEN** at least one fixture trips it and one passes it, encoded in their oracles

### Requirement: Prose-relaying verdicts match without regard to case

A verdict that judges whether a skill relayed given content into its chat answer SHALL match case-insensitively. Sentence capitalisation is a property of prose, not of the finding being relayed, so a correct relay SHALL NOT fail on it.

#### Scenario: Relay begins a sentence with the finding

- **WHEN** the skill reports a finding as "Duplicate reference id `Lee24Index`" and the oracle records it as "duplicate reference id"
- **THEN** the verdict counts it as relayed

#### Scenario: Finding genuinely absent

- **WHEN** the skill's answer never mentions a finding the oracle records
- **THEN** the verdict does not count it, and enough missing findings still fail the scenario

### Requirement: Export paths are verified by building real documents

Automated verification SHALL build real documents on every export path the publish skill can resolve, over the full fixture corpus, and SHALL assert that each build completes and produces its declared outputs. A test that only exercises path selection, argument assembly, or offline helpers SHALL NOT be treated as coverage of a build path.

Such a test SHALL drive the shipped build entry point rather than reassembling the converter invocation, so that a defect in how the shipped code constructs that invocation is caught rather than reproduced.

#### Scenario: A broken tier fails the suite

- **WHEN** a change makes one output tier unable to produce a document
- **THEN** the export verification fails for that tier, naming it, without any model involvement

#### Scenario: Selection logic alone is not coverage

- **WHEN** the only test touching a tier verifies which engine would be chosen
- **THEN** that tier counts as unverified, because no document was produced

### Requirement: CI provides the document toolchain

Continuous integration SHALL provide the converter and engines the export verification needs, so those tests execute rather than skip. Toolchain provisioning SHALL use pre-built published images at pinned versions, so a failing run always indicates a change in this repository rather than an upstream update. Where an image cannot host the test runner, the export path it covers MAY be exercised by a script, and that script's invocation SHALL be guarded against divergence from the shipped build path by a test requiring no toolchain.

#### Scenario: Toolchain absent locally

- **WHEN** a contributor without the toolchain runs the suite
- **THEN** the build tests skip and the rest of the suite passes, while CI still executes them

#### Scenario: Script and shipped build diverge

- **WHEN** the shipped build path gains a converter filter that a CI build script does not
- **THEN** the divergence guard fails, independently of whether any toolchain is installed

### Requirement: Notes files excluded from draft selection
The shared draft-selection function SHALL treat files ending in `.notes.md` as non-proposal markdown, alongside the existing non-proposal names, so no verdict ever grades a notes file as the produced proposal. The exclusion SHALL be covered by L0 tests without a model call. Fixtures MAY ship notes files; a notes file carries no `expected.json` oracle obligations of its own.

#### Scenario: Notes file never selected as the draft
- **WHEN** a scenario workspace contains `energy-attack.notes.md` and `energy-attack.md`
- **THEN** draft selection returns `energy-attack.md` even when the notes file sorts first

#### Scenario: Exclusion tested without a model
- **WHEN** the L0 suite runs
- **THEN** a unit test exercises the `.notes.md` exclusion through the pure selection function

### Requirement: Title-alarm coverage
The corpus SHALL carry at least one fixture whose title trips several title tells at once, with the tells encoded in its `expected.json` oracle, alongside the existing fixtures whose titles trip none. The agent-judgment half of the title rule — recognising that a proper noun names a tool carried as the instrument, and offering abstracted alternatives — is not reachable by any offline test, so it SHALL be covered by a metered L2 eval task scoring whether the skill raises the title, names the certificate consequence, and offers alternatives without silently rewriting the title.

#### Scenario: Bad-title fixture
- **WHEN** the corpus is exercised against the deterministic check
- **THEN** the bad-title fixture reports its title tells as warnings, matching its oracle, and the run does not fail on them

#### Scenario: Clean-title control
- **WHEN** a fixture whose title names a contribution and its object is checked
- **THEN** no title warning is emitted and its oracle records none

#### Scenario: L2 title alarm scored
- **WHEN** the metered title eval runs against a proposal whose title carries a tool name as the instrument
- **THEN** the score reflects whether the skill raised the title, named the certificate consequence, and offered abstracted alternatives rather than replacing the title unannounced

### Requirement: Support classification exported as data

The support classification the matrix produces SHALL be exportable as machine-readable data alongside the human-readable report, keyed by model and task, so it can be vendored into a skill that must consult it without network access or repository access. The export SHALL distinguish an untested cell from a failing one, because a skill treating "never measured" as "passes" would clear a model it knows nothing about.

#### Scenario: Verdicts exported after a matrix run

- **WHEN** the classification is regenerated from eval logs
- **THEN** a machine-readable export is produced alongside the report, keyed by model and task

#### Scenario: Cell never measured

- **WHEN** a model and task combination has no eval result
- **THEN** the export marks it untested rather than passing

### Requirement: Report offer discipline covered by tests

The uniform failure-path report offer SHALL have negative coverage: the offline suite SHALL fail when a skill's offer wording drifts from the set's, and the model-facing evals SHALL cover that a skill completing normally with findings does not offer a report. A false positive here is more damaging than a miss, because an offer on every ordinary run teaches users to ignore it.

#### Scenario: Skill reports findings on a flawed fixture

- **WHEN** a diagnostic skill runs against a fixture whose oracle expects findings
- **THEN** the eval fails the run if the skill offers a bug report

#### Scenario: Offer wording drifts in one skill

- **WHEN** one skill's offer wording no longer matches the set's
- **THEN** the offline suite fails naming that skill

### Requirement: Externally submitted reproduction seeds

A reproduction seed submitted with a bug report MAY enter the fixture corpus, subject to provenance rules distinct from session-derived fixtures: no committed session log backs it, so it SHALL be verified to contain no real proposal content and no personal data, SHALL be confirmed to still trigger the reported defect before entry, and SHALL receive an `expected.json` oracle encoding the corrected behavior rather than the observed one.

#### Scenario: Submitted seed accepted

- **WHEN** a submitted reproduction seed is verified synthetic and still triggers the defect
- **THEN** it enters the corpus with an oracle encoding the behavior the fix must produce

#### Scenario: Submitted seed no longer reproduces

- **WHEN** a submitted seed does not trigger the defect on the current revision
- **THEN** it is not added, and the report is answered with the revision that already fixed it

#### Scenario: Submitted seed carries real content

- **WHEN** a submitted seed contains recognizable real proposal content or personal data
- **THEN** it is rejected from the corpus regardless of its diagnostic value

### Requirement: Substance-verdict coverage
The fixture corpus SHALL contain at least one hollow control: a proposal that passes every mechanical check with zero errors and zero warnings while failing at least the guidance's swap, delta, and executability tests — generic well-sounding text naming no object of study and no delta beyond its citations. Its oracle SHALL encode the check-clean state, so the fixture doubles as proof that "mechanically clean" carries no substance signal. Naming those three tests is a statement about this fixture, not about how many tests exist.

A metered review task over the hollow control SHALL assert: the review file opens with the verdict "no viable thesis core"; at least two failed substance tests are cited by name; the proposal file is byte-identical after the run. The verdict-line assertions SHALL be a pure function in the shared verdict module, exercisable by L0 tests without a model call. A model-graded scorer SHALL additionally judge that the review states what kind of work would change the verdict and that no finding is softened into needs-revision phrasing.

#### Scenario: Hollow control stays check-clean
- **WHEN** the mechanical check runs over the hollow fixture
- **THEN** it reports zero errors and zero warnings, exactly as the fixture's oracle encodes

#### Scenario: Review task fails on a soft verdict
- **WHEN** the review of the hollow fixture opens with "needs revision" or omits the failed-test names
- **THEN** the L1 verdict fails the run without model involvement

#### Scenario: Verdict logic covered without a model
- **WHEN** the verdict-line function's failure modes are tested
- **THEN** L0 tests call it directly on crafted review texts and no model is invoked

### Requirement: Proposal-prose density scoring
The write task producing a full draft SHALL carry a model-graded scorer that judges the draft body against the information-density rule: scene-setting openers, truisms, restatements of the obvious, and sentences that would fit any thesis in the area fail the grade. The scorer SHALL follow the harness's rubric-template contract and the `*_l2*` naming the support classifier reads.

#### Scenario: Padded draft fails the density grade
- **WHEN** a produced draft opens sections with generic scene-setting sentences
- **THEN** the density scorer grades the sample incorrect, naming the filler

#### Scenario: Dense draft passes
- **WHEN** every sentence of the draft carries thesis-specific information
- **THEN** the density scorer grades the sample correct regardless of section length

### Requirement: Tone criteria in artifact rubrics
The review-quality rubric SHALL include the voice-block conduct rules: the graded review contains no praise of the student or their draft, no self-congratulation by the agent, and neutral constructive wording throughout. The Socratic dialogue rubric's existing no-praise-padding criterion SHALL remain.

#### Scenario: Praising review fails the rubric
- **WHEN** a graded review opens by complimenting the student's excellent proposal before its findings
- **THEN** the review-quality judge grades the sample incorrect on the tone criterion

### Requirement: Pinned model registry
Matrix runs SHALL take their model roster exclusively from a tracked registry file pinning exact provider-qualified model IDs (the version visible in the ID), each with family, price tier, cached input/output pricing, and an enabled flag. A registry entry MAY carry a free-text note recording a caveat about the model's standing in the matrix — for example that the harness cannot drive it — which SHALL default to empty when absent. The roster SHALL cover at least three model families (Anthropic, OpenAI, open-weight) at cheap and frontier price points. Changing a model version SHALL require editing the registry, never a runtime "latest" resolution, so successive runs stay comparable.

The registry SHALL record the date its prices were copied from the provider's catalog. Prices SHALL be taken from the model vendor's own endpoint at its standard service tier. An entry MAY name the endpoint its prices come from. It SHALL do so when the vendor's provider name differs from its catalog namespace, or when the vendor serves no endpoint of its own.

The registry SHALL also carry a roles table naming every model the harness uses outside the roster:

- the rubric judge of matrix runs;
- the dialogue persona, which SHALL default to the judge when absent;
- the metered smoke model, which SHALL name an enabled roster entry;
- the subscription dev-runner judge, together with its pinned effort level.

Every roster and role ID SHALL be a pinned full ID. A floating alias SHALL make registry parsing fail and name the offending entry. Floating aliases are a bare family name, a `~`-prefixed ID, and an ID ending in `-latest`. The judge's ID SHALL appear only in the roles table; the judge's per-run token budget MAY stay with the task configuration.

Every metered role, that is the judge and the persona, SHALL be priced by the registry: by the roster entry with its ID, or, when no roster entry carries that ID, by a price-only role-price entry under the same price basis and date. A registry whose judge or persona cannot be priced SHALL fail parsing and name the role. A role-price entry that no role names, or that duplicates a roster entry, SHALL fail parsing. All harness price lookups SHALL go through this one resolution.

Harness code SHALL take these IDs from the registry. An environment override MAY replace one role for one invocation, and SHALL NOT carry over to any other role.

#### Scenario: Roster comes from the registry
- **WHEN** a matrix run is started with a tier filter
- **THEN** exactly the enabled registry models of that tier are exercised, under their pinned IDs

#### Scenario: Disabled model skipped
- **WHEN** a registry entry sets enabled to false
- **THEN** matrix runs omit it without failing

#### Scenario: Note is optional
- **WHEN** a registry entry carries no note
- **THEN** the registry parses and the model's rendered notes are unchanged

#### Scenario: Role changed in the registry only
- **WHEN** the judge role is set to a different pinned ID in the registry and no override is present
- **THEN** the rubric scorers and the cost estimate both use the new ID without any code edit

#### Scenario: Floating alias rejected
- **WHEN** a roster entry or a role names `sonnet`, `~anthropic/claude-sonnet-latest`, or any ID ending in `-latest`
- **THEN** registry parsing fails and names the offending entry

#### Scenario: Judge named twice
- **WHEN** the task configuration still carries a judge model ID beside the roles table
- **THEN** registry parsing fails and points to the roles table

#### Scenario: Smoke model outside the roster
- **WHEN** the smoke role names an ID that is not an enabled roster entry
- **THEN** registry parsing fails

#### Scenario: Persona defaults to the judge
- **WHEN** the roles table names a judge and no persona
- **THEN** the persona resolves to the judge's ID

#### Scenario: Judge override does not move the persona
- **WHEN** an invocation overrides the judge from the environment and does not override the persona
- **THEN** the persona keeps the registry's persona role

#### Scenario: Held judge priced after leaving the roster
- **WHEN** the roster entry that carried the judge's ID has been re-pinned and a role-price entry for that ID exists
- **THEN** the registry parses, and the cost estimate prices the judge from the role-price entry

#### Scenario: Unpriced metered role rejected
- **WHEN** the judge or persona names an ID that neither a roster entry nor a role-price entry carries
- **THEN** registry parsing fails and names the role

#### Scenario: Orphaned role price rejected
- **WHEN** a role-price entry names an ID that no role names, or an ID a roster entry also carries
- **THEN** registry parsing fails and names the entry

### Requirement: Cost-gated matrix execution
Before issuing any metered call, a matrix run SHALL print a cost estimate derived from registry pricing and SHALL wait for explicit operator confirmation; an explicit non-interactive flag MAY bypass the prompt. Besides each model under test, the estimate SHALL cover the role models the run will call: the rubric judge on every cell-epoch and the student persona on every dialogue-task cell-epoch, each at a per-cell-epoch token budget taken from the registry. Role model IDs SHALL be resolved exactly as the evaluation resolves them, environment overrides included, so the model that is priced is the model that runs. Every model SHALL be priced through the registry's one price resolution: by its roster entry when the roster carries its ID, and otherwise by its role-price entry. The estimate and the post-run actual spend SHALL use this same resolution. When a role model resolves to an ID that neither a roster entry nor a role-price entry prices, the run SHALL stop before the confirmation prompt, name the unpriced ID, and make no metered call; the non-interactive flag SHALL NOT bypass this stop. After the run it SHALL report actual spend per model and in total, computed from recorded token usage and registry pricing, and persist it alongside the run logs. Uncached input, output, cache reads and cache writes SHALL each be charged at their own registry price. A roster entry or role-price entry MAY carry a cache-write price; one without it SHALL be charged its input price for cache writes. The report and the persisted summary SHALL also carry, per model under test, the cache-hit rate (cache-read tokens divided by all prompt tokens, that is uncached input plus cache writes plus cache reads), the cache-read and cache-write token counts, and the serving providers recorded in the run's logs. The run SHALL warn when the cache-hit rate of an Anthropic-family model under test whose requests are routed for caching falls below 50%, or when any of its recorded calls was served by a provider outside those its routing pins; a call served by any provider in the pin's list SHALL NOT be warned. A log MAY record the serving provider for only some of its calls; a call without one SHALL be counted as unrecorded and SHALL NOT be warned. After the run it SHALL also print each role model's observed token usage per cell-epoch beside the registry budget, and flag any budget that the observation exceeds.

#### Scenario: Estimate shown and declined
- **WHEN** the operator declines the pre-run confirmation
- **THEN** no metered call has been made and the run exits cleanly

#### Scenario: Actual cost reported
- **WHEN** a matrix run completes
- **THEN** per-model and total actual cost are printed and persisted with the run's logs

#### Scenario: Judge override priced
- **WHEN** the operator overrides the judge with a registry model priced above the default judge
- **THEN** the estimate charges every cell-epoch's judge budget at the override's registry pricing, not the default judge's

#### Scenario: Persona priced on dialogue tasks only
- **WHEN** a selection contains one dialogue task and one single-turn task
- **THEN** the persona budget is added to the dialogue task's cell-epochs and to no others

#### Scenario: Unpriced role model stops the run
- **WHEN** a role model resolves to an ID that has no registry pricing, with or without the non-interactive flag
- **THEN** the run exits non-zero before the confirmation prompt, names the unpriced ID, and has made no metered call

#### Scenario: Held judge priced from its role-price entry
- **WHEN** no roster entry carries the judge's ID, a role-price entry does, and no override is set
- **THEN** the estimate charges the judge budget at the role-price entry's pricing, the run reaches the confirmation prompt without an unpriced-role stop, and the actual spend prices the judge's usage, cache writes included, from the same entry

#### Scenario: Cache writes priced
- **WHEN** a run's recorded usage includes cache-write tokens
- **THEN** the actual cost charges them at the model's cache-write price, or at its input price where its roster entry or role-price entry carries none

#### Scenario: Cache telemetry persisted
- **WHEN** a matrix run that included an Anthropic-family model under test completes
- **THEN** the printed report and the persisted summary carry that model's cache-hit rate, its cache-read and cache-write token counts, and the serving providers recorded for it

#### Scenario: Caching regression warned
- **WHEN** an Anthropic-family model under test, routed for caching, has a cache-hit rate below 50% in a completed run
- **THEN** the run prints a warning naming the model and its measured rate

#### Scenario: Serving outside the pin warned
- **WHEN** a routed Anthropic-family model under test pins an ordered list of providers, and its recorded calls were served by the second provider in that list and by one provider outside it
- **THEN** the run warns about the provider outside the list, naming it, and does not warn about the second provider in the list

### Requirement: Epoch-based support classification
Each scorable model×task cell SHALL run a fixed number of epochs (default three) and classify by pass rate: all passes solid, mixed flaky, none fail. Per model, the verdict SHALL be: supported when all scorable cells are solid; flaky with the affected skills named when any cell is flaky; a warning naming the failing skills when any cell fails. Tasks red-by-design on the metered path (environment-fidelity probes) and network-dependent tasks SHALL be excluded from classification; a task MAY contribute only its rubric score where its structural score is excluded. Heavy dialogue tasks MAY run reduced epochs on frontier-tier models for budget reasons, and the report SHALL disclose reduced-epoch cells.

#### Scenario: Flaky cell names the skill
- **WHEN** a model passes a task in some epochs and fails it in others
- **THEN** the model's verdict is flaky and names that task's skill

#### Scenario: Environment-fidelity probe not scored
- **WHEN** a task known to be red-by-design on the metered path fails for every model
- **THEN** no model's verdict is affected by that task's structural score

### Requirement: Generated model-support report
A report generator SHALL derive, from the newest run logs only, (1) a summary table in the repository README between generated-section markers — one row per enabled registry model with its pinned ID, verdict, warnings, and the date of the newest log among those models — and (2) a full model×task grid document with per-cell pass rates and per-model run cost, covering every registry model and marking a disabled one as disabled. A disabled registry model SHALL have no README row: the README shows the models a reader can pick today, while the grid document and the exported verdict data keep the disabled model's verdict. Regeneration SHALL be idempotent and SHALL replace only the marked README region. Models never exercised in the available logs SHALL appear as untested rather than silently omitted. ### Requirement: Isolated measurement environment
A routing run SHALL execute against an isolated host configuration that contains only the skills under measurement. It SHALL contain no operator-specific skills, hooks, plugins or agents. It SHALL also contain none of the surfaces the operator's claude.ai account carries: the skills and plugins the account syncs, and its claude.ai MCP connectors. Results then reproduce on any machine and describe a user's install rather than the developer's. A run that cannot establish that isolation SHALL fail with a message naming what is missing, and SHALL NOT fall back to the ambient configuration.

The rules below on authentication, on account-surface opt-outs and on account surfaces govern Claude configurations: the routing rig's, and the dev runner's in isolated mode. A configuration of a client added later is outside them. The requirements that add that client prescribe its home, its login, its child environment and its checks (requirement: Harness-owned host logins).

An isolated Claude configuration SHALL authenticate in one of three ways:

- **Long-lived token.** If a long-lived token is in the environment, the configuration SHALL hold no credentials of its own.
- **Harness login (default).** Otherwise it SHALL hold a link to the harness login (requirement: Harness-owned host logins), never a copy. It SHALL do so only after that login has passed its preflight.
- **Operator's login (explicit opt-in).** Only when the operator explicitly names another stored login's directory for the run SHALL the configuration link that login instead. The harness SHALL never take this opt-in as a fallback, and SHALL label the run with it.

A run SHALL never link the operator's own login because the harness login is missing or was refused. The harness SHALL accept no prepared configuration directory in place of the one it creates. An environment that still names one SHALL be refused with a message naming the replacement.

While such a link exists, a login refresh the host performs inside the isolated configuration SHALL reach the linked login. The host refreshes by replacing the link with a file of its own.

- When the replacement expires later than the linked login, the harness SHALL write it to the link's target with owner-only permissions. The target is the harness login, or the opted-in login. The write SHALL happen within a second of the replacement, and the harness SHALL check once more when the run ends.
- Credentials that do not expire later SHALL never be written.
- No credentials SHALL be written anywhere but the link's target.
- Credential values SHALL NOT be printed, logged, or kept anywhere other than the link's target and the isolated configuration.

The host serializes refreshes only within one configuration directory. A run that starts while the linked login has expired, or is about to, SHALL therefore first hold an exclusive refresh claim beside the linked login. A run that finds the claim held SHALL wait a bounded time for the refreshed login, then proceed with it. If the wait ends without one, the run SHALL refuse with a message naming the cause. A claim left behind by a run that ended without releasing it SHALL stop blocking after a bounded age.

A login the host rejects only once a case is running cannot be detected before the run starts. A routing case that the host ends for that reason SHALL produce no routing verdict. Its recorded error SHALL carry the host's reason and the one remedy for the login the case used, as the dev runner names it for the same failure (requirement: Dev-runner cost and helper-agent telemetry).

Billing per token, too, shows only in a case's stream. Each routing case SHALL therefore be held to the billing checks the dev runner applies to a model-under-test stream (requirement: Dev-runner cost and helper-agent telemetry), over the part of the stream the case read:

- an API-key source;
- a provider other than Anthropic's own API, where the stream reports one;
- overage in use;
- a rate-limit status other than `allowed` or `allowed_warning`;
- a rate-limit report without its overage flag;
- no rate-limit report at all, in a case whose stream holds a model turn. A case stopped before any model turn is not held to this one, and neither is a case stopped for an account surface, which the surface cut short. An assistant event the host writes itself for a failed API call, such as a rejected login, is no model turn: no model served it.

The host may write the rate-limit report after the assistant events of the turn that routed, rather than before the first assistant event. It may also write it after that turn's tool results, and, when the route is a skill invocation, after the skill instructions the host adds to the conversation (all recorded on 2.1.284). A case whose route is recorded SHALL therefore be read on past the route, past the routing turn's tool results and past the skill's instructions. It SHALL be stopped at the first of these: the rate-limit report, the run's closing result, or the first assistant event of a later turn (a model response other than the one that routed). It SHALL NOT be read into a later turn beyond that turn's first assistant event. The case's deadline still bounds it.

A case that fails one of these SHALL produce no routing verdict, and SHALL be recorded as an error naming the reason. The rig SHALL then start no further case. It SHALL record every case of the run as such an error, persist the raw per-case results, leave the tracked report unchanged, and exit with a failure status. Detection after a case is the rig's only billing check, so it stops the rest of the run.

Account surfaces follow the login, not the configuration directory. Every isolated Claude configuration SHALL therefore carry settings that hold exactly three opt-outs and nothing else: claude.ai skill sync off, claude.ai plugin sync off, and claude.ai connectors disabled. Before a run starts, the harness SHALL refuse an isolated Claude configuration in either of these cases, with a message naming what is wrong:

- its settings are not exactly that object;
- it already holds synced skills or synced plugins.

This applies to every isolated Claude configuration.

Whether the host takes its Anthropic profiles only from the profile-directory variable (requirement: Isolated child environment) is unverified. Unless a long-lived token is in the environment, the harness SHALL therefore also refuse an isolated Claude run before it starts while the default Anthropic profile directory holds any entry or cannot be listed: before any host process starts for it, the harness login's status check included. That directory is the one the run's host children would resolve: the user's XDG configuration directory, or `~/.config` without one, followed by `anthropic`. The message SHALL name that directory, never its contents, and SHALL name both remedies: moving the profiles aside, or token mode.

After a run, an isolated measurement SHALL count as invalid in either of these cases:

- the host's stream shows an account surface, in its initialization event or in any later change to its command list. An account surface is any of these:
  - an MCP server, whatever its source;
  - a plugin other than the host's built-in plugins;
  - a skill or command that the host tags as synced from claude.ai, or names under the claude.ai skills namespace;
- the isolated configuration holds synced skills or synced plugins after the run.

An invalid measurement is reported as follows:

- **Dev runner.** The runner SHALL read the host's stream as the host writes it, and SHALL stop the host at the first event that shows a surface, rather than finding the surface after the run. It SHALL send a termination request first and kill the host only if it is still running after a bounded grace (requirement: Harness-owned host logins). An invalid run SHALL exit with the untested status. Its message SHALL name each surface by kind and name, say that the configuration's opt-outs did not hold, and also name any billing reason the stream shows (requirement: Dev-runner cost and helper-agent telemetry). It SHALL compute no verdict and make no judge call.
- **Routing case.** A case whose stream shows a surface SHALL be stopped as soon as the surface appears. It SHALL be recorded as an error naming the surface, whether or not a route was recorded.
- **Routing sweep.** A routing run whose shared isolated configuration holds synced skills or synced plugins after its cases SHALL record every case of the run as such an error. A case started after the content appeared may have loaded it without any tag in its stream.

### Requirement: Route determined by the first skill invocation
A case's route SHALL be the first invocation of a `proposal-*` skill observed in the run, and the run SHALL be terminated as soon as that route is recorded. Preparatory non-skill tool calls SHALL be tolerated up to a bounded number, and a case that exceeds that bound SHALL be recorded as unrouted rather than retried. A case still running when its time limit is reached, with no route recorded, SHALL instead be recorded as an error naming the limit — whether or not it had exceeded the bound — and SHALL NOT be retried: a host that has not finished within the limit says nothing about the descriptions, and a negative case would pass on it. Skill invocations after the first SHALL NOT change the recorded route.

A case the host ends with an error result before any `proposal-*` invocation SHALL be recorded as an error carrying the host's reason — its subtype, its errors or result text, and the cost and turns so far — and SHALL NOT be recorded as unrouted. Unrouted is a finding about the descriptions; a host failure says nothing about them, and a negative case would pass on it.

- **THEN** the invoked skill is still recorded as the route

- **THEN** the recorded route remains the first invocation

#### Scenario: Host ends the case with an error
- **WHEN** the host ends a case with an error result and no `proposal-*` skill was invoked

- **THEN** the case is recorded as unrouted

#### Scenario: Case reaches its time limit

### Requirement: Routing dataset covers canonical, oblique, and contested phrasings

### Requirement: Routing reported as a confusion matrix
A routing run SHALL persist its raw per-case results and SHALL generate a tracked report presenting expected skill against selected skill, so that a failure names the skill that wrongly claimed the utterance. A single aggregate pass rate SHALL NOT be the only reported figure. The report SHALL record the model and case count the run used. A case whose expected skill was never selected and a case claimed by the wrong skill SHALL be reported as distinct outcomes, since one says a description is too narrow and the other says it reaches too far. The report SHALL state the result it supersedes, so a later run is read as a movement rather than as an isolated figure.

The model SHALL be recorded as what the host served, not only as what the run requested, because an alias resolves to whatever the host currently maps it to. Each raw per-case result SHALL carry the full model ID the host reported serving and the host CLI version, both read from that case's own event stream. A stream that reports neither leaves them empty. The report SHALL name the requested alias, beside each served model ID with the number of measurements it served, and each CLI version with its count. Measurements whose stream reported no served model SHALL be counted as not reported. A report rebuilt from a raw log written before the served model was recorded, whose results carry no served-model field, SHALL say that the served model was not recorded.

A run in which any measurement ended in an error SHALL exit with a failure status, whatever the completed measurements scored. A run in which no measurement completed SHALL leave the tracked report unchanged, so that the report never carries a score no case produced and the next run is still compared against the last real one.

- **WHEN** cases expected to select one skill are routed to another
- **THEN** the report shows that pairing and the utterances involved

#### Scenario: Run provenance recorded
- **WHEN** a report is generated
- **THEN** it names the requested model, each served model ID with its measurement count, the CLI version, and the number of cases measured

#### Scenario: Served model recorded per case

#### Scenario: Nothing measured
- **WHEN** every measurement of a run ends in an error
- **THEN** the tracked report is left unchanged, the raw per-case results are still persisted, and the run exits with a failure status

### Requirement: Routing runs are on-demand, not a CI gate
The routing rig SHALL be invocable through a registered task and SHALL NOT be part of the default local test chain or of CI, since it depends on an interactive host installation and subscription credentials. The dataset's structural integrity and the rig's pure functions SHALL be part of the default test chain.

#### Scenario: Default chain stays offline
- **WHEN** the L0 chain runs
- **THEN** no routing measurement is issued and the chain passes without host credentials

#### Scenario: Dataset guarded by the default chain
- **WHEN** the dataset is edited to drop a required case kind
- **THEN** the L0 chain fails

### Requirement: A routing case is measured in the workspace its utterance implies
The workspace staged for a routing measurement SHALL contain the files that case's utterance names, and SHALL NOT contain unrelated fixture files staged for other cases. An utterance naming no file SHALL be measured against a single proposal, so the workspace still resembles a user's rather than an empty directory. A measurement whose utterance names a file the suite cannot stage SHALL fail rather than run against a workspace missing it.

#### Scenario: Utterance names one file
- **WHEN** a case's utterance names a proposal file
- **THEN** that file is present in the workspace and the other cases' fixtures are not

#### Scenario: Ambiguity is not manufactured
- **WHEN** a case's utterance refers to the user's work without naming a file
- **THEN** the workspace holds exactly one proposal, so the reference has one referent

#### Scenario: Unstageable file named
- **WHEN** an utterance names a file no fixture provides
- **THEN** the run reports it instead of measuring against an incomplete workspace

### Requirement: Uniform epoch coverage across routing cases
Every routing case SHALL be measured at the same epoch count by default, so that a failure is reported as a rate rather than as a single event and no class of case carries less evidence than another. A run MAY override the count, and the report SHALL state the count used.

#### Scenario: Single failure is not read as settled
- **WHEN** a case fails in some epochs and passes in others
- **THEN** the report shows the rate rather than a pass or fail

#### Scenario: Epoch count recorded
- **WHEN** a report is generated
- **THEN** it states the epochs each case was measured at

### Requirement: A conditions change invalidates comparison
When a routing run is produced under changed measurement conditions, the report SHALL NOT present the previous score as a comparable predecessor. The conditions are workspace staging, epoch policy, case set, model, and the isolation of the host configuration. The report SHALL instead record that conditions changed, so that a movement caused by the rig is never read as a movement caused by the skills.

The report and the run's raw results SHALL record the isolation conditions they were measured under. When the outgoing report records no isolation conditions, or records different ones, the run SHALL treat the earlier score as measured under different conditions, without the operator having to declare it.

The model condition SHALL be detected in the same way, from the served model IDs rather than from the requested alias. When the outgoing report records no served model, or a different set of served model IDs than the new run, the run SHALL treat the earlier score as measured under different conditions, without the operator having to declare it. The host CLI version SHALL be recorded, but a different version SHALL NOT on its own make the earlier score incomparable. The operator's own declaration of a conditions change SHALL still apply for every other condition, including a CLI change the operator judges relevant.

#### Scenario: Staging changed between runs
- **WHEN** a run follows a change to how workspaces are staged
- **THEN** the report marks the earlier score as measured under different conditions rather than as superseded

#### Scenario: Earlier report measured with account surfaces present
- **WHEN** a routing run is measured with the claude.ai account surfaces closed, and the outgoing report records no isolation conditions
- **THEN** the new report marks the earlier score as measured under different conditions rather than as superseded, although the operator declared no conditions change

#### Scenario: Alias resolves to a different model
- **WHEN** the outgoing report records `claude-haiku-4-5-20251001` as served, and the new run's alias `haiku` is served as `claude-haiku-5-5`
- **THEN** the new report marks the earlier score as measured under different conditions, although the operator declared no conditions change

#### Scenario: Earlier report records no served model
- **WHEN** the outgoing report carries no served model
- **THEN** the new report marks the earlier score as measured under different conditions rather than as superseded

#### Scenario: Same isolation conditions
- **WHEN** the outgoing report records the same isolation conditions and the same served model IDs as the new run, and the operator declares no conditions change
- **THEN** the new report states the earlier score as the one it supersedes

#### Scenario: Same served model on a newer CLI
- **WHEN** the outgoing report records the same isolation conditions and served model IDs as the new run but an older CLI version, and the operator declares no conditions change
- **THEN** the new report states the earlier score as the one it supersedes and names its own CLI version

### Requirement: Read-only mandate measured under a compound request
The harness SHALL carry an L1 task whose single utterance asks for the check and the fixes together, against a fixture whose errors are genuinely fixable, scored on the proposal being byte-identical after the run. A check-only utterance cannot measure the mandate: nothing in it asks for an edit, so a run that would have edited under pressure still passes.

The task SHALL sit outside the model-support matrix, alongside the other check-report variants, because its verdict measures a mandate rather than a model capability.

#### Scenario: One utterance asks for both
- **WHEN** the compound task runs and the agent is asked to check a proposal and fix whatever the check reports
- **THEN** the verdict passes only if the oracle's errors are relayed in chat and the proposal file is unchanged

### Requirement: Baseline comparison arm
Both runners SHALL support a without-skill control for single-turn tasks: the same fixture staging, user request, and verdicts, with the skill neither installed nor injected. Baseline runs SHALL be on-demand and cost-gated like every metered run, never part of the default matrix. Where baseline results exist beside with-skill results, the report SHALL show per task what the skill buys (pass-rate delta) against what it costs (token delta), SHALL flag scorers that pass in both arms as dead-assertion candidates, and SHALL flag scorers that fail in both arms as too-hard candidates. Verdict logic SHALL be identical in both arms.

#### Scenario: Baseline run requested
- **WHEN** a baseline run is invoked on a single-turn task
- **THEN** the model receives the task's user request and files without any skill instructions, and the run is scored by the same verdicts as the with-skill run

#### Scenario: Delta reported
- **WHEN** the report finds baseline and with-skill results for the same task and model
- **THEN** it renders the pass-rate delta beside the token delta, so a skill that buys nothing at double the tokens is visible as such

#### Scenario: Assertion passes in both arms
- **WHEN** a scorer passes with and without the skill
- **THEN** the report names it as a dead-assertion candidate rather than counting it silently toward skill value

#### Scenario: Multi-turn task requested as baseline
- **WHEN** a baseline run is invoked on a persona-dialogue task
- **THEN** the invocation is rejected with the reason rather than producing a meaningless control

### Requirement: Duration reported beside token usage
The support report SHALL read wall-clock duration from the run logs and present it alongside token usage, so the cost of a skill is visible in both currencies.

#### Scenario: Report generated from logs
- **WHEN** the report is regenerated from eval logs
- **THEN** each run's duration appears beside its token usage and cost

### Requirement: Measured environments carry no eval definitions
No runner SHALL stage eval definitions, oracles, or assertion text into the environment the model under test can read. That covers the fixture oracles, and the eval projections the skills ship for the standard's sake. A skill installed for a real user legitimately carries its eval projection. A skill installed for measurement SHALL NOT, because a model that can read what it will be graded on is not being measured.

This holds wherever a runner installs a skill: the host's skill directory in the dev runner's workspace, whichever host the run uses (for example `.claude/skills/` for Claude and `.agents/skills/` for Codex), the routing rig's isolated configuration, and an Inspect sandbox.

#### Scenario: Dev runner stages a skill
- **WHEN** the dev runner installs a skill into its temp workspace
- **THEN** the installed copy contains no eval definition file, while scripts, references, and templates copy as shipped

#### Scenario: Routing rig stages the skill set
- **WHEN** the routing rig installs the skills into its isolated configuration
- **THEN** no installed skill carries an eval definition file

#### Scenario: Inspect staging stays a whitelist
- **WHEN** an Inspect task stages a fixture and a skill's assets
- **THEN** only the skill's references, scripts, and templates enter the sandbox, and the fixture's oracle never does

#### Scenario: Codex dev run stages a skill
- **WHEN** the dev runner installs a skill and its siblings under `<ws>/.agents/skills/` for a Codex run
- **THEN** no installed copy contains an eval definition file, while scripts, references, and templates copy as shipped

### Requirement: Bilingual terminology guard

The L0 suite SHALL verify that the shipped bilingual surfaces use the per-language document term: the supervise closing note's English section names the document a proposal and never an Exposé; its German section names it an Exposé and contains "proposal" only inside identifiers or URLs; and the shipped German verdict-tier phrases and German subtitle strings use "Exposé". The guard SHALL name the offending file and term on failure.

#### Scenario: Crossed term caught
- **WHEN** "Exposé" enters the closing note's English section, or a bare "proposal" enters its German prose outside an identifier or URL
- **THEN** the L0 suite fails and names the file and the offending term

#### Scenario: Identifiers exempt
- **WHEN** the German section carries the repository URL or a `proposal-*` skill name
- **THEN** the guard does not flag it

### Requirement: Closing-note shape guard

The L0 suite SHALL verify the shape of the shipped supervise closing note, since its whole purpose is to survive a channel that renders no markup and nothing else checks that. For each of its English and German sections the guard SHALL require exactly one paragraph, no line beginning with a blockquote, heading, or list marker, and no emphasis markers anywhere in the section. It SHALL require the English section to open with "Note:" and the German section to open with "Hinweis:" and to name the artifact "Rückmeldung". The guard SHALL name the offending section and the offending construct on failure.

#### Scenario: Markup reintroduced
- **WHEN** a blockquote marker, heading marker, or bold run-in returns to either section of the shared snippet
- **THEN** the L0 suite fails and names the section and the construct

#### Scenario: Paragraph split
- **WHEN** a section is split into two paragraphs
- **THEN** the L0 suite fails, because a run-in label reaches only the paragraph it opens

#### Scenario: Run-in label missing
- **WHEN** a section no longer opens with its language's run-in label
- **THEN** the L0 suite fails and names the section

### Requirement: Dev-runner cost and helper-agent telemetry

The dev runner SHALL read the host's event stream rather than its plain text output, and SHALL save that stream into the run's workspace, so that a kept workspace carries the run's tool calls and narration for later reading. On Codex, the stream is the JSON event stream together with the records the runner reads from the host's session record, saved in the same file. On Copilot, it is the prompt mode's JSON event stream together with the records the runner reads from the session's event file in the home. Those records are reduced to the fields the readers use and saved in the same file. Beside each run's L1 verdict, the runner SHALL report:

- the model the host served, by the full ID the host reports, beside the name the run requested, and the host CLI version.
  - On Codex, the served model is the reroute's target where the host reports a reroute. Otherwise it is the model the session record's turn context names, noted where it differs from the requested name, and "unreported" where the record names none. The CLI version comes from the session record.
  - On Copilot, the served model is read as the requirement "Dev-runner host adapters" prescribes, and the CLI version comes from the session record;
- the run's cost, number of turns and duration.
  - Codex reports no cost. On Codex the cost SHALL be absent, never zero. A notional figure is given only where the registry's roster prices the same model name under OpenAI's provider; otherwise the run is labelled unpriced.
  - Copilot reports AI credits, not money. On Copilot the cost SHALL be absent, never zero. The notional figure SHALL be the credits consumed at one cent each, labelled as notional Copilot credits that were not billed;
- the input and output token counts, with the cache read and cache write counts.
  - On Codex, the input count excludes the cached input, and the reasoning token count is added.
  - On Copilot, the counts come from the per-model usage in the session's shutdown record, and the reasoning token count is added;
- on Codex, each plan quota window's usage before and after the run;
- on Copilot, the overage count and the remaining percentage before and after the run, the credit cap and the credits consumed;
- the helper-agent tool calls observed (`Agent`, `Task`, `Workflow`). A Codex subagent spawn and a Copilot task-tool call are both reported as `Agent`;
- for scenarios that produce a supervise feedback, the feedback body's word count, excluding URLs and the closing note;
- for a run graded by the subscription judge: each rubric criterion's grade, the judge's served model ID, its effort and CLI version, its thinking tokens, and the cumulative notional cost of the judge calls. All of these appear under a label saying the grades are dev-runner L2 and not comparable to the matrix.

A dedicated verdict function SHALL pass when a run spawned no more helper agents than its scenario allows. A scenario allows none unless it declares an allowance, as a supervise scenario does for its single verifier. The verdict SHALL name the spawning calls when the run exceeds the allowance. The runner SHALL report it as a separately labelled advisory verdict that does not change the scenario's exit status.

For the supervise scenarios, the verifier is part of the scored L1 verdict, not only of the advisory probe. A run SHALL fail in either of these cases:

- it spawned no helper whose task carries the skill's verifier brief;
- its review's verification section does not state who verified.

Every host offers a subagent tool to a supervise run. Codex has its subagent feature enabled for scenarios with a helper allowance, and Copilot offers its task tool to them. A run that checks inline has therefore skipped the verifier rather than fallen back.

The runner starts the host without permission prompts. On Claude it SHALL therefore deny the host's outward-facing tools on every run, so that no test run can publish, send or schedule anything, whatever the model decides. Those tools are:

- publishing artifacts, and their comments or data;
- messaging other sessions;
- push notifications;
- remote triggers;
- scheduling;
- design sync.

The routing rig SHALL deny the same tools, from the same list.

On Codex there is no tool list to deny. Instead, the harness home's configuration and the run's command SHALL:

- disable apps, plugins, hooks, browser use, computer use, image generation, memories and web search;
- configure no MCP server.

A Codex run whose stream nevertheless shows an MCP tool call SHALL be untested (requirement: Dev-runner host adapters).

On Copilot, the run's command SHALL deny memory, the built-in GitHub MCP server, the GitHub CLI in the shell and `git push`. It SHALL disable the built-in MCP servers and the remote sessions and their export, and it SHALL never pass a sharing option. The home configures no MCP server. A Copilot run whose stream nevertheless shows an MCP tool call SHALL be untested (requirement: Dev-runner host adapters).

The account's claude.ai MCP connectors publish too. Their tool names depend on the account, so no fixed list can deny them. Instead:

- every Claude run SHALL start with the connector switch off (requirement: Isolated child environment);
- a Claude run in either mode whose stream nevertheless shows an MCP server sourced from claude.ai SHALL be stopped at the event that shows it, as the requirement "Isolated measurement environment" prescribes for a dev run, and SHALL be untested;
- an isolated Claude run SHALL also be held to the wider account-surface check of the requirement "Isolated measurement environment".

The runner SHALL accept a hard budget cap and pass it through to the host, where the host offers one. For a host that offers none, such as Codex, the runner SHALL refuse a budget cap rather than ignore it. A Codex run is bounded instead by its wall-clock limit and by the pre-run quota read (requirement: Codex plan billing guard). Copilot offers only a soft cap, in AI credits. On Copilot, the runner SHALL therefore refuse a budget cap in dollars and require the credit cap instead. That cap bounds the run together with its wall-clock limit and the status reads around it (requirement: Copilot plan billing guard).

The runner SHALL label each run with its host, and as measuring either the ambient host configuration or an isolated one prepared for the run.

- For an isolated Claude run, the label SHALL name the isolated directory and the login it links: the harness login, the operator's login under the explicit opt-in, or a long-lived token. For a linked login, the label SHALL also name that login's directory, which is the one place a refresh is written back. The label SHALL follow how the configuration was prepared, never the link's state after the run: while the host refreshes, its own file stands where the link was until the harness restores it. A run that always isolates, such as the install probe, SHALL be labelled with the login it would have linked when its configuration could not be prepared.
- Every run on a non-Claude host, Codex among them, is isolated. Its label SHALL name that host's harness home and the harness login.

The runner SHALL remove from the Claude model-under-test child's environment every inherited variable that can route the host's billing away from the subscription login, in ambient and isolated mode alike. That means every inherited `ANTHROPIC_`-prefixed variable, which covers the API key, the gateway base URL and its auth token, and every `CLAUDE_CODE_USE_` cloud-provider switch. The child environment of every non-Claude host follows that host's billing-guard requirement: for Codex, the requirement "Codex plan billing guard", and for Copilot, the requirement "Copilot plan billing guard".

- **Ambient mode.** The runner SHALL leave every other inherited variable in place, apart from setting the connector switch to off, so that the operator's effort and session settings remain part of what an ambient run measures.
- **Isolated mode.** The child SHALL receive the isolated child environment instead (requirement: Isolated child environment). Its allowlist admits none of those billing variables and no effort or session setting of the launching process, so that an isolated run measures the default host. The one `ANTHROPIC_`-prefixed variable an isolated child carries is the profile directory, which the harness sets to an empty directory and which routes no billing.

Failures SHALL be reported as follows:

- **An error result.** A host result event marked as an error SHALL end the run as a runner failure; a budget overrun is one such event. On Codex, the equivalent is a failed turn or a fatal error event, and on Copilot a session error event. The message SHALL carry the host's subtype or message, its errors, and the cost and turns so far where the host reports them. The Copilot client's exit code SHALL never decide the outcome on its own, because the client can exit 0 after a failed child task or a failed model call.
- **A failure to authenticate.** When that error is a failure to authenticate, the message SHALL also say that the login the run used is no longer valid, and SHALL name the one remedy for that login:
  - for the Claude harness login: running `uv run poe host-login claude`, closing with the login note (requirement: Harness-owned host logins);
  - for the Codex harness login: running `uv run poe host-login codex`, closing with the login note of the same requirement;
  - for the Copilot harness token: creating a fine-grained token that carries only Copilot Requests, then running `uv run poe host-login copilot --reset`, closing with the login note of the same requirement;
  - for an ambient run or the opted-in login: running `claude` and entering `/login`;
  - for a long-lived token: generating a new one with `claude setup-token`.
- **The time limit.** A run still going at its time limit SHALL be stopped as the requirement "Harness-owned host logins" prescribes, and SHALL end as a runner failure naming the limit.
- **A non-zero exit without such an event.** The runner SHALL report the host's stderr. On Copilot, it reports it only after scrubbing the token's value from it (requirement: Harness-owned host logins).
- **A missing closing event.** A stream with no result event SHALL be a runner failure, never a silent success with empty telemetry. On Codex, the closing event is a completed turn. On Copilot, it is the stream's closing result line. A Copilot run whose session record holds no shutdown record SHALL also be a runner failure, because its consumption cannot be read, and it records a billing stop (requirement: Copilot plan billing guard).

The runner's exit status SHALL distinguish four outcomes, so that only a failed verdict reads as a failure of the skill:

- every verdict the run computed passed;
- a verdict failed — L1, or a graded L2 criterion;
- the run is untested, for one of three reasons:
  - the subscription could not serve it. This covers:
    - a harness login refused by its preflight;
    - a login the host rejected;
    - a stream reporting overage use, a refused or unknown rate-limit status, or an API-key source;
    - a stream that reports no rate-limit status at all, so overage cannot be ruled out;
    - a Codex run refused by the plan billing guard, before or after the run;
    - a Copilot run refused by its plan billing guard, before or after the run, a recorded billing stop included, or ended by a quota, rate, session or credit-cap limit (requirement: Copilot plan billing guard);
    - a judge call that produced no grade;
  - its isolation did not hold. This covers:
    - a claude.ai account surface that reached an isolated run (requirement: Isolated measurement environment);
    - a claude.ai connector that reached an ambient run;
    - a foreign skill or an MCP tool call in a Codex run (requirement: Dev-runner host adapters);
    - in a Copilot run (requirement: Dev-runner host adapters), any of these:
      - a workspace or parent-folder finding, a machine-wide managed settings file, or a skill or MCP listing that differs from what was staged;
      - loaded skills not confirmed, or a foreign skill;
      - an MCP server or tool call, or a hook event;
      - a confinement probe that reached a credential or whose session the pinned sandbox settings could not be applied to, a run stopped at a shell call not reported as sandboxed, or a sandbox that was ignored or not reported active;
      - the token's value found in the child's output (requirement: Harness-owned host logins);
      - a recorded isolation stop (requirement: Copilot plan billing guard);
  - a non-Claude run's own preconditions or served settings did not hold. This covers:
    - the run lock not taken within its bounded wait (requirement: Harness-owned host logins);
    - on Codex, an installed CLI below the pinned minimum, or a feature outside the allowlist that reads enabled, even where the preflight reports them;
    - a requested effort the host did not serve (requirement: Dev-runner host adapters);
    - on Copilot (requirement: Dev-runner host adapters), any of these:
      - an installed CLI other than the pinned version, a tool the sandbox needs that is not installed, or a confinement probe that could not run the skills' interpreter;
      - a model the listing does not offer, or offers under a policy other than enabled;
      - a served model other than the requested one, or a model switched because of a rate limit;
      - an effort reported as left unapplied, or an unknown tool name;
      - the approval stop a login records, or the runner records once a skill run's child started, until the operator clears it (requirement: Copilot plan billing guard);
      - a model call no go covers: none recorded, a skill run before the go's canary passed, or a second canary under one go (requirement: Copilot plan billing guard, the go);
- any other runner failure.

A run that is untested because its isolation did not hold SHALL also name in its message any API-key source, overage use, or refused or unknown rate-limit status that its stream shows, so that a surface never hides a billing problem.

The chat the verdicts read SHALL be the closing event's final text and nothing else. On Codex, that is the last completed agent message. On Copilot, it is the content of the last top-level assistant message. All of this logic SHALL be covered by L0 tests against recorded and synthetic event streams:

- the verdicts;
- the event parsing and the telemetry;
- the command the runner builds and the judge command;
- the judge's child environment and the model-under-test child's environment;
- the stream checks that mark a call unavailable, the account-surface checks, and the stop at the first surface;
- the login-failure remedy for each kind of login;
- the login label, and that a refresh is written back only into the labelled login's directory;
- the exit-status mapping;
- the summary it prints.

The telemetry and final-text readers SHALL be pinned against a recorded result event of the host, so that a host field rename fails a test rather than blanking the line. Until a later change records a Codex stream, the Codex readers are pinned against synthetic streams derived from the source of the pinned minimum CLI version, labelled synthetic. Until a later change records a Copilot stream, the Copilot readers are likewise pinned against synthetic streams derived from the package of the pinned version, labelled synthetic.

#### Scenario: Telemetry printed beside the verdict
- **WHEN** a dev-runner scenario completes
- **THEN** its summary carries cost, turns, duration, token counts including the cache pair, the helper-call list, the single-context verdict, and the configuration label

#### Scenario: Served model recorded, not the alias

#### Scenario: Judged run reports L2 beside L1

#### Scenario: Event stream kept

#### Scenario: A surface does not hide overage

#### Scenario: Allowance respected

- **THEN** the scenario's L1 verdict fails and names the missing declaration

#### Scenario: Feedback length reported

- **THEN** the summary carries the feedback body's word count, without URLs and the closing note, as information that changes no verdict

#### Scenario: Budget cap passed through
- **WHEN** the runner is invoked with a budget cap and the host ends the run with an error result for exceeding it
- **THEN** the run ends as a runner failure whose message names the host's subtype, its errors, and the cost and turns so far — not as a skill failure and not with an empty message — and its exit status is the runner-failure status

#### Scenario: Expired login names the remedy
- **WHEN** an isolated run on the harness login ends with an error result saying the host failed to authenticate because the login expired and could not be refreshed

#### Scenario: Ambient run keeps the operator's settings
- **WHEN** the runner is launched in ambient mode from an environment carrying an effort setting and host-session variables
- **THEN** the model-under-test child's environment still carries them, and its connector switch is off

#### Scenario: Isolated run drops the operator's settings
- **WHEN** the runner is launched in isolated mode from an environment carrying an effort setting and host-session variables
- **THEN** the model-under-test child's environment carries neither, because it is the isolated child environment

#### Scenario: No result event

- **THEN** the runner fails saying so, and no verdict is computed over partial narration

#### Scenario: Recorded shape pinned
- **WHEN** the host renames a result-event field the telemetry reads
- **THEN** the L0 test against the recorded result event fails naming the field

#### Scenario: Isolated run labelled

### Requirement: Off-topic-reference resolution covered
The fixture corpus SHALL carry a proposal whose `references:` block holds two uncited entries that are each well-formed and academically legitimate, and whose correct resolutions are opposite: one that a claim already in the proposal needs, and one that is topically adjacent but which no research question, delta statement, or method step needs. The mechanical finding SHALL be identical for both, so that only reading the proposal distinguishes them — a fixture carrying just the second would be passed by a run that removes every uncited entry on sight, which is the same failure to judge in the other direction. #### Scenario: The needed entry is cited, not removed

#### Scenario: Check stays silent on relevance
- **WHEN** the mechanical check runs over the fixture
- **THEN** it reports the entry as uncited and reports no finding about whether the entry is relevant, as the oracle records

### Requirement: Substance-test names consistent across guidance, skills, specs and pins
An offline test SHALL assert that the substance tests named in the prose guidance are exactly the set cited wherever the guidance's tests are referred to by name or by count — the skill bodies that judge substance, the verbatim pins that quote a phrase naming them, and the specifications that enumerate them. A site that names a test the guidance does not, omits one the guidance names, or states a count that disagrees with it SHALL fail the offline suite.

Specifications SHALL be checked only while no change is in flight: a specification is rewritten from a change's delta when that change is archived, so between implementation and archive it describes the previous set by design, and failing the suite for that window would make the gate something to route around.

Two constructs SHALL NOT be reported as drift, because neither is a claim about the set: an enumeration explicitly marked as partial, such as a verdict citing only the tests that actually failed; and a number that states an evidence bar — how many tests must fail — rather than how many exist.

This test is a prerequisite for changing the set: it SHALL be in place before a test is added to or removed from the guidance, so that every dependent site fails loudly in the same change rather than drifting silently.

#### Scenario: Test added to the guidance alone
- **WHEN** a substance test is added to the prose guidance and a dependent skill body still enumerates the previous set
- **THEN** the offline suite fails and names the file that disagrees

#### Scenario: Count drifts in a pinned sentence
- **WHEN** a pinned sentence states a number of substance tests that no longer matches the guidance
- **THEN** the offline suite fails

#### Scenario: Evidence bar is not a set size
- **WHEN** a specification states that at least three substance tests must fail decisively
- **THEN** the offline suite does not read that number as a claim about how many tests exist

#### Scenario: Specification stale while its change is in flight

- **THEN** the offline suite skips the specifications and still checks the guidance, the skill bodies, and the pins

#### Scenario: All sites agree
- **WHEN** guidance, skill bodies, specifications, and pins name the same set
- **THEN** the offline suite passes without a model call

### Requirement: Citation-practice coverage
The fixture corpus SHALL carry two synthetic fixtures for citation practice, each with an `expected.json` oracle calibrated against the mechanical check:
- an idea seed whose references block holds at least ten entries, one of them central enough to a theme that a draft could lean on it for several sentences;
- a proposal draft that already carries the overcitation pattern: the same key on at least three consecutive sentences of one paragraph, an identical multi-key group repeated on adjacent sentences, and a contribution paragraph that summarises one source sentence by sentence.

Neither fixture SHALL contain content from a real proposal. The over-citing draft's oracle SHALL record the repeated-citation warning, and every other proposal fixture's oracle SHALL record its absence. This makes the draft the trip case and the rest of the corpus the pass case for that rule.

The harness SHALL exercise a writing pass that drafts from the seed and a writing pass over the draft, both as dev-runner scenarios and as Inspect tasks. Each run SHALL be judged by an L1 verdict that is a pure function in the shared verdict module, testable without a model call. The verdict SHALL fail when two adjacent sentences carry the same non-empty set of citation keys, comparing within a paragraph and across consecutive items of one list. Sentences whose key sets differ pass. A paragraph break, a heading or a table row resets the comparison. The verdict's sentence and block boundaries SHALL be those of the check's repeated-citation rule, pinned to it by L0 tests. For the pass over the draft, the verdict SHALL additionally fail when a reference the input cites is cited nowhere in the output, so that deleting citations is never a way to pass.

Each Inspect task SHALL carry two model-graded scorers following the rubric-template contract and the `*_l2*` naming the support classifier reads:
- citation scope: every sentence's source is recognisable, no publication is repeated on consecutive sentences while source and topic are unchanged, and no sentence continues a source without a citation or a back-reference cue;
- synthesis: prior work is grouped and compared by theme rather than summarised one source after another.

#### Scenario: Repeated key fails the run
- **WHEN** a produced draft cites the same key on two adjacent sentences of one paragraph
- **THEN** the L1 verdict fails the run, naming the line

#### Scenario: Source switch passes
- **WHEN** adjacent sentences carry different key sets, such as one key and then that key with a second
- **THEN** the L1 verdict does not fail on them

#### Scenario: Deletion is not a repair
- **WHEN** a writing pass over the repetitive draft removes every citation of a reference the input cited
- **THEN** the L1 verdict fails the run, naming the reference

#### Scenario: Verdict logic covered without a model
- **WHEN** the verdict's failure modes are tested
- **THEN** L0 tests call it directly on crafted proposal texts and no model is invoked

#### Scenario: Over-citing draft trips the warning
- **WHEN** the mechanical check runs over the over-citing draft
- **THEN** it reports the repeated-citation warning, as the draft's oracle records, and reports no error

#### Scenario: Uncued deletion fails the scope grade
- **WHEN** a draft keeps one citation per paragraph but leaves the following sentences without a back-reference to the source
- **THEN** the citation-scope scorer grades the sample incorrect

### Requirement: Model identifiers live only in the registry
An L0 test SHALL scan the tracked tree for model identifiers. It SHALL recognize the identifier shapes of the vendor families the harness has used, and the version line of every registry entry.

- **Code and configuration:** the harness and repository scripts, the project configuration, and the CI workflows SHALL carry no model identifier.
- **Any other tracked file:** it MAY name a model only by an identifier that resolves to a current roster entry or role. A resolving identifier is in one of these spellings:
  - provider-qualified;
  - without the provider prefix;
  - the subscription CLI's form, which has dashes between version digits and an optional trailing date.

An explicit allowlist SHALL exempt these, each entry with its reason:

- the registry itself;
- change records under the OpenSpec changes directory;
- the main specifications, whose scenarios carry illustrative identifiers, receive them when a change is archived, and change only through a change record;
- generated report outputs, including the generated region of the README;
- generated eval projections;
- model-identifier normalization test data, including an eval scenario whose subject is the model identifier a user reports.

An allowlist entry MAY cover a category of files, a whole file, or a single identifier within one file. An entry that tolerates a violation another change will remove SHALL name that change. Such a parked entry SHALL fail the test once it exempts nothing, and so SHALL an entry for a single identifier, so that a resolved exemption cannot linger. Category entries such as generated outputs and the main specifications stay in place even when their files currently name only current models.

### Requirement: Model currency check
A checker SHALL compare every roster pin and every role against the provider's public model catalog. It SHALL use no credentials and only the standard library. For each pin it SHALL derive a version line: the identifier with its version number wildcarded and any trailing snapshot-date token ignored. Variants carrying a `:` suffix SHALL be excluded.

An entry MAY override its line with an explicit pattern, or opt out of tracking. An opted-out entry SHALL be reported as untracked, never silently omitted. Subscription-form role IDs SHALL be mapped to catalog IDs: dashes between version digits become dots, a trailing date is dropped, and the vendor namespace is added.

The checker SHALL report each of the following as a structured finding:

- a newer model in the line, newer meaning a higher version, or the same version created later;
- a pin missing from the catalog;
- a non-empty expiration date;
- price drift beyond a fixed relative tolerance against the vendor's own endpoint, for roster entries and role-price entries alike.

It SHALL also report, as informational findings that are never written, the version lines in any vendor namespace the registry uses that no registry entry or role derives and that have a member created after the registry's line-review date. The registry SHALL record that date, and only a maintainer's edit SHALL move it.

Its output SHALL be human-readable by default and JSON on request.

A write mode SHALL apply newer-in-line bumps and refreshed prices to the registry, and update the price date. It SHALL edit lines so that comments and notes are preserved, and running it a second time SHALL change nothing. It SHALL NOT rewrite the matrix judge or the persona role. It SHALL report them as held, because changing either invalidates every rubric-counted cell until a full re-baseline. When it re-pins a roster entry whose outgoing ID a held role still names, it SHALL add a role-price entry for that ID in the same edit, so the held role stays priced. It SHALL NOT change the line-review date. Its logic SHALL be covered by L0 tests over a recorded catalog snapshot, without network access.

#### Scenario: Newer model in the line
- **WHEN** the roster pins `openai/gpt-5.6-sol` and the catalog lists `openai/gpt-6-sol` and `openai/gpt-6.1-sol`
- **THEN** the checker reports `openai/gpt-6.1-sol` as the newest model in the line

#### Scenario: Variants and siblings are not successors
- **WHEN** the catalog lists `:batch` variants, `-pro` or `-prime` siblings, and `~`-prefixed floating aliases next to a pinned model
- **THEN** none of them is reported as a newer model

#### Scenario: Dated snapshot of the same version
- **WHEN** the catalog lists a dated snapshot of the pinned version that was created after the pinned entry
- **THEN** the checker reports the dated snapshot as newer

#### Scenario: Floating pin detected
- **WHEN** a pinned ID is absent from the catalog while a dated sibling of the same version is listed
- **THEN** the checker reports the pin as missing and proposes the dated sibling

#### Scenario: Subscription role mapped
- **WHEN** the dev-runner judge role is `claude-sonnet-5-5` and the catalog lists a newer Sonnet
- **THEN** the checker reports the newer model and proposes its subscription-form ID for review

#### Scenario: Judge held
- **WHEN** a newer model exists in the matrix judge's line
- **THEN** the checker reports it as held and the write mode leaves the judge and persona roles unchanged

#### Scenario: Held judge's roster entry re-pinned
- **WHEN** the write mode re-pins the roster entry that carries the judge's ID
- **THEN** the judge role keeps its ID, a role-price entry for that ID is added in the same edit, and the edited registry parses

#### Scenario: New line in a roster vendor namespace
- **WHEN** the catalog lists `anthropic/claude-fable-5.1`, created after the line-review date, and no registry entry or role tracks the Fable line
- **THEN** the checker reports the Fable line as an informational finding naming `anthropic/claude-fable-5.1`, exits as it would without it, and the write mode adds no roster entry

#### Scenario: Reviewed new line
- **WHEN** the maintainer moves the line-review date past the newest member of a reported line
- **THEN** the checker no longer reports that line

#### Scenario: Write is idempotent
- **WHEN** the write mode runs twice against the same catalog snapshot
- **THEN** the second run changes no byte of the registry

#### Scenario: Catalog unreachable
- **WHEN** the catalog request fails
- **THEN** the checker exits with a distinct "currency unknown" status and writes nothing

### Requirement: Weekly model-bump pull request
A CI workflow SHALL run the currency check in write mode weekly and on manual dispatch. When the registry changes, it SHALL keep exactly one open pull request from a fixed branch, creating it or updating it. It SHALL use only the repository's built-in token, with the least permissions this needs.

Pull requests opened with that token trigger no pull-request workflows. The workflow SHALL therefore start the regular CI workflow on the bump branch itself.

It SHALL NOT overwrite the bump branch once the branch carries a commit from anyone else; it SHALL comment on the pull request instead. When main already satisfies every finding, it SHALL close a pull request that is no longer needed.

The pull request description SHALL:

- list every finding, including any role-price entry added for a held role;
- list the new lines in the registry's vendor namespaces as a roster decision for the maintainer;
- instruct the maintainer to regenerate the model-support report locally from the run logs and to re-run the shared-copy sync before merging;
- state that new IDs render as untested until a cost-gated matrix run;
- flag a bump of a subscription role for a check that the CLI resolves the new ID to itself.

Report-only findings, new lines included, SHALL appear in the run summary. A new line alone SHALL NOT open a pull request or fail the run. A pin that is missing or expiring without a writable successor SHALL fail the scheduled run.

The workflow SHALL NOT call any model, read any secret beyond the built-in token, or merge.

#### Scenario: New model published
- **WHEN** the weekly run finds a newer model in a roster line
- **THEN** a pull request from the fixed branch carries the registry edit and a description with the regeneration instructions, and the regular CI workflow runs on that branch

#### Scenario: Pull request already open
- **WHEN** a bump pull request is open and a later run finds further changes
- **THEN** the same pull request is updated and no second one is opened

#### Scenario: Maintainer has pushed to the bump branch
- **WHEN** the bump branch carries a commit not made by the workflow
- **THEN** the workflow leaves the branch untouched and comments the new findings on the pull request

#### Scenario: Nothing to bump
- **WHEN** the check finds no writable change
- **THEN** no pull request is opened, and an open one that main has made obsolete is closed

#### Scenario: Pin about to disappear
- **WHEN** a pinned model carries an expiration date and no newer model exists in its line
- **THEN** the scheduled run fails and its summary names the pin

The warning SHALL NOT block the run, alter the estimate, or change the exit status.

The L0 suite SHALL disable the checker's network access for every test by default, so that no test touches the network, including a test that runs a matrix invocation without mentioning the catalog. Tests that assert warnings SHALL substitute a recorded catalog.

#### Scenario: Stale pin warned before confirmation

- **THEN** the warning naming the newer model is printed before the confirmation prompt, and the estimate is unchanged

#### Scenario: Offline gate

- **THEN** a "model currency unknown" warning is printed and the run proceeds to the usual confirmation

#### Scenario: L0 test without a catalog substitute

### Requirement: Subscription text roles (dev runner)

The dev runner's text-only role, its rubric judge, SHALL run through the unmodified official Claude host CLI under the operator's subscription login, whichever host ran the model under test. The judge SHALL be one single-turn text call per rubric criterion, issued under the following constraints.

**Invocation:**

- The model is named by the full model ID that the registry's roles table assigns to the dev judge, never by an alias. An ID that names a metered provider SHALL be refused before any call.
- The effort is passed explicitly, from the same roles table.
- Host customizations are disabled, no tools are offered, the call is limited to one turn, and no session is persisted.
- The host's minimal mode SHALL NOT be used, because it bypasses the subscription login.
- The prompt is delivered on standard input. The content under grading travels only in the prompt and is never written into a measured workspace.
- The child runs in a fixed working directory outside every measured workspace.

**Environment and login:**

- The child environment SHALL be the isolated child environment (requirement: Isolated child environment), built by the same function as the isolated model-under-test child's. No API key, no gateway or provider-routing variable, no inherited effort setting and no host-session variable reaches the child.
- The one credential that MAY reach the child is the subscription's own long-lived login token, when the operator has exported one. The isolated configuration relies on that token, and it is passed through unread. Apart from that token, the harness SHALL NOT read, copy or forward a credential.
- Before the first call of an invocation, the runner SHALL confirm that the host is logged in with the subscription login. That login is one of these:
  - the login linked into the isolated configuration: the harness login, or the operator's login under the explicit opt-in;
  - the subscription's long-lived token.
- Otherwise the runner SHALL stop with the one remedy for that login:
  - for the harness login, the harness login command, closing with the login note (requirement: Harness-owned host logins);
  - for the opted-in login, `claude`, then `/login`;
  - for the token, a new token from `claude setup-token`.
- The remedy for a missing login SHALL never be an API key.
- **Where judging runs.** Judging SHALL run in an isolated Claude configuration, inside which the linked login is kept current.
  - For a Claude run in isolated mode, that is the run's own configuration.
  - For a run on another host, the runner SHALL prepare a fresh isolated Claude configuration for the judge after the model run has ended. The Claude dev judge therefore grades the runs of every non-Claude host, Codex among them.
  - The judge SHALL never run in another host's login home, and SHALL never receive another host's login or environment.
  - A Claude run in the ambient configuration SHALL NOT be judged.
- The first judge call of an invocation runs alone. Later calls run at most four at a time across the process.

**Failing closed.** A judge call SHALL count as unavailable, never as a failing grade, when any of the following holds:

- the host's result is marked as an error;
- the result has no text, zero output tokens or no per-model usage;
- the host reports a rate-limit status other than `allowed` or `allowed_warning`;
- the stream carries no rate-limit report at all, so overage cannot be ruled out;
- overage is in use;
- the session used an API-key source;
- the call was served through a provider other than Anthropic's own API;
- the served model differs from the requested one;
- the call exceeds its time limit. The child process SHALL then first be sent a termination request, and SHALL be killed if it has not exited after a bounded grace (requirement: Harness-owned host logins);
- the response carries no grade line.

An unavailable call SHALL stop further judge calls in the same invocation. A call whose result is marked as an error, and whose stream also shows an API-key source, a provider other than Anthropic's own API, overage in use or a refused rate-limit status, SHALL name that billing reason beside the error and count as untested for billing (Smoke, below).

**Bounding and records:**

- The runner SHALL keep a cumulative notional-cost total of the judge calls and SHALL stop issuing calls once an operator-set cap is reached; criteria left ungraded then count as untested.
- Before a batch re-grade fans out, the runner SHALL print a notional estimate projected from the first call's measured cost. It SHALL NOT start the batch when the projection exceeds the cap.
- Each call SHALL record the host CLI version, the effort, the served model, its thinking tokens and its notional cost. A warning-level rate limit SHALL be reported with its window and utilization.

**Rubrics:**

- The dev judge and the matrix judge SHALL read the same rubric templates and criteria. Each rubric template and criterion SHALL be defined once, and the prompts the matrix judge sends SHALL stay byte-identical to the prompts it sent before that sharing existed.
- The dev judge's question SHALL be the visible user request. Where the matrix judge's question is an oracle list rather than the request, both judges SHALL use the same list.

### Requirement: Prompt caching on Anthropic matrix rows
Matrix requests for an Anthropic-family model under test SHALL be issued so that prompt caching covers the growing conversation, not only the static system and tool prefix. They SHALL be served by a fixed, ordered list of pinned upstream providers with fallbacks beyond that list disabled, the first listed provider serving whenever it is available, so that successive turns reach the cache they wrote. The pinned providers SHALL be ones the operator account's routing guardrails, such as zero data retention, admit; the harness SHALL NOT require relaxing those guardrails. These routing and caching settings SHALL apply to Anthropic rows only, and requests for every other family SHALL be unchanged. The model ID recorded in a run's log SHALL equal the registry ID, so the logs of a cached run count toward the generated report exactly as before. The rubric judge and the student persona SHALL keep their serving configuration: this requirement neither moves nor re-routes them. No one-shot request, that is a rubric-judge or student-persona prompt that no later call extends, SHALL be given a conversation cache breakpoint, because it would pay the cache-write premium without ever reading the cache back; a request of the model under test heads a conversation whose later turns read it back, even when it consists of a single message. The caching mechanism in use SHALL be one that the cache reuse probe has passed on the Anthropic rows it covers. Until a mechanism has passed, Anthropic-family requests SHALL be issued without the provider pin and the caching settings, exactly as for every other family.

#### Scenario: Other families unchanged
- **WHEN** a matrix run includes an OpenAI-family model and an Anthropic-family model
- **THEN** only the Anthropic model's requests carry the provider pin and the caching settings, and the OpenAI model's requests are built exactly as before

#### Scenario: Logged model ID equals registry ID
- **WHEN** an Anthropic row runs with its routing and caching settings
- **THEN** the run's log records the registry ID as its model, and the report generator counts that log for the row

#### Scenario: One-shot prompt gets no breakpoint
- **WHEN** a judge request consists of a single user message
- **THEN** no conversation cache breakpoint is added to it

#### Scenario: No mechanism passed yet
- **WHEN** a matrix run includes an Anthropic-family model and no caching mechanism has passed the cache reuse probe
- **THEN** that model's requests carry neither the provider pin nor the caching settings

### Requirement: Cache reuse probe
The harness SHALL provide a metered probe that replays a fixed, synthetic multi-turn tool conversation for each selected Anthropic registry model and caching mechanism. The conversation's content SHALL be independent of the model's replies, the probe SHALL build the model the same way the matrix does, and it SHALL record the cache usage of every call. Before its first metered call the probe SHALL print a worst-case cost estimate derived from registry pricing, with every prompt token charged at the cache-write price, and SHALL wait for explicit operator confirmation, as a matrix run does. A mechanism SHALL pass on a model only when cache-read tokens make up at least 80% of all prompt tokens, summed over the calls after the first call that writes the cache. The result SHALL state the measured share, the serving providers recorded, and the actual cost. The pass/fail decision and the worst-case estimate SHALL be pure functions covered by L0 tests that invoke no model.

#### Scenario: Probe declined
- **WHEN** the operator declines the probe's confirmation
- **THEN** no metered call has been made and the probe exits cleanly

#### Scenario: Below threshold fails
- **WHEN** cache reads make up 60% of the prompt tokens on the calls after the first cache write
- **THEN** the mechanism fails on that model and the explanation names the measured 60% and the 80% threshold

#### Scenario: No cache write fails
- **WHEN** no call of the replay writes the cache
- **THEN** the mechanism fails and the explanation says that no call wrote the cache

#### Scenario: Reuse at threshold passes
- **WHEN** cache reads make up at least 80% of the prompt tokens on the calls after the first cache write
- **THEN** the mechanism passes on that model

### Requirement: Isolated child environment
An isolated Claude host child SHALL receive an environment built from an allowlist. This covers every Claude host child that runs in an isolated configuration:

- every routing-rig run;
- the model-under-test child of every Claude dev-runner run in isolated mode;
- the dev judge's child, together with its login check.

It also covers the Claude harness login's status checks (requirement: Harness-owned host logins). Such a child SHALL NOT receive the launching process's environment with only the configuration directory overridden. One function SHALL build that environment for all of them, so that no second allowlist can drift from the first. The status check alone then drops the long-lived token from it, so that it reports the home's own login rather than the token's.

A host child of a client added later is outside the allowlist, the configuration-directory variable and the account-surface variables of this requirement. The requirement that adds the client prescribes that child's environment, and the same function SHALL build it from that client's own description. That function SHALL read no credential.

Some clients' harness logins are a token file (requirement: Harness-owned host logins). For such a client, the harness SHALL add exactly one variable to what the function returns: the record's token variable, read from the client's token file immediately before that client's child starts, unless the requirement that adds the client runs that child without it. No other child the harness starts SHALL receive that variable, or any value read from the token file. That excludes:

- every Claude child;
- the dev judge's child and its login check;
- another client's child;
- the audit pre-flight's child.

The allowlist SHALL admit only:
- `PATH` and `HOME`;
- `CLAUDE_CODE_OAUTH_TOKEN`, the long-lived OAuth token variable;
- variables that describe the machine rather than configure the host: user identity and login shell, locale, temporary directories, XDG base directories, proxy and certificate-trust settings, and the process basics Windows requires.

The configuration-directory variable SHALL be set to the configuration the child runs in, replacing any inherited value.

Two account-surface variables SHALL be set by the harness rather than admitted. Each replaces any inherited value:
- the connector switch, `ENABLE_CLAUDEAI_MCP_SERVERS`, set to off, so that the host does not fetch the account's claude.ai MCP servers;
- the Anthropic profile-directory variable, `ANTHROPIC_CONFIG_DIR`, set to an empty directory that belongs to the configuration the child runs in. No Anthropic profile stored outside that configuration can then become the child's login; the user's default profile directory is one such place.

Every other variable SHALL be dropped. That includes:
- the variables a launching desktop-app or SDK session sets to bind a child to itself: entrypoint, session identifiers, messaging socket and token, host auth refresh, and OAuth scopes;
- the variables that tune the host: effort, tool enablement, compaction, timeouts, API endpoint, and MCP connection settings;
- variables that no list names yet. A host that adds one would otherwise leak it into measurement without any sign.

The connector switch SHALL reach every Claude host child the harness starts, not only the isolated ones: the ambient model-under-test child and the advisory audit pre-flight's child as well. The profile-directory variable SHALL reach every Claude child that runs in an isolated configuration. The switch's value SHALL be defined in one place and applied wherever a Claude host child is started.

A runner in ambient mode SHALL keep passing the operator's environment to the child, less only the billing variables the dev runner removes from every model-under-test run (requirement: Dev-runner cost and helper-agent telemetry), and with the connector switch set to off.

The advisory audit pre-flight's child SHALL receive that same ambient environment: the launching environment less every billing variable the dev runner removes, with the connector switch set to off. An exported API key, gateway or cloud-provider switch then cannot bill its calls per token. One function SHALL build the ambient environment for the dev runner and the audit pre-flight alike.

Building the isolated environment SHALL print nothing. No runner output SHALL carry the value of any variable, admitted or dropped. L0 tests with synthetic values SHALL cover:

- how the environment is built;
- every place that uses it: the rig, the isolated dev run, the judge's call and its login check, and the harness login's status check;
- every place the connector switch is applied;
- the audit pre-flight's environment;
- the token variable a token-file client's child receives, and its absence from every other child.

### Requirement: Harness-owned host logins
The harness SHALL keep its own login for each host client it drives, in a login home it owns. No harness action may then share a refresh token with, write to, or log out the operator's own logins of that client: neither the CLI nor a desktop app or editor integration. This requirement covers Claude, Codex and GitHub Copilot. A client added later gets its own home under the same rules.

**Credential kinds.** Each client's record SHALL name the kind of credential its harness login is:

- **Client login** (Claude, Codex): the client's own subscription login, run inside the home. A refreshed Claude login reaches the home through the harness write-back (requirement: Isolated measurement environment); Codex keeps its own login current there.
- **Token file** (Copilot): a fine-grained personal access token. The operator creates it on GitHub with the "Copilot Requests" permission and no other, and with an expiry date. The login command stores it in one file, the token file. That file lies beside the home under the harness state directory, never inside the home, so that no access the client grants its sandbox to its own home can cover it.

For a token-file record, the harness SHALL:

- read exactly one credential, the token file, and no other credential store;
- hand its value only to that client's children, under the one variable the record names, and never on a command line;
- inspect only its prefix, and otherwise use the value only to scrub it, as the next item says;
- before it saves, prints or forwards anything a child of that client produced (its standard error, a runner-failure message, the saved events, the judge's input), replace every occurrence of the value. An occurrence, one in a workspace file the runner could not rewrite included, SHALL make the run untested for isolation and record an isolation stop (requirement: Copilot plan billing guard). The client's own session store in the home keeps its transcripts, which the runner does not rewrite, so the remedy for an occurrence SHALL name revoking the token and a reset of the home, which deletes that store;
- never print, log or copy it, and never write it anywhere but the token file. Only the login command writes that file, with owner-only permissions.

**Location.**

- The home SHALL lie under a per-user state directory for the harness, following the platform's convention:
  - Linux: the XDG state directory;
  - macOS: Application Support;
  - Windows: the local application-data directory.
- Its path SHALL be absolute, its permissions owner-only, and it SHALL lie outside the repository.
- It SHALL never equal, contain, or lie inside the operator's own configuration directory of any client. For Copilot, those are `~/.copilot`, the directory an inherited `COPILOT_HOME` names, and `~/.config/github-copilot`.
- The Codex home SHALL also lie outside the system temporary directory, because Codex refuses to place its helper binaries there.
- A test override of the state directory SHALL be refused in any of these cases:
  - it is not an absolute path;
  - it equals or contains the user's home directory;
  - it equals, contains or lies inside a client's own configuration directory;
  - it lies inside the repository.

**Creation and wipes.**

- When the harness creates a home, it SHALL write a marker into it.
- It SHALL delete a home only when the home carries that marker and is not a symbolic link.
- It SHALL seed only a home that does not exist yet. A login SHALL never adopt a directory at the home's path that lacks the marker, or a symbolic link there: it refuses, naming the directory, and writes, logs out and deletes nothing in it.
- Before the first login, the Claude home SHALL be seeded with two things: the account-surface opt-out settings that every isolated configuration carries (requirement: Isolated measurement environment), and an empty profile directory. The seeding comes first because account content synced once stays on disk.
- Before the first login, the Codex home SHALL be seeded with a pinned configuration. That configuration selects OpenAI's own provider, requires the ChatGPT login, and keeps the credentials in a file in the home. It also turns off web search, the update check, history, analytics, feedback and the bundled skills.
- Before the first login, the Copilot home SHALL be seeded with a pinned settings file and an empty GitHub CLI configuration directory.
  - The settings turn off auto-update, the switch to automatic model selection, hooks, memory, editor auto-connect, experimental features and the shell's start-up file, and they keep custom agents local. The client's prompt mode writes the start-up file's setting into the settings itself on every start, from the run's flag that turns it off; the seed carries that value, so the client's write leaves the settings as they were.
  - They keep any token the client stores in a file in the home rather than in the OS keyring.
  - They pin the OS sandbox: enabled, no bypass, no git or GitHub CLI credentials inside it, and no developer-tool grants.
  - Its deny list is built by construction, not picked entry by entry. It names, by their real paths, the operator's whole home directory, the per-user runtime directory that holds the session bus and the agent sockets, the system's shared temporary directories (`/tmp`, and `/var/tmp` where it exists) and the harness process's own temporary directory where that lies outside them, the harness state directory where it lies outside that home, the token file, and the Copilot log directory, a directory beside the home into which the Copilot children whose sessions the client sandboxes write their process logs, named exactly, because the client grants its log directory to the sandbox after the masks of its denied ancestors. On Linux it SHALL also name the whole process directory of the sandbox's first process (`/proc/1`), never only that process's environment file: the sandbox's first process is its own init, which keeps the environment the client started the sandbox with, the token included, and a thread's environment file shows the same environment. On every other platform the deny list SHALL carry no such entry. Those paths are resolved from the account's entry in the password database and the harness process, never from a child's scratch home. The workspace and the scratch homes lie in the Copilot work directory, outside every temporary directory; the sandbox grants the workspace as the working directory and nothing around it (requirement: Dev-runner host adapters).
  - On Linux they SHALL also keep the staged skill tree read-only inside the sandbox, with one read-only entry: the workspace's `.agents` directory, named relative, which the client resolves against each session's working directory, the workspace, so the settings stay the same for every run. The client's skill tool reads a staged skill's file in its own process, outside the sandbox, and follows a link the sandboxed shell put there; with the whole `.agents` directory read-only the shell can neither replace a staged skill nor rename the directory aside and plant another. The entry SHALL never be narrowed to the skill directory beneath it, which such a rename bypasses. On every other platform the settings SHALL carry no read-only entry.

**Commands.**

- **Login.**
  - For a client-login record, it SHALL run the client's own subscription login inside the home, never a console or API-billing login: for Codex, never an API-key login or an access-token login. For Codex, it MAY use the client's device-code login.
  - For the token-file record, it SHALL run no client login. It SHALL:
    1. read the token from the terminal without echoing it;
    2. before writing anything, refuse a token whose prefix is not the fine-grained token's prefix, a classic token included;
    3. write the token file, and record the approval stop (requirement: Copilot plan billing guard);
    4. run the status read (requirement: Copilot plan billing guard). The login reports ready only when that read passes the preflight, the approval stop it has just recorded apart.
  - Only the operator runs it, never an agent. It SHALL refuse when its standard input is not a terminal. It SHALL also refuse when its environment carries a marker of an agent session: a variable that a Claude Code session, or a Codex or Copilot shell, exports to the commands it runs. The refusal names the marker variables, never their values. Both refusals are speed bumps, not guards: an agent with a terminal tool has a terminal, and a marker can be unset. The rule that agents never log in is the guard.
  - For a client-login record, its environment, the login environment, is the operator's own, so that a browser can open. Every billing variable and every host-session variable of that client is removed, and the configuration directory is set to the home. For Claude, the profile directory is also set to the home's empty one. A token-file login opens no browser. Its status read runs in that client's child environment (requirement: Copilot plan billing guard).
  - On a home that already holds a login, it SHALL first log out of that login in the home. Where the login is no file in the home, the host's own status decides whether the home holds one. For a token file, logging out means deleting the file.
  - If that logout fails, the login SHALL stop, naming the logout's exit status, and neither log in nor wipe: replacing a login whose logout did not go through could orphan a live grant.
  - For Copilot, a clear option SHALL instead remove a recorded stop of any kind (requirement: Copilot plan billing guard), holding the run lock, record the operator's go, and change nothing else. It carries the same terminal and agent-marker refusals. Clearing is the operator's go: it covers one canary and, only once that canary has passed, one skill run (requirement: Copilot plan billing guard, the go). With no stop recorded, the clear option records the go alone.
- **Reset.** A reset option SHALL log out, wipe the marked home, seed it again and log in. A failed logout stops a reset as it stops a login.
- **Clear (Codex).** A clear option of the login command SHALL instead remove a recorded Codex isolation stop (requirement: Dev-runner host adapters), holding the run lock, and change nothing else in the home. It carries the login's terminal and agent-marker refusals, and runs no client login. A Codex reset SHALL keep a recorded isolation stop, recording it again in the reseeded home with its cause and time: a reset replaces the login, not the run's findings, so the clear option stays the stop's one remedy.
- **Logout.**
  - A logout command SHALL run the client's own logout in the home and nowhere else.
  - For the token-file record, the logout SHALL instead delete the token file and nothing else, run no client logout, and name the page where the operator revokes the token.
  - Every logout of a client-login record SHALL run in the login environment: the logout command's own, the one before a login, and the one in a reset. No inherited token, profile directory or configuration directory can then steer it at another login.
  - Live check L3 shows whether the harness logout leaves the operator's other Claude sessions working. Live check X8 shows the same for Codex, whose logout revokes the home's refresh token, and whose login revokes the previous one held in the home. Until a client's check has passed, the logout command, a reset and a login over an existing login of that client SHALL say, before they log out, that this is unverified. A token-file login and logout touch only the token file, so no such check applies to them, and their messages carry no such caveat.
- **Status.**
  - It SHALL make no model call.
  - It SHALL print only:
    - the home's path;
    - whether the home carries its marker;
    - whether the home is logged in; for Copilot, whether the token file is present;
    - the auth method and, for Claude, the API provider; for Copilot, the auth type the status read reports, and whether the host is GitHub's public host;
    - for Claude, whether the host reports the home as its configuration directory;
    - whether the home is clean, naming any offending entry; for Codex, also whether its configuration equals the pinned one; for Copilot, also whether its settings equal the pinned ones;
    - for Claude, how long the access token remains valid; for Codex, how long ago its stored login was last written, by login or refresh;
    - for Codex, the installed CLI version against the pinned minimum, and whether the feature allowlist holds;
    - for Copilot, the installed CLI version against the pinned version, whether the OS sandbox is available, and, on Linux, the kernel's ptrace scope;
    - for Codex, the last quota snapshot the home keeps and, only on request, a fresh plan quota from the client's rate-limit read;
    - for Copilot, from the status read: the plan class, whether billing is token based, the chosen snapshot's overage permission, overage count, overage entitlement and remaining percentage, and the reset date;
    - for Codex, whether an isolation stop is recorded, and its cause;
    - for Copilot, whether a stop is recorded, and its kind and cause;
    - for Copilot, what the operator's go still covers: nothing, the canary, or one skill run, and when it was given;

### Requirement: Readiness coverage
The fixture corpus SHALL test proportionate review in both directions with fixtures that differ only where the judgement under test differs:

- an **overblocking control**: a check-clean proposal whose substance tests pass while it leaves bounded execution decisions open — the compared models chosen at the thesis start by a stated rule with no version named, an optional expert assessment that no research question depends on and whose organisational arrangements are not stated, and a sample size to be fixed by a pilot;
- an **underblocking control**: the same proposal with one change, making a research question answerable only through access to a partner organisation that is still to be negotiated;
- a **convergence workspace**: the overblocking control's text beside an earlier review whose blockers that text resolves and which lists a clarify-early item about a passage the text leaves unchanged.

Each proposal fixture SHALL carry an `expected.json` encoding its check-clean state. Over them, dev-runner scenarios and registered Inspect tasks SHALL assert with pure verdict functions, each exercised by L0 tests without a model call: the overblocking control's review opens with the ready verdict, its blocker section holds no item, and its clarify-early section — the early-thesis agenda — holds at least one; the underblocking control's review opens with the needs-revision verdict and carries a blocker concerning the doubtful access; the convergence review opens ready, carries an earlier-round section marking the earlier blockers resolved, and lists no blocker about the unchanged passage; and a supervise run over the overblocking control produces feedback that opens with the ready tier, carries no numbered point, carries a clarify-early block of at most five items, and promises no meeting. A model-graded rubric SHALL judge the review each of the three review scenarios produces against the readiness classification: each blocker names its failed test and why it must be settled before approval, no blocker rests on an element merely being unspecified, each clarify-early item carries its deferral record, and no requirement exceeds the applicable guidelines. These scenarios run on the subscription dev runner; a metered run of the Inspect tasks is a separate cost-gated decision.

#### Scenario: Overblocking caught

- **THEN** the readiness verdict fails without model involvement

#### Scenario: Underblocking caught
- **WHEN** the review of the underblocking control opens with "ready"
- **THEN** the dependency verdict fails without model involvement

### Requirement: Handoff coverage
The harness SHALL test the stage handoff in conversations, including the two failures that motivated it: a user left to ask what to do with feedback, and a review that no longer covers the text being announced instead of a fresh one being recommended.

- **Follow-up turns**: a dev-runner scenario MAY list follow-up user turns. Each SHALL be sent to the same host session in the same workspace and the same configuration, under the same budget cap — which the host applies to the session's running total, so the conversation as a whole stays within it — with every billing and account-surface check applied per turn. A first turn whose stream carries no session identifier SHALL end the run as a runner failure, never as a single-turn pass. The verdict SHALL read the final turn's chat; the transcript of every turn SHALL be saved with the run.
- **Format verdict**: a pure function in the shared verdict module SHALL check the closing lines of a chat in English and German: exactly one position line, exactly one next-step line, at most two alternatives (as lines, or as list items under one empty alternative label; a list under any other label continues that label's line), none of them empty, no text after them, no skill identifier and no skill named as one in them, and a length cap. It SHALL be exercised by L0 tests without a model call. Every dev run SHALL report it as an advisory field that never changes the exit status.
- **Scenarios** on the subscription dev runner, each asserted with pure verdict functions:
  - a review followed by the turn "What do we do now with that feedback?" — the final chat passes the format verdict and the proposal is byte-identical after both turns;
  - a narrowed draft beside a review of its broader predecessor, asked where it stands — the first sentence of the next-step line recommends a fresh review, not merely mentions one, with a phrase to send; a sentence about the review says it judged an earlier version; and the proposal and review files are byte-identical;
  - a draft beside a review with a blocker, asked where it stands, then the approval of the revision with the decision it needs — the revision ran under the writing skill's instructions, the proposal changed, the review file is byte-identical, the check reports no errors, and the next-step line recommends a fresh review with a phrase to send;
  - the same draft and review, with a single cold request to apply the review's blocker that carries the decision it needs — the same assertions without a status turn, the writing skill loaded although no handoff led there;
  - a draft beside a current ready review, asked what comes next — no file is added or changed, and the next-step line recommends the final check or the hand-in build with a phrase to send, recommends no further review, and makes none of the review's clarify-early items a step;
  - a complete draft with two decision markers and three execution-detail markers, asked where it stands — the proposal is byte-identical and the chat passes the format verdict.
- **Rubric**: a model-graded rubric SHALL judge each scenario's transcript against its fixture's `semantic` list: the position is stated accurately, the recommended step is the one that unblocks the next milestone and its reason is given, a superseded review is recognised and a fresh one recommended, a decision step quotes the student's text and offers options from the student's material with a way out, nothing was done unasked, and no checklist is repeated. Its grades are dev-runner L2, not comparable to matrix results.
- **Routing**: the routing dataset SHALL carry the status moment — where a proposal stands, what to do next — expecting the check skill, and the canonical continuation phrases the handoffs suggest, each expecting the skill that owns the step.
- **Fixtures**: every new proposal fixture SHALL carry an `expected.json` oracle calibrated against the mechanical check.

Inspect twins and matrix cells for these scenarios are a separate, cost-gated decision.

#### Scenario: Follow-up turn sent to the same session
- **WHEN** a scenario lists the follow-up "What do we do now with that feedback?"
- **THEN** the runner sends it to the session the first turn opened, in the same workspace, and the verdict reads the reply to it

- **THEN** the run ends as a runner failure naming the missing identifier

- **THEN** the format verdict fails and names the skill identifier

#### Scenario: Advisory probe on an unrelated scenario
- **WHEN** a check-report dev run's chat ends without handoff lines
- **THEN** the summary reports the format verdict as failed and the run's exit status is unchanged

#### Scenario: Silent revision after "what now"
- **WHEN** the reply to "What do we do now with that feedback?" edits the proposal
- **THEN** the scenario verdict fails because the proposal is no longer byte-identical

### Requirement: Dev-runner host adapters
The dev runner SHALL drive the model under test on one of its host CLIs, selected per invocation. Its hosts are:

- Claude Code, the default;
- Codex, under the operator's ChatGPT plan;
- GitHub Copilot CLI, under the operator's Copilot plan.

An invocation that selects no host SHALL keep every behaviour of the Claude runner as it was before this requirement, with two additions: its summary records the host and the host's label, and a summary-log path inside the directory the support report reads is refused (requirement: Inverted-hybrid runners). No host but Claude has an ambient mode. Every Codex run executes in the Codex harness home, and every Copilot run in the Copilot harness home (requirement: Harness-owned host logins).

**One core.** Every host SHALL share:

- the scenario set and the workspace staging;
- the L1 verdicts;
- the summary and its exit statuses;
- the saved event stream;
- the re-grading of kept workspaces;
- the judge machinery.

Five parts SHALL differ per host, each behind one adapter per host: the host's command, its run, its stream readers, its isolation and its login. No second runner SHALL copy the shared core. Each run's summary SHALL record its host.

**Canonical tool calls.** The verdicts and the route reader SHALL see tool calls under one set of names on every host. The completed items of a Codex stream SHALL be read as follows:

- a shell command as `Bash`. When the command reads the `SKILL.md` of a `proposal-*` skill, it is also read as a `Skill` call naming that skill;
- a file change as `Edit`;
- a subagent spawn as `Agent`, carrying the spawn prompt;
- an MCP tool call as `mcp__<server>__<tool>`;
- a web search as `WebSearch`.

The tool events of a Copilot stream SHALL be read as follows:

- a call of a shell tool as `Bash`;
- a file creation, edit or patch as `Edit`;
- a file view as `Read`. A view of the `SKILL.md` of a `proposal-*` skill is also flagged as a skill-file read, but is not a `Skill` call;
- a file-pattern search as `Glob`, and a content search as `Grep`;
- a call of the client's skill tool as a `Skill` call naming the requested skill, without a plugin prefix. A call whose completion reports failure is an attempt, not an invocation;
- a call of the client's task tool as `Agent`, carrying its prompt;
- a web fetch as `WebFetch`, and a web search as `WebSearch`;
- an MCP tool call as `mcp__<server>__<tool>`.

The client's internal bookkeeping tools are not tool calls. A tool name that is neither offered to the run nor one of those internal tools SHALL make the run untested.

**The model on Codex.**

- A Codex run SHALL require the model on the command line and pass it on unchanged. It SHALL refuse a provider-qualified identifier before staging.
- The registry SHALL hold no Codex role, the runner SHALL supply no default model, and the model-currency check SHALL raise no alert for Codex.
- A reasoning effort MAY be requested, from the host's explicit levels, but never the level that hands work to subagents.
- The effort the host served SHALL be recorded, as the session record's turn context names it, and as "unreported" where it names none. A requested effort that the host did not serve SHALL make the run untested.

**The model on Copilot.**

- A Copilot run SHALL require the model on the command line and pass it on unchanged. Before staging, it SHALL refuse a provider-qualified identifier and the client's automatic model selection.
- The registry SHALL hold no Copilot role, the runner SHALL supply no default model, and the model-currency check SHALL raise no alert for Copilot.
- Before the run, the run SHALL be refused as untested when the client's model listing does not offer the model, or offers it under a policy other than enabled. Remedy: enable the model in the account's Copilot settings, or name another model.
- A reasoning effort MAY be requested, but only one that the listing reports for the model. Any other is refused before the run.
- The run SHALL be untested, naming both models, in any of these cases:
  - a top-level message was served by a model other than the requested one;
  - the session reports usage by another model in a scenario without a helper allowance;
  - the client switched the model because of a rate limit.
- The summary SHALL record as the served model the models the top-level messages and the per-model usage name, or "unreported" when they name none. The session's record of its creation options SHALL never count as evidence of the served model or effort.
- A requested effort that the client reports as left unapplied SHALL make the run untested. Until a recorded run pins the event that reports it, the summary SHALL say that the effort was requested and not verified.

**Invocation on Codex.** A Codex run SHALL:

- run the host's non-interactive mode with its JSON event stream, the prompt on standard input, and the workspace as its working root. The workspace lies outside any git repository;
- validate its configuration strictly, so that an unknown configuration key fails the run rather than being ignored;
- sandbox the run to the workspace. Network access is granted only to scenarios that need it: those whose skill or sibling skills include import, literature search or reverse, and those that serve a fixture over localhost;
- enable subagents only for scenarios that declare a helper allowance;
- disable every other host feature that is on by default and adds a tool, a surface or reach beyond the shell and the workspace, through the host's validated feature switch. A default-on feature that adds none of these MAY stay on only when the allowlist names it with its reason. Before the run, it SHALL refuse when the host's feature listing still shows a feature enabled outside that allowlist; a feature the listing marks as removed and reading enabled SHALL be ignored by that check only when a pinned list of removed features measured reading enabled names it, and no feature the run disables is on that list. A listing row is a name, a stage of one or more words and an on/off state; the run SHALL refuse on any listing line it does not read that way, or whose stage is not one the host is known to print;
- keep the host's session record while the run lasts, read it after the run, and then delete it.

**Invocation on Copilot.** A Copilot run SHALL:

- run the client's prompt mode with its JSON event stream, streaming off and colour off. It starts a new session under an identifier the harness chooses, for which no session folder may already exist in the home. The workspace is the working directory and lies outside any git repository;
- carry the client's AI-credit cap (requirement: Copilot plan billing guard) and the flag that runs its shell in the OS sandbox;
- offer only an allowlisted tool set, chosen per scenario:
  - every run gets the shell and skill tools and the client's internal bookkeeping tools, and none of the client's own file or search tools: at the pinned version those refuse every path under an entry of the sandbox's deny list, the workspace included, which always lies under one, and a grant for the workspace does not lift that refusal. Every file read, search and write goes through the sandboxed shell, which the sandbox grants the workspace;
  - the task and agent tools are offered only to scenarios that declare a helper allowance;
  - the web-fetch tool is offered only to scenarios that need the network, the same scenarios the Codex invocation grants network access. It comes with a URL approval for each host the scenario needs: a served fixture's local host, and the hosts its skills' scripts contact. No run approves every URL;
- approve every offered tool without prompting, and deny memory, the built-in GitHub MCP server, the GitHub CLI in the shell, and `git push`;
- disable, from the command line:
  - the built-in MCP servers, custom instructions and questions to the user;
  - remote sessions and their export;
  - login from stored or GitHub CLI credentials;
  - auto-update, the shell's start-up file and the temporary-directory grant;
- name the token variable as the one credential the client reads, since disabling automatic login also leaves an unnamed environment token unread at the pinned version;
- mark the token variable as a secret, and write its logs into the Copilot log directory the sandbox's deny list names, never into a scratch directory the client would grant to the sandbox; the runner scans and empties that directory after the run, and never saves a log (Sandbox on Copilot);
- never pass an extra directory, a plugin directory, approval of every path, memory, sharing, a custom agent, or a resume or continue option;
- after the run, read the session's event file in the home, and then delete the session's folder. Among what it keeps, scrubbed, is each permission request the client raised and its outcome: the request's kind, the access kind and paths it named, and the result's kind, never the command text, so that a call the client's own permission check refused can be read from the kept events.

**Isolation on Codex.** A Codex run SHALL see only the skills under test, installed in the workspace where Codex discovers repository skills. Its home directory and XDG base directories SHALL be scratch directories belonging to the run, so the operator's user-scope skills, shell start-up files and key files are not visible to it. After the run, it SHALL count as untested in either of these cases:

- its session record lists a skill outside the workspace's skill directory, or one whose location it does not resolve, or shows a call of the host's cloud-skill tools. A location given as a root alias resolves only through the root table of the same skills block, and only to an absolute directory. A location given as an absolute path is read as it is. Any other location counts as unresolved;
- its stream shows an MCP tool call. The home configures no MCP server, so any call is foreign.

After the run, before the runner reads or writes anything in the workspace, it SHALL check that the workspace is still the directory the run started in and holds no link, no FIFO, socket or device, and no file with a second name elsewhere: the sandbox lets the run write the workspace, and a link it makes there never touches its target, so the runner, which is not sandboxed, would otherwise act on the target. The check SHALL fail closed: the workspace and every directory in it must still be open to their owner for reading, writing and search, and every entry must be examinable, because a directory the runner cannot list would hide a link from the check while the runner could still open a fixed name in it. Each such entry SHALL be removed without being followed, a directory closed to its owner is left as it is and never reopened, and the run SHALL be untested for isolation with an isolation stop recorded in the Codex home; no verdict reads its files. While that stop is recorded, every later Codex run SHALL be refused as untested for isolation before any Codex process starts, naming the stop's cause and its one remedy: reading the run's findings, then clearing the stop with the login command's clear option (requirement: Harness-owned host logins). A stop record that cannot be read SHALL count as a recorded stop. The status command reports the stop and is not refused by it.

**Isolation on Copilot.** A Copilot run SHALL see only the skills under test, installed under `<ws>/.agents/skills/`. That is the project skill directory a student's folder install writes, where the client lists the skills as project skills. Its home directory and XDG base directories SHALL be scratch directories belonging to the run.

The workspace, the run's scratch directories and every scratch directory of a Copilot call SHALL lie in the Copilot work directory, never in the system temporary directory, because the sandbox denies that directory and the operator's other processes keep their files there. The work directory is under the harness state directory where that lies outside the operator's home directory, the repository and every temporary directory; otherwise under the per-user runtime directory, where that is a directory only the user may enter. With neither, every Copilot run SHALL be refused as untested for a precondition, naming both, and nothing is created. The state directory's location check comes first. Each of these directories is owner-only, and each is deleted after its run or call unless the workspace is kept.

Before the run, and without a model call, it SHALL be refused as untested in any of these cases:

- the workspace lies inside the operator's home directory, inside the repository, or inside a temporary directory the sandbox denies;
- the workspace, or any of its parent directories up to the filesystem root, holds a skill directory other than the staged one, or an instruction, agent, rule, hook, MCP or client settings file that the client reads;
- a machine-wide managed settings file of the client exists;
- the client's skill listing, taken in the run's environment and working directory, names anything other than the staged skills and the client's bundled skills;
- the client's MCP listing names a server outside the built-in names pinned for the CLI version, or one whose source is not built-in.

After the run, it SHALL count as untested in any of these cases:

- the skills it loaded cannot be confirmed. A loaded-skills report that reaches its stream SHALL equal the listing. The pinned version emits that report before its prompt mode's stream starts and never records it, so without it the confirmation SHALL rest on positive evidence the run recorded, never on the report's absence: the skill listing taken before the run (above), recorded with the staged skills, names every staged skill and nothing but staged and bundled skills; the session record was read; and it carries no skill record of a kind the runner does not read. A missing listing or session record SHALL say that the loaded skills could not be confirmed;
- a skill record in its session record, an invocation or a delivery of skill context, names no skill of the listing, or names a source other than the workspace's project skills or the client's bundled skills, or a project skill's file other than its own `SKILL.md` in the workspace's skill directory;
- its stream shows an MCP tool call, or reports an MCP server as connected;
- its session record shows a hook event.

**Sandbox on Copilot.** Only the client's OS sandbox confines the model's shell. A Copilot run SHALL therefore run under it, with the home's pinned sandbox settings (requirement: Harness-owned host logins). When the sandbox cannot start, earlier client versions only warned that it was ignored and ran the shell unconfined, and the pinned version warns and fails sandboxed commands; no personal setting turns either into a refusal, so the runner checks confinement before the run, while it lasts and after it. At the pinned version the client's prompt mode reads the home's sandbox settings and applies them to its session itself, while its headless server applies them to no session it creates. The client also ignores its sandbox flag outside experimental mode, which the pinned settings keep off, so the run's sandbox comes from the home's pinned settings alone; the notice it prints for the ignored flag is not a sandbox warning. The runner SHALL:

- refuse to start on Windows with a usage error, because the sandbox cannot enforce its deny list there;
- refuse the run as untested when any tool the platform's sandbox needs, as the pinned package names them, is not installed. Remedy: install the named tool;
- on Linux, refuse the run as untested for a precondition, before the status read, when the kernel's Yama ptrace scope is missing, unreadable or below one (requirement: Harness-owned host logins). The harness reads the scope and never writes it, nor any other system setting: every guard of this requirement lives in the harness's code and its own state directory, and a part specific to Linux applies on Linux only, every other platform keeping its behaviour;
- before every run, and without a model call, run a confinement probe in a session that carries the run's sandbox settings. The probe SHALL first read the sandbox settings the client reads from the home, and refuse the run as untested for isolation unless they equal the pinned ones; it SHALL then apply them to its session the way the client's prompt mode does, and refuse the run as untested for isolation when that fails or is not confirmed. No probe command runs in a session those settings were not applied to, and the message never echoes the settings. Its commands are fixed in the harness; each discards its own output and reports only whether its target was denied or readable, or its exit code. The run SHALL be refused as untested for isolation when the probe can read the token file, the environment of the harness's own process, the operator's GitHub CLI configuration or SSH directory, or can obtain the GitHub CLI's token through the per-user session bus or a credential for GitHub from git run with the operator's own home and configuration, or when its shell's own environment carries the token variable or a GitHub CLI token variable, or when the client does not report every probe command as sandboxed. It SHALL also be refused as untested for isolation when the probe's shell finds a token in any process environment, thread environment or command line it can read: an entry that sets the token variable or a GitHub CLI token variable, or a GitHub token prefix followed by a token's characters. That search reads by content, never by a process identifier of the host, because the sandbox has a process namespace of its own whose first process, the sandbox's init, holds the environment the client started it with; its own command line, and that of every program it runs, SHALL never match it; it reports one word, never a match; and a search that cannot complete SHALL refuse as well. Every Copilot run's probe runs it, a skill run's included. The run SHALL also be refused as untested for isolation when the probe's shell can read a file the harness put in either of the host's shared temporary directories, `/tmp` and `/var/tmp`, or can write one into `/tmp` that the host then sees; a write the shell reports as done but the host never sees, because it landed in the sandbox's own throwaway layer, is denied, so the harness judges that row on the host, and only once the row's command has printed its exit code: a row whose command never ran is unanswered, not denied. It SHALL be refused as untested for a precondition when the probe cannot run the skills' interpreter in the workspace, because the deny list would then fail the skill rather than confine it. Where the pinned settings keep the staged skill tree read-only (requirement: Harness-owned host logins) and a skill is staged, the probe's shell SHALL also try, over one staged skill file, to rename the workspace's `.agents` directory aside, to make a file in it and to put a link over that skill file, undoing at once a rename or a file that succeeded; the run SHALL be refused as untested for isolation when any of the three succeeds or the shell does not see the staged file, the message naming the staged skill tree and never the row's word, and as untested for a precondition when that row has no answer. The probe SHALL also report, without refusing, whether its shell shares the harness's network namespace;
- write the process logs of the probe's server and of the run, the two children whose sessions the client sandboxes, into the Copilot log directory, which the deny list names exactly, because the client grants its log directory to the sandbox after the masks of its denied ancestors. That directory SHALL be the user's own and open to no one else before either child starts; anything else at its name, a link included, refuses the run as untested for a precondition, and the runner never enters it. After the probe, and after the run beside the workspace's scrub, the runner SHALL read every entry there without following a link, count as a finding the token's value, a GitHub token prefix followed by a token's characters, and any entry that is not a plain file or cannot be read, and then remove every entry. A finding after the probe refuses the run as untested for isolation before its prompt-mode child starts; a finding after the run makes it untested for isolation and records an isolation stop (requirement: Copilot plan billing guard). The message counts the entries and never quotes one;
- while the run lasts, read its event stream and its error output as they arrive, and stop the run at the first shell call the client does not report as sandboxed (for a call that ran, sandboxed with the sandbox applied), at the client's warning that the sandbox did not engage, at the first call of the client's file tools whose path, with links resolved, leaves the workspace, or at a call of the client's skill tool while the staged skill tree holds a link or another entry the runner must not follow, so that a run whose shell is not confined does not go on with the skill prompt. The read-only staged tree keeps the shell from planting such an entry on Linux; this check, and the staged tree's fingerprint after the run, stay as the guard where it does not. The run is then untested for isolation, its message names the stop, and an isolation stop is recorded (requirement: Copilot plan billing guard). Prompt mode applies the sandbox settings itself, so a run is where its confinement is first observed; the probe shows the same settings, applied the same way but before the client's own resolution of them, confining the shell. Whatever ends a Copilot child, the runner SHALL stop every process left in the child's process group;
- after the run, before it reads, scrubs or writes anything in the workspace, check that the workspace is still the directory the run started in and holds no link, no FIFO, socket or device, and no file with a second name elsewhere: the sandboxed shell may write the workspace, and a link it makes there never touches its target, so the runner, which is not sandboxed, would otherwise act on the target. The check SHALL fail closed: the workspace and every directory in it must still be open to their owner for reading, writing and search, and every entry must be examinable, because a directory the runner cannot list would hide a link from the check while the runner could still open a fixed name in it. Each such entry SHALL be removed without being followed, a directory closed to its owner is left as it is and never reopened, and the run SHALL be untested for isolation with an isolation stop recorded; no verdict reads its files. The event stream file SHALL be created afresh on every host, never written through an entry the run left at its name;
- count the run as untested for isolation, and record an isolation stop (requirement: Copilot plan billing guard), when its stream or session record carries the client's warning that the sandbox was ignored, or lacks the client's report that the sandbox is active. Until a recorded run confirms which event reports it, the runner uses the event the pinned package's source names. Every shell completion SHALL be reported as sandboxed, and a completion that shows its command ran, with a result and an exit code, SHALL also report the sandbox applied to it, as the canary requires of its own call. Only such a completion counts as the report that the sandbox is active: a shell call the client refused before any shell ran it, by its own permission check, reports the sandbox field as well, and a run whose shell calls were all refused that way has confirmed nothing; the message then names the refusal as the client's, not the sandbox's, and points to the kept permission records.

Limiting the sandboxed shell's network per scenario is not part of this requirement.

**Canary on Copilot.** The first model call after the operator's go SHALL be a canary run, which confirms the sandbox the client's prompt mode resolves and applies, and the skill run the go covers SHALL follow only once that canary has passed; the runner enforces the order through the go it records (requirement: Copilot plan billing guard, the go). The canary is no eval scenario: no verdict, judge or support report reads it. It SHALL:

- run on Copilot only, with a model named on the command line and exactly the minimum credit cap; any other cap, another host, a judge, a re-grade or the no-skill baseline is a usage error;
- run in a workspace in the Copilot work directory that holds nothing but the canary's script and a placeholder skill, and offer the shell tool alone. The harness stages the placeholder before anything reads the workspace, so that the probe and the canary have a staged skill tree to try the read-only tree's row on; it carries no instructions and no script, the client lists it as the workspace's one project skill, and the canary, offering no skill tool, never loads it. A workspace that refuses it refuses the canary as untested for a precondition before any Copilot process starts;
- carry every other part of a skill run's invocation, apart from the denial of the GitHub CLI in the shell: a permission rule above the sandbox, which measures nothing about it, and which could refuse the whole script on its GitHub CLI command should the client's permission checks read inside the script;
- pass every check before the run that a skill run passes, the confinement probe among them, and run under the same live watch and the same checks after the run;
- under the run lock, write the confinement probe's fixed commands into a script in the workspace, readable by its owner alone, that runs each command, prints one tagged line per command carrying the command's name and its one word, and closes with a closing line; and record the script's digest. The search for a token in the environments and command lines its shell can see is the probe's own, by content, so the probe's run of the script before the child (below) already reads the probe server's sandbox init, which holds the real token. Where the pinned settings keep the staged skill tree read-only, the script carries the probe's staged-tree row over the placeholder's skill file, which is the first reading of that read-only tree under prompt mode, and a canary without that row's answer is untested for a precondition;
- before its child, under the same lock hold, run that script once, with the one fixed command, through the confinement probe's sandboxed session, and remove it before the canary writes its own. The canary SHALL be refused as untested before any model call, for a precondition, when that run does not print every row's tagged line and the closing line, or takes longer than a limit set below the shell tool's own time limit; and for isolation when its rows do not read as the probe requires or it is not reported as sandboxed. That session skips the client's own permission check, so this run says nothing about it;
- prompt the model to run one fixed command, which runs that script by a name relative to the workspace and carries no absolute path, quoting, escaping, variable or line break, exactly once with the shell tool, and nothing else;
- read each row from the client's own completion of that one shell call, never from the model's reply. The completion counts only when the client reports that the call ran to its end: successful, with no error, a result and an exit code of zero. A row counts as answered only when that completion carries its tagged line exactly once, with a word of the probe's vocabulary, and the closing line; any other row is unanswered and never passes. An answered row's sandbox report is the completion's, true only when the completion is reported as sandboxed with the sandbox applied, and a row not so reported fails the canary for isolation. The write into the host's shared temporary directory is judged on the host, and only once its row is answered.

It SHALL pass only when the run has no finding a skill run's checks would make, apart from the confirmation of its loaded skills, which it records instead; when the fixed command ran exactly once, verbatim, and no other shell call ran, because a canary that ran anything else measured something else; when the script still has, after the run's workspace check, the digest recorded before its child started; when every row is answered and reads as the probe requires; when its shell's network namespace reads as its own, not the harness's, a shared, unknown or unanswered namespace failing it until a network rule has been decided through a reviewed change; when every shell completion is reported as sandboxed; when no sandbox warning appeared other than the client's notice that its sandbox flag is ignored; and when the billing guard still passes on the status read after the run. Any outcome after its child started other than a pass is untested and records a stop (requirement: Copilot plan billing guard) naming the finding: a billing stop for a billing finding, an isolation stop otherwise, which names the network-namespace reading when that reading failed it and, for an unanswered one, why it is unanswered. A canary refused before its child starts records no stop, and its go's canary stays unpassed. A fixed command the model skipped or altered leaves every row unanswered, and so does a completion the client refused before any shell ran it. The summary SHALL name each row with its result and its sandbox report, the fixed command's state (ran; refused by the client's permission check before any shell ran it; or not run to its end, and why), each shell call that matched no fixed command or repeated one (its command, cut short), whether the ignored-flag notice appeared, and, for the client's loaded-skills, loaded-servers, session-start, result, shutdown, skill-invocation and tool-completion events, whether each reached the stream, the session record, both or neither.

### Requirement: Copilot plan billing guard
A Copilot run SHALL draw only on the included AI credits of the operator's Copilot plan, and nothing else. The account keeps money out: the operator keeps a budget of zero on the account's AI-credit usage with its "stop usage" setting on, and never deletes it, because a product with no budget has unlimited usage. The checks below are the backstop, and each one fails closed. A run that any of them refuses:

- is untested and exits with the untested status. The one exception is a run whose session record holds no shutdown record, which is a runner failure (requirement: Dev-runner cost and helper-agent telemetry) and still records a billing stop;
- starts no further Copilot process;
- is reported in the one refusal template (requirement: Harness-owned host logins).

**Stops.** Some findings are not settled by the next run's checks. For each of them the runner SHALL record a stop in the harness home, naming the cause and the time. A stop is one of three kinds:

- **A billing stop**, for a finding after a run that shows the run may have drawn more than its bound. The cases are listed under "After every run". Its one remedy is checking the account's billing page and then clearing the stop.
- **An isolation stop**, for a run whose sandbox was ignored or not reported active, a run stopped at a shell call not reported as sandboxed, a run whose output or process log carried the token's value, a run whose process log carried a GitHub token, or a canary that did not confirm the sandbox (requirement: Dev-runner host adapters). Its one remedy is reading the run's findings and then clearing the stop.
- **The approval stop**, which the login command records whenever it writes a token file, a reset included, and which the runner records again once the skill run a go covers has started (below). It holds back the next model call until the operator gives the go. Its one remedy is clearing the stop, which is that go.

While a stop is recorded, every later Copilot run SHALL be refused before any Copilot process starts. The refusal names the stop's cause and its remedy. A stop record that cannot be read SHALL count as a recorded billing stop. Only the operator clears a stop, with the login command's clear option or a reset; a reset records a new approval stop. Both carry the login command's terminal and agent-marker refusals (requirement: Harness-owned host logins). A stop SHALL NOT refuse the status command or the preflight-only option (requirement: Dev-runner host adapters), which make no model call; both report it.

**The go.** Clearing a stop with the login command's clear option is the operator's go, and the clear option SHALL record it in the harness home, with no stop recorded too. A go covers one canary (requirement: Dev-runner host adapters) and, only once that canary has passed, one skill run, in that order. The runner SHALL refuse as untested for a precondition, before any Copilot process starts and again once it holds the run lock: any Copilot model call while no go is recorded; a skill run while the go's canary has not passed; and a second canary once it has. A canary that passes SHALL be recorded in the go, with its time and session identifier. A canary that does not pass leaves the go's canary unpassed, whether it was refused before its child started or found wanting after it, so the skill run stays refused. Recording a stop of any kind ends the go. Once a skill run's prompt-mode child has started, the runner SHALL record the approval stop again, which ends the go, so every later model call needs a new go and, after it, a canary that passes first. The status command and the preflight-only option report what the go still covers and are not refused by it.

**Environment.** These Copilot children are covered: the run, the version check, the status read, the confinement probe, and the skill and MCP listings. Each SHALL receive one final environment. The same function that builds the isolated Claude child's environment builds it from the Copilot record (requirement: Isolated child environment), and the token is added after that function. That requirement's allowlist, configuration-directory variable and account-surface variables govern Claude children only; this requirement prescribes the Copilot child's environment. The one exception is the status command's on-request read without the token (requirement: Harness-owned host logins), whose child receives the same environment less the token variable. It holds:

- only the machine plumbing the allowlist admits, without the Claude long-lived token, plus a dumb terminal type and the no-colour switch;
- the Copilot home variable, set to the harness home;
- the client's package-cache variable, set to a persistent cache directory that the harness owns outside the home;
- the client's auto-update switch, set to off;
- the home directory and the XDG base directories, the runtime directory among them, set to scratch directories belonging to the run or the call;
- the session-bus address, set to a disabled value rather than dropped. The GitHub CLI's bus library falls back to the fixed per-user bus when the variable is empty, and the operator's keyring is reachable there;
- the GitHub CLI's configuration-directory variable, set to an empty directory in the home;
- the token variable, `COPILOT_GITHUB_TOKEN`, read from the token file (requirement: Harness-owned host logins).

Every inherited variable whose name begins with `COPILOT_`, `GITHUB_`, `GH_`, `CAPI_`, `OTEL_`, `OPENAI_`, `ANTHROPIC_` or `AZURE_OPENAI_`, or ends in `_TOKEN` or `_API_KEY`, SHALL be dropped. So SHALL `BASH_ENV` and `SSH_AUTH_SOCK`. The run's summary SHALL name the dropped variables, never their values.

Immediately before starting any Copilot child, the harness SHALL check again the final environment that child will receive, after every variable the harness sets has been applied. It SHALL refuse to start the child in either of these cases:

- the environment carries a variable of the dropped families that the Copilot record does not set itself and that is not the token variable;
- it carries a token-shaped variable other than the token variable. A variable is token-shaped when its name ends in `_TOKEN` or `_API_KEY`, or when its value begins with a GitHub token prefix.

The refusal names the variable, never its value. The reason: an environment token outranks every other credential in the client, so a leaked one would bill, and act, as whichever account owns it. A provider variable would route the run to a third-party key.

**Status read.** The runner SHALL read the account's state through the client's own headless server mode: its current-authentication call and its model listing. Neither makes a model call. It reads the state before every run and again after it, under one hold of the run lock (requirement: Harness-owned host logins).

- It SHALL read the raw quota snapshots the client receives, never the client's mapped quota values, which turn a missing field into "no overage".
- It SHALL choose the snapshot as the client does: the chat snapshot when the access SKU names the free limited plan, otherwise the premium-interactions snapshot.
- It SHALL keep only these values:
  - the auth type and host, and the number of auth errors;
  - the plan, the access SKU, whether billing is token based, and the quota reset date;
  - the chosen snapshot's overage permission, overage count, overage entitlement, remaining percentage, and has-quota and unlimited flags;
  - each listed model's identifier, policy state and supported efforts.
- The raw reply SHALL never be stored or logged, a refusal for a runner bug included, because it carries the token, the login and the organization list.
- The reader's child SHALL write its process log to a scratch directory of the call, which is deleted with it, never into the home. The confinement probe's child, whose session the client sandboxes, SHALL write its process log into the Copilot log directory instead, which the sandbox's deny list names (requirement: Dev-runner host adapters, Sandbox on Copilot).
- The reader's child SHALL carry the run's credential flags: automatic login off, and the token variable named as the one credential the client reads. At the pinned version, automatic login off also leaves an unnamed environment token unread, so a read without the name reports no login. The read thereby validates the token exactly as the run will use it. The on-request read without the token names no variable.
- Every other Copilot child, the version check and the skill and MCP listings included, SHALL carry automatic login off as well, and, when it carries the token, the token variable named; a command with a subcommand takes both before it.

Before the run, the runner SHALL refuse in any of these cases:

- **The read is unavailable.** The reader cannot start, its handshake or a call fails, it gives no answer within a bounded time, or the answer carries no Copilot user record or no chosen snapshot. Remedy: report it, because the client's server interface does not match the pinned version.
- **A budget is possible.** The overage permission is missing, is not a boolean, or is true; or the overage entitlement is missing, is not a number, or is above zero. Remedy: set the account's AI-credit budget to zero with "stop usage" on, never deleting it, or, on an organization seat, ask its administrator.
- **Overage already drawn.** The overage count is missing or above zero. Remedy: check the account's billing page, and rerun after the reset date.
- **Legacy billing.** Billing is not token based. A legacy plan reports no consumption in credits, which would leave the credit cap unenforced. Remedy: report it.
- **Quota low.** The remaining percentage is missing or below 10, or the snapshot reports no quota. Remedy: rerun after the reset date.

The runner SHALL keep the last status snapshot in the harness home. It holds only the plan class, whether billing is token based, the chosen snapshot's overage and remaining values, the reset date, and any stop.

**Per-run bound.**

- Every Copilot run SHALL carry the client's AI-credit cap, which the operator names on the command line, at 30 credits or more. A run without it, or with less, SHALL be refused with a usage error before staging.
- The cap is soft: one model call can overshoot it. It is therefore not the hard per-run cap that a smoke task requires (requirement: Dev-runner host adapters).

**After every run.** The runner SHALL read the run's consumption, in credits, from the session's shutdown record, and it SHALL read the status again. The run SHALL be untested, and the runner SHALL record a billing stop, in any of these cases:

- the overage count grew, or appeared, between the two reads;
- the status read after the run is unavailable, so overage growth cannot be ruled out;
- the shutdown record carries no readable consumption;
- the run consumed more than twice its cap;
- the shutdown record reports zero consumption while the per-model usage reports tokens;
- the stream reports that the session limit or the credit cap was reached.

A check after the run that does not complete SHALL record a billing stop as well, after the token's value has been scrubbed from the workspace.

A session record that holds no shutdown record leaves the consumption unreadable. Such a run SHALL be a runner failure rather than untested (requirement: Dev-runner cost and helper-agent telemetry), and the runner SHALL record a billing stop for it as well.

A quota or rate-limit error SHALL make the run untested as a limit reached, not a result. The two reads compare overage only, never consumption, because the operator's other Copilot clients draw on the same pool outside the lock.

The summary SHALL report the overage count and the remaining percentage before and after the run, the cap, and the credits consumed.

**Never in CI.** No CI workflow SHALL use a Copilot token.

**L0 coverage.** L0 tests SHALL cover every check above. They run over event streams and status replies derived from the package of the pinned CLI version. Until a later change replaces them with reduced recordings, the fixture directory SHALL label each of these files synthetic and name the version and the source it follows.

### Requirement: Swap-test anchor coverage
The fixture corpus SHALL carry a minimal pair for the swap test's check of named choices. Both fixtures are synthetic and check-clean, and both are built from the readiness controls' text, so that the anchor is the only judgement that differs between them:

- the decorative-name review opens with needs revision and carries a proposal blocker whose text cites the swap test as failed and names the tool;
- the anchored-name review carries no enumerated finding, in any class, that cites the swap test as failed — an item saying the name passes the swap test, or that no swap-test finding applies, does not count;
- the decorative-name feedback opens with needs revision, carries a numbered point that names the tool and asks the replacement question — a question, direct ("what would change if …?") or indirect ("ask yourself what would change if …", "überlegen Sie, was sich ändern würde, wenn …"), carrying a contrast with a comparable alternative in the same sentence, so a point that only quotes a research question naming the tool does not count — and contains no mention of the swap test outside the closing note;
- the anchored-name feedback opens with the ready tier and carries no numbered point.

The L1 verdicts match test names, pass and failure cues, contrast cues and the tool name only. Whether a finding treats the named tool as replaceable under another test's name is left to the model-graded criterion. That criterion SHALL grade the two review scenarios against the fixture's `semantic` list. On the decorative-name review it checks that the blocker states what stays unchanged under replacement, offers both repairs, says why it cannot wait, and reports the name once even though the title also carries it. On the anchored-name review it checks that no finding treats the named tool as replaceable or decorative, under any test's name. These grades are dev-runner L2, not comparable to matrix results.

The scenarios SHALL run on the subscription dev runner. Inspect twins and matrix cells for them are a separate, cost-gated decision, and skill routing is not part of this coverage.

When the rule lands, the corpus's existing oracles SHALL be audited. A fixture whose title, purpose statement, research questions or contribution names a tool, system, platform or application domain SHALL have its `semantic` list say how the swap test judges that name where a review of it could otherwise be graded against the earlier rule. Its `check` block is unaffected, because the check is not mechanical.

#### Scenario: Decorative name caught
- **WHEN** the review of the decorative-name fixture opens ready, or none of its blockers cites the swap test and names the tool
- **THEN** the verdict fails without model involvement

#### Scenario: Anchored name blocked
- **WHEN** the review of the anchored-name fixture carries a finding that cites the swap test
- **THEN** the verdict fails without model involvement and quotes the finding

#### Scenario: Verdict that names the passing tests
- **WHEN** the anchored-name review's verdict line lists the swap test among the tests that pass, and no enumerated finding cites it
- **THEN** the anchored verdict passes

#### Scenario: Passing name mentioned in a refinement
- **WHEN** the anchored-name review carries a refinement saying the tool passes the swap test as the object of study
- **THEN** the anchored verdict passes

#### Scenario: Test name reaches the student
- **WHEN** the feedback over the decorative-name fixture says "swap test" outside the closing note, or its point on the tool asks the student nothing
- **THEN** the feedback verdict fails and names which property broke

#### Scenario: Quoted research question is not the replacement question
- **WHEN** the feedback's only point naming the tool quotes a research question that names it and ends in a question mark, about another issue
- **THEN** the feedback verdict fails

#### Scenario: Indirect replacement question
- **WHEN** the feedback's point on the tool asks the student, in imperative form and without a question mark, to consider what in the thesis would change if another framework stood in its place
- **THEN** the feedback verdict counts it as the replacement question, and the same imperative without a contrast cue in its sentence does not count

#### Scenario: Anchored name raised in the feedback
- **WHEN** the feedback over the anchored-name fixture opens with needs revision or carries a numbered point
- **THEN** the feedback verdict fails and quotes the tier phrase or the first point

#### Scenario: Pair stays check-clean and minimal
- **WHEN** the mechanical check runs over both fixtures and the offline suite compares them
- **THEN** each reports exactly what its oracle encodes, and the two proposal files differ only in the contribution's close

#### Scenario: Verdict logic covered without a model
- **WHEN** the new verdict functions' failure modes are tested
- **THEN** L0 tests call them directly on crafted review and feedback texts and no model is invoked

#### Scenario: Existing oracle audited
- **WHEN** the rule lands and a fixture's title names a platform that its research questions never use
- **THEN** that fixture's `semantic` list states that the name fails the swap test and is a blocker, and its `check` block is unchanged
