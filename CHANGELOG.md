# Changelog

Notable changes to the thesis-proposal skills, newest first. Format: [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); one [Semantic Versioning](https://semver.org/) number covers all eleven skills.

- **Major**: something you already have (a proposal, `guidelines.md`, a `proposal-build`, an install, a file a skill reads back) stops working or is read differently. Such entries start with **Breaking:**. Below 1.0.0 these raise the minor number.
- **Minor**: new skills, settings or checks, or stricter judgement.
- **Patch**: fixes and wording.

Installs and updates deliver `main`, which holds the latest release. Work in progress collects on `develop` under [Unreleased] until the next release fast-forwards `main`. Releases are tagged `vX.Y.Z` and stamped into each `SKILL.md` as `metadata.version`.

## [Unreleased]

_On `develop`, not yet released._

The suite gets this changelog and version numbers, and from now on installs receive released versions only. A proposal's files stay together under one name, a review records which research questions it judged, and a named tool or domain has to matter to the research. The scripts also run on Windows whatever characters they print, and the install guide says how to confirm that a setup works.

### Added

- This changelog says, per release, what changed for students, supervisors and workspaces; the suite's history since its first publication appears as releases 0.1.0 to 0.8.0, each tagged on the commit it describes. ([add-changelog](openspec/changes/archive/2026-10-14-add-changelog/))
- `proposal-review` ends each review with a `## Research questions reviewed` section that copies the proposal's numbered research questions verbatim, and `proposal-check` warns `review-questions-changed` once those questions have changed, so its status read treats a review that may describe an earlier version as superseded. ([mark-review-currency](openspec/changes/archive/2026-10-14-mark-review-currency/))
- `proposal-check` warns `companion-orphaned` when a review, kept files or other companion files carry a slug that has no proposal, notes file or harvest record, when a family file lies at the workspace root outside a configured proposal location, or when a figure link points under another slug; the workspace's own files are never reported. ([tighten-proposal-family](openspec/changes/archive/2026-10-14-tighten-proposal-family/))
- `docs/install.md` opens with what each kind of work needs (an agent app for writing, Python 3.11 or newer for checks and literature search, pandoc with typst or LaTeX for PDF export), says the proposals folder is never a clone of this repository, and gains "Is everything working?" checks and a "PDF export" section with a digest-checked fallback ([add-setup-readiness-guide](openspec/changes/archive/2026-10-14-add-setup-readiness-guide/)).

## [0.8.0] - 2026-10-13

_Retroactive release, tagged at 88247bf on 2026-10-14. Published 2026-10-13, together with 0.7.0._

Every skill now ends by saying where the proposal stands and what to do next. A review now counts a proposal as ready once nothing blocks a decision to supervise it, so repeated review rounds converge instead of adding requirements, and literature search passes DBLP's new verification page by itself or explains why it could not.

### Added

- Every skill closes with a handoff that says where the proposal stands (seeded idea, complete draft, ready for supervisor discussion, handed in), what blocks the next stage, and one recommended next step with at most two alternatives. Nothing is applied, built or sent unasked, and a decision only the student can make comes as up to three options from their own material. ([add-stage-handoffs](openspec/changes/archive/2026-10-13-add-stage-handoffs/), [sharpen-handoff-choices](openspec/changes/archive/2026-10-13-sharpen-handoff-choices/))
- `proposal-check` answers "where does my proposal stand?" and "what next?". It places the proposal on that ladder from the check result and from the review and notes files beside it, judges only whether the review still covers the current text, and stays read-only. ([add-stage-handoffs](openspec/changes/archive/2026-10-13-add-stage-handoffs/))
- The guidance gains a Readiness section that sorts every finding into a proposal blocker, an item to clarify early in the thesis, or an optional refinement. A finding may wait only when its deferral record can be filled, a proposal with no blocker is ready, and a workspace `guidelines.md` can still make an item block for its program. ([proportionate-readiness-review](openspec/changes/archive/2026-10-13-proportionate-readiness-review/))
- `proposal-lit-search` documents an optional, consent-bound browser route for a source the script could not get through. It uses the source's official API URL with public query terms only, merges results under the usual rules and reports them as coming through the browser. ([pass-source-verification](openspec/changes/archive/2026-10-13-pass-source-verification/))

### Changed

- **Breaking:** `proposal-review` writes `<slug>-review.md` as three sections instead of one severity-ordered list: `## Proposal blockers`, `## Clarify early in the thesis` and `## Optional refinements`, preceded by `## Earlier round` if an earlier review exists. Blockers set the verdict. Anything reading the old list needs adjusting; an older single-list review is still read as the earlier round. ([proportionate-readiness-review](openspec/changes/archive/2026-10-13-proportionate-readiness-review/))
- `proposal-review` reads its earlier review before overwriting it. Earlier blockers are judged resolved, partly resolved or open against what they asked for, a finding about unchanged text never moves to a higher class, and a new blocker needs changed text or the label "missed in the earlier round". Title, density and necessity findings no longer block on their own. ([proportionate-readiness-review](openspec/changes/archive/2026-10-13-proportionate-readiness-review/))
- `proposal-supervise` feedback carries up to five numbered points that block approval, and none on a ready verdict. A separate unnumbered block lists up to five decisions to settle early in the thesis and marks them as no condition for resubmission. An over-scoped plan counts as a review blocker, and the handoff goes to the professor in chat, never into `<slug>-feedback.md`. ([proportionate-readiness-review](openspec/changes/archive/2026-10-13-proportionate-readiness-review/), [add-stage-handoffs](openspec/changes/archive/2026-10-13-add-stage-handoffs/))
- `proposal-write` applies a review's blockers and refinements, records clarify-early items in the notes file's Open Points, moves execution-detail `[TODO: …]` markers to the notes file only on approval, and recommends a fresh review after a pass that changed research questions, scope, method, the contribution delta or a passage a blocker cites. ([proportionate-readiness-review](openspec/changes/archive/2026-10-13-proportionate-readiness-review/), [add-stage-handoffs](openspec/changes/archive/2026-10-13-add-stage-handoffs/))
- `proposal-lit-search` stops broad searching once the contribution delta and every research question have an accepted source, or once a round adds no accepted entry. The reference count alone never keeps a search going. ([add-stage-handoffs](openspec/changes/archive/2026-10-13-add-stage-handoffs/))
- The README's model-support table lists only current models, so Haiku 5.5 (untested) replaces Haiku 4.5; its note says polishing and bug-report requests may not reach `proposal-write` and `proposal-troubleshoot` and recommends Sonnet or Opus. Haiku 4.5's results stay in `docs/model-support.md`, marked disabled, and in the data `proposal-troubleshoot` uses to warn. ([readme-current-models](openspec/changes/archive/2026-10-13-readme-current-models/), [route-bug-reports-to-troubleshoot](openspec/changes/archive/2026-10-05-route-bug-reports-to-troubleshoot/))

### Fixed

- Literature search passes DBLP's new verification page by itself instead of failing with a cryptic JSON error, and keeps the cookie in memory only. A page it cannot pass gets a short diagnostic naming the cause, without the query or response; the run continues with the other sources, and `proposal-ideate` falls back to Crossref. ([pass-source-verification](openspec/changes/archive/2026-10-13-pass-source-verification/))
- `proposal-check` no longer flags an outcome phrased as an expectation ("the thesis expects", "it is hypothesized") as a forbidden expected result, because that is the form the guidance requires. ([add-stage-handoffs](openspec/changes/archive/2026-10-13-add-stage-handoffs/))

### For contributors

- The dev runner gains scripted follow-up turns (`claude -p --resume`), an advisory handoff-format verdict on every run, and handoff and readiness scenarios over new synthetic fixtures (`f28`–`f30`, `w09`–`w12`), each with deterministic verdicts and a rubric, so overblocking and underblocking are both tested. ([add-stage-handoffs](openspec/changes/archive/2026-10-13-add-stage-handoffs/), [sharpen-handoff-choices](openspec/changes/archive/2026-10-13-sharpen-handoff-choices/), [proportionate-readiness-review](openspec/changes/archive/2026-10-13-proportionate-readiness-review/))
- Routing-rig and dev-run records name the served model ID and CLI version. A changed served model marks an earlier routing score as not comparable, and a cited measurement must name the served model, not only the alias. ([label-served-models](openspec/changes/archive/2026-10-13-label-served-models/))
- `poe lit-live` runs one live DBLP query through the shipped script, outside `poe test` and CI, and exits 1 when DBLP's verification page can no longer be passed automatically. ([pass-source-verification](openspec/changes/archive/2026-10-13-pass-source-verification/))
- A push now needs confirmation at the maintainer's terminal (`.githooks/pre-push`), and `.claude/settings.json` denies `git push` to agents. Deferred follow-ups are tracked in `docs/backlog.md`, one line each, and each line is removed in the commit that lands its change. ([guard-push](openspec/changes/archive/2026-10-13-guard-push/), [add-backlog](openspec/changes/archive/2026-10-13-add-backlog/))
- The offline suite passes on Windows again: golden prompts are pinned to LF, extended-length link paths are stripped, and case-insensitive environments are modelled. The judge's child process now closes its pipes on every path, and a racy login test is deterministic. ([fix-windows-l0](openspec/changes/archive/2026-10-13-fix-windows-l0/), [fix-flaky-l0](openspec/changes/archive/2026-10-13-fix-flaky-l0/))

## [0.7.0] - 2026-10-06

_Retroactive release, tagged at bf57878 on 2026-10-14. Not published on its own: it reached users with the push of 2026-10-13._

Students can install the skills from a desktop agent app without a terminal, start an idea from a published paper, and have their drafts held to a sixth substance test and an attribution-scope rule for citations. `proposal-supervise` checks its claims against their sources and checks the size of the plan before a professor sees the feedback.

### Added

- An install prompt pasted into a local agent app checks for Python 3.11 or newer and runs the repository's own `install.py`, which installs for all projects or only the open folder, writes an install record (`.thesis-proposal-install.json`) and updates the skills when run again; `npx skills add` remains the terminal route (7385be1).
- In the Claude desktop app, a plugin marketplace (`.claude-plugin/marketplace.json`) that follows `main` installs all eleven skills in one step, and an institution on Claude Team, Enterprise or Education can provide it to a cohort; `docs/install.md` replaces `docs/getting-started.md` with per-app recipes, still marked unverified (7385be1).
- `proposal-ideate` can start from a published paper (a DOI or arXiv link, the PDF, or "a thesis similar to this paper"): it reads only the abstract, contributions, limitations, future work and conclusion, never turns the paper's future work into a topic menu, asks what the thesis changes relative to it, and adds the paper as a starter reference only from metadata fetched in the session. ([add-paper-foundation-entry](openspec/changes/archive/2026-10-06-add-paper-foundation-entry/), [refine-paper-foundation-entry](openspec/changes/archive/2026-10-06-refine-paper-foundation-entry/))
- A sixth substance test, necessity, fails a sentence, citation or technical term that serves no research question, the delta or the method, which may flag drafts that passed before. `proposal-lit-search` merges a reference only for a claim it can name, and `proposal-write` may move a reference no claim needs to Excluded Literature. ([guard-non-serving-material](openspec/changes/archive/2026-10-03-guard-non-serving-material/), [fix-substance-test-count](openspec/changes/archive/2026-10-05-fix-substance-test-count/))
- `proposal-check` warns `citation-repeated` when a sentence cites exactly the same sources as the sentence before it in the same paragraph, which may flag drafts that passed before; `proposal-write` drafts prior work concept-first and resolves the warning by restructuring, never by deleting a citation or a source. ([scope-citation-attribution](openspec/changes/archive/2026-10-04-scope-citation-attribution/))

### Changed

- The guidance replaces "stop repeating the citation" with an attribution-scope rule: cite a source once per continuous use in a paragraph, open with the author-in-text form, carry the attribution in words, and cite again at a new paragraph, a source switch or a claim of the thesis's own. ([scope-citation-attribution](openspec/changes/archive/2026-10-04-scope-citation-attribution/))
- `proposal-check`'s `hindsight-leakage` warning accepts an uncited sentence that continues a source's attribution run with a back-reference cue ("their evaluation", "they report"), in English and German. ([scope-citation-attribution](openspec/changes/archive/2026-10-04-scope-citation-attribution/))
- `proposal-supervise` checks every claim in the feedback before handing it over: the student's text by exact quote, cited papers by their fetched abstracts, standards and regulations by the issuer's text. A fresh verifier that did not write the feedback re-reads it, offline too, the review names who verified, and unverifiable claims are dropped or turned into questions. ([verified-scoped-supervise-feedback](openspec/changes/archive/2026-10-03-verified-scoped-supervise-feedback/), [require-supervise-verifier](openspec/changes/archive/2026-10-03-require-supervise-verifier/))
- `proposal-supervise` checks whether the plan fits the student's months, with a work-package table and a fits, tight or over-scoped verdict in the review. Over-scoped feedback opens with two or three lettered ways to cut the plan to one core, and a resubmission is read against the earlier review, whose points are marked resolved, partly resolved or open. ([verified-scoped-supervise-feedback](openspec/changes/archive/2026-10-03-verified-scoped-supervise-feedback/))
- `proposal-supervise` asks one question at the start of the run for read-only lookups and, with approval, weaves at most three verified papers into the points they serve, each with a DOI link; this replaces the standalone starter-literature list offered at the end of idea-stage runs. ([weave-supervise-literature](openspec/changes/archive/2026-09-10-weave-supervise-literature/), [verified-scoped-supervise-feedback](openspec/changes/archive/2026-10-03-verified-scoped-supervise-feedback/))
- `proposal-troubleshoot` reads the install record, names the update route that matches how the skills were installed (install prompt, plugin or terminal), and ships its own copy of the check script, so it also works when the skills are installed for all projects or as a plugin (7385be1).
- The README's model-support table lists the current model versions, with versions not yet measured shown as untested, and the README notes that in test runs Haiku 4.5 did not pick up `proposal-supervise` and did not reliably route polishing passes to `proposal-write`. ([track-model-currency](openspec/changes/archive/2026-10-05-track-model-currency/), [block-outward-tools-in-dev-runs](openspec/changes/archive/2026-10-04-block-outward-tools-in-dev-runs/), [record-polish-routing-boundary](openspec/changes/archive/2026-10-05-record-polish-routing-boundary/))

### Fixed

- `proposal-write`'s description covers writing, editing and polishing passes, including getting a proposal ready for a supervisor, so such requests reach the skill; the question whether a proposal is ready stays with `proposal-review`. ([route-polish-to-write](openspec/changes/archive/2026-10-05-route-polish-to-write/), [record-polish-routing-boundary](openspec/changes/archive/2026-10-05-record-polish-routing-boundary/))

([fix-troubleshoot-model-match](openspec/changes/archive/2026-10-05-fix-troubleshoot-model-match/))

- A new `AGENTS.md` rule sends Anthropic-model runs to the Claude subscription first; the dev runner grades rubric scenarios on the subscription (`--judge`, `--rejudge`), and `poe smoke` now runs the core scenarios there, with the metered check moved to `poe smoke-inspect`. ([steer-subscription-first](openspec/changes/archive/2026-10-05-steer-subscription-first/), [add-dev-runner-judge](openspec/changes/archive/2026-10-05-add-dev-runner-judge/))

([track-model-currency](openspec/changes/archive/2026-10-05-track-model-currency/))

## [0.6.0] - 2026-09-02

_Retroactive release, tagged at f2787ff on 2026-10-14. Published in pushes on 2026-09-01 and 2026-09-02; this state stayed live until 2026-10-13._

The proposal title moves into the file as its only top-level heading, and supervisors get one paste-ready feedback text instead of a send-package. Expectations now follow the degree level named in the subtitle, workspaces can keep proposals in a subdirectory, and seven skills ask the host to run them in a single context.

### Added

- `proposal-ideate`, `proposal-write`, `proposal-review`, `proposal-supervise` and `proposal-lit-search` grade their expectations by the degree level named in the subtitle, so a Bachelor's proposal is not asked for a novelty claim and a Master's proposal is. While the level is a TODO, `proposal-write` asks once and review and supervise judge level-neutrally; structure and checks stay the same. ([add-degree-level-tailoring](openspec/changes/archive/2026-09-02-add-degree-level-tailoring/), [document-degree-level-sources](openspec/changes/archive/2026-09-01-document-degree-level-sources/), [document-degree-level-readme](openspec/changes/archive/2026-09-02-document-degree-level-readme/))
- A workspace can keep its proposals in a subdirectory with `[paths] proposals` in `guidelines.md`: each proposal's notes, figures, review, feedback and built documents move with it, while `guidelines.md`, `api-keys.env` and `bug-report/` stay at the root. `proposal-check` reports a proposal outside that directory as an error, and `proposal-customize` sets the key. ([add-proposal-paths-override](openspec/changes/archive/2026-09-01-add-proposal-paths-override/))
- `proposal-check` warns (never errors) when a proposal has fewer references than its length calls for, by default 4 per 1000 words (changed or disabled with `[references] min_per_1000_words`), which may flag earlier drafts. The guidelines derive the usual ten to fifteen references for five pages from coverage, such as at least two sources per theme and grounding for each research question. ([derive-reference-target-from-coverage](openspec/changes/archive/2026-09-01-derive-reference-target-from-coverage/))

### Changed

- **Breaking:** A proposal opens with `# <title>` as its only H1 and an emphasized subtitle; sections move to H2, an empty `## References` (`## Literatur`) ends the body, metadata holds only `references`, and language is inferred. `proposal-check` flags the old layout as a `legacy-format` error with conversion steps; workspace `proposal-build` scripts need pandoc's `--shift-heading-level-by=-1`. ([title-as-h1-format](openspec/changes/archive/2026-08-31-title-as-h1-format/))
- **Breaking:** `proposal-supervise` writes one paste-ready `<slug>-feedback.md` instead of the `<slug>-package/` send-package of a letter and an attached proposal copy. The professor pastes the feedback as text into an email reply or a learning platform's feedback field, nothing is attached, and the professor-only `<slug>-review.md` is never presented as feedback. ([simplify-supervise-letter](openspec/changes/archive/2026-08-31-simplify-supervise-letter/), [rename-letter-to-feedback](openspec/changes/archive/2026-08-31-rename-letter-to-feedback/))
- `proposal-publish` reads the title, subtitle, language and References heading from the new layout and builds the same document as before; `proposal-troubleshoot` treats the title heading as proposal text, so structure-level bug reports hide it. _Retroactive release, tagged at 35ff3b3 on 2026-10-14. Not published on its own: it reached users with the pushes of 2026-08-11._

Proposals are anonymous by default, author-in-text citations render with the authors' names, and the import and write skills check their own output before reporting it. The LaTeX export now builds, and leftover TODO markers stand out in the compiled document.

### Added

- `proposal-import` and `proposal-write` ship their own copy of the mechanical check, run it over the file they just wrote, fix what it reports and only then report back; a reference shortfall is reported rather than padded with invented sources, and open `[TODO: …]` markers stay in place. ([import-self-verification](openspec/changes/archive/2026-07-30-import-self-verification/), [write-self-verification](openspec/changes/archive/2026-07-31-write-self-verification/))
- `proposal-publish` renders `[TODO: …]` markers as numbered annotations (`TODO 1`, `TODO 2`, …) that cannot be mistaken for prose: a marker alone on its line becomes a callout block, one inside a sentence an inline highlight, and every cue survives grayscale printing; nothing is appended, so page limits are unaffected, and no switch hides the markers. ([highlight-todo-markers](openspec/changes/archive/2026-07-31-highlight-todo-markers/))
- `proposal-check` warns when an author surname is typed beside a citation of that same reference (`Smith et al. [@Smith26Deep]`, or `Smith et al. @Smith26Deep`, which now prints the name twice); the match uses the cited reference's own authors, so a sentence ending in an unrelated proper noun is not flagged. ([check-typed-author-names](openspec/changes/archive/2026-07-30-check-typed-author-names/))
- `proposal-check` warns on reference keys that break the documented `AuthorYearFirstWordOfTitle` shape (e.g. `Smith26Deep`) or reach the 20-character limit. ([check-reference-key-shape](openspec/changes/archive/2026-07-31-check-reference-key-shape/))

### Changed

- Proposals are anonymous by default: the metadata contract is `title`, `subtitle`, `lang`, `references`; `proposal-ideate` no longer seeds an `author` key, the guidance forbids the writer's own name, `proposal-import` strips it, and `proposal-check` warns on an `author:` key. ([anonymous-proposal-author](openspec/changes/archive/2026-07-30-anonymous-proposal-author/))
- A program that requires a named cover page can say so in the workspace `guidelines.md`, and a deliberately set `author` is still printed. ([anonymous-proposal-author](openspec/changes/archive/2026-07-30-anonymous-proposal-author/))
- `proposal-import` converts each source citation by its role in the sentence: authors named as the actor become `@key` with the typed name removed, a citation backing a claim becomes `[@key]`, for numeric, author-date and footnote sources alike. ([import-citation-forms](openspec/changes/archive/2026-07-30-import-citation-forms/))
- `proposal-import` writes from a worked example of the target file (closed metadata block, CSL-YAML reference list, one methodology from the closed set, research questions as an ordered list, one person per author entry) instead of copying the source's layout. ([import-output-conformance](openspec/changes/archive/2026-07-30-import-output-conformance/))
- `proposal-write` decides the methodology when the material leaves it open: it picks the one from the closed set that the research questions best support, keeps the canonical heading and records `[TODO: confirm methodology choice]` in the section body, since a heading never carries a TODO marker. ([write-self-verification](openspec/changes/archive/2026-07-31-write-self-verification/))

### Fixed

- `proposal-publish` renders author-in-text citations (`@key`) as `Smith et al. [1]` instead of a bare `[1]`, with the names taken from the proposal's own references (`und` in German, editor or title as fallback), and no longer drops locators such as `[@key, p. 5]`. ([render-author-in-text-citations](openspec/changes/archive/2026-07-30-render-author-in-text-citations/))
- The guidance says to use `@key` where the authors belong in the sentence and `[@key]` for evidence, and `proposal-check` warns on `@key` for a reference with neither author nor editor. ([render-author-in-text-citations](openspec/changes/archive/2026-07-30-render-author-in-text-citations/))
- The LaTeX output tier of `proposal-publish` now builds; before this fix, every proposal failed on it. ([fix-latex-tier-and-cover-exports](openspec/changes/archive/2026-07-31-fix-latex-tier-and-cover-exports/))
- `proposal-check`, `proposal-import`, `proposal-lit-search` and `proposal-publish` name their scripts by a path that resolves from the workspace, and a skill that cannot find its script says so and names what went unverified instead of presenting its own reading of the file as the script's result. ([resolvable-script-paths](openspec/changes/archive/2026-07-31-resolvable-script-paths/))
- `proposal-lit-search` and `proposal-import` find API keys regardless of where a script runs: each key is looked up in the environment, then `$THESIS_PROPOSAL_KEYS`, then `api-keys.env` in the working directory and its parents up to the home directory, then `~/.config/thesis-proposal/api-keys.env`, and the missing-key error names every location tried. ([streamline-key-file-lookup](openspec/changes/archive/2026-07-30-streamline-key-file-lookup/))

### For contributors

## [0.1.0] - 2026-07-30

_Retroactive release, tagged at 4a8a3de on 2026-10-14. Published 2026-07-30: the first publication of the skills._

Eight agent skills replace the LaTeX proposal template and guide a student from a rough idea to a checked, literature-grounded proposal in English or German. Each proposal lives in one markdown file, and building a PDF is optional.

### Added

- Each proposal is one `<slug>.md` with the text on top and a trailing metadata block (`title`, `author`, `subtitle`, `lang`, and `references` as CSL-YAML). It can be written in English or German, with canonical section titles in both languages, and several proposals can share one folder. ([seed-initial-specs](openspec/changes/archive/2026-07-29-seed-initial-specs/), [implement-remaining-skills](openspec/changes/archive/2026-07-29-implement-remaining-skills/))
- The skills share default guidance carried over from the former template's `AGENTS.md`: four canonical sections, analytical research questions, exactly one methodology out of four (prototype implementation, theoretical analysis, systematic literature review, user study), at least three scientific references, and no timelines, expected-results sections, supervisor names or personal data. ([extract-shared-guidance](openspec/changes/archive/2026-07-29-extract-shared-guidance/))
- `proposal-ideate` develops a rough idea through Socratic questions and never asks directly for missing input. It checks the idea against the literature early and ends by seeding a proposal file with candidate research questions and open TODOs. It uses the `proposal-lit-search` scripts when that skill is installed and queries the academic APIs directly otherwise. ([implement-remaining-skills](openspec/changes/archive/2026-07-29-implement-remaining-skills/), [reduce-skill-duplication](openspec/changes/archive/2026-07-30-reduce-skill-duplication/))
- `proposal-lit-search` finds literature by keyword, or by snowballing from existing references, across DBLP, Crossref, arXiv, OpenCitations, Semantic Scholar and OpenAlex. It judges relevance and merges the accepted entries into the proposal as CSL-YAML. Only OpenAlex needs a key, which the agent can store in a gitignored `api-keys.env` in the workspace. ([implement-lit-search](openspec/changes/archive/2026-07-29-implement-lit-search/), [polish-style-and-evals](openspec/changes/archive/2026-07-29-polish-style-and-evals/))
- `proposal-write` drafts a proposal from notes or a seed file, or refines an existing one with minimal edits. It cites only keys present in the references block, never invents publications or facts, marks every gap with a `[TODO: …]` marker, and can work through a review file item by item. ([implement-remaining-skills](openspec/changes/archive/2026-07-29-implement-remaining-skills/))
- `proposal-review` writes a supervisor-style content review to `<slug>-review.md`: numbered findings ordered by severity, each with a concrete suggestion. It covers research questions, contribution, argument, methodology and scope, and never comments on formatting. ([implement-remaining-skills](openspec/changes/archive/2026-07-29-implement-remaining-skills/))
- `proposal-import` converts an existing proposal, usually a PDF, into the proposal format. It strips personal data and forbidden content and lists what it removed. It then validates the references through Crossref and completes the entries it can identify: unverifiable entries get a `[TODO: verify reference …]` marker, and offline the check is skipped with a note. ([implement-remaining-skills](openspec/changes/archive/2026-07-29-implement-remaining-skills/), [import-reference-validation](openspec/changes/archive/2026-07-29-import-reference-validation/), [implement-import-ref-validation](openspec/changes/archive/2026-07-29-implement-import-ref-validation/))
- `proposal-check` runs a standard-library Python 3.11+ script plus a typo and grammar pass and reports errors and possible-false-positive warnings in chat: metadata, sections, methodology subsections, `(RQn)` references, citation keys, reference count, open TODOs, first-person wording and personal data. It never edits the proposal, and unattended runs make it read-only until the check ends. ([implement-proposal-check](openspec/changes/archive/2026-07-29-implement-proposal-check/), [validation-runs-and-hardening](openspec/changes/archive/2026-07-29-validation-runs-and-hardening/))
- `proposal-publish` optionally builds a PDF with pandoc. It prefers typst, then an installed LaTeX, then docx as a last resort, and uses a compact layout ported from the former template. `--handout` writes a markdown hand-in copy without reference abstracts. Build artifacts are added to the workspace `.gitignore`, and when tools are missing the skill says what to install. ([s3-typst-template-spike](openspec/changes/archive/2026-07-29-s3-typst-template-spike/), [implement-remaining-skills](openspec/changes/archive/2026-07-29-implement-remaining-skills/), [polish-style-and-evals](openspec/changes/archive/2026-07-29-polish-style-and-evals/))
- A `guidelines.md` in the proposal folder overrides the defaults with prose for the agents and one TOML block (`required_sections`, `forbidden_sections`, `min_references`) that `proposal-check` enforces. Each key wins on its own, and a list replaces the default list. `proposal-customize` maintains it from a supervisor's or program's requirements and explains conflicts with the defaults first. ([implement-proposal-check](openspec/changes/archive/2026-07-29-implement-proposal-check/), [implement-remaining-skills](openspec/changes/archive/2026-07-29-implement-remaining-skills/))
- A newcomer README introduces the skills with a table, a quick start built on `npx skills add hutzelmann/thesis-proposal-skills`, a section for supervisors and a three-shot demo of a condensed real session. `docs/getting-started.md` walks through installing an agent from zero. ([docs-and-legacy-cleanup](openspec/changes/archive/2026-07-29-docs-and-legacy-cleanup/), [add-readme-demo-gif](openspec/changes/archive/2026-07-30-add-readme-demo-gif/))

### Removed

- The LaTeX template (`proposal.tex`, `compactarticle.cls`, `literature.bib`, and the template's agent instructions in `AGENTS.md`) is removed from the repository. Anyone who keeps using the template finds it unchanged at the tag `legacy-latex-template`. An existing proposal moves over through `proposal-import`, from its PDF or from pasted text. ([docs-and-legacy-cleanup](openspec/changes/archive/2026-07-29-docs-and-legacy-cleanup/))

### For contributors

- The OpenSpec capability specs, 13 of them seeded from the rewrite plan, are the source of truth for spec-first development: every change runs propose, review, implement and archive, and a contributor `AGENTS.md` states the repository rules. ([seed-initial-specs](openspec/changes/archive/2026-07-29-seed-initial-specs/), [repo-cleanup](openspec/changes/archive/2026-07-29-repo-cleanup/))
- The guidance has one source under `shared/`. `scripts/sync_shared.py` writes its generated copies into the skills, a pre-commit hook keeps them current, and drift tests guard section titles and format prose. ([extract-shared-guidance](openspec/changes/archive/2026-07-29-extract-shared-guidance/), [reduce-skill-duplication](openspec/changes/archive/2026-07-30-reduce-skill-duplication/))
- A synthetic English and German fixture corpus includes workspace fixtures and one derived from a demo session, and each fixture has an `expected.json` oracle calibrated against `check.py`. ([build-fixture-corpus](openspec/changes/archive/2026-07-29-build-fixture-corpus/), [validation-runs-and-hardening](openspec/changes/archive/2026-07-29-validation-runs-and-hardening/), [add-demo-derived-fixtures](openspec/changes/archive/2026-07-30-add-demo-derived-fixtures/))
- Inspect AI evals cover all eight skills plus German, with deterministic L1 checks and rubric-judged L2 checks, through OpenRouter. A dev runner tests a skill through the real Claude Code binary with the same L1 verdicts. ([s1-eval-harness-spike](openspec/changes/archive/2026-07-29-s1-eval-harness-spike/), [build-eval-harness](openspec/changes/archive/2026-07-29-build-eval-harness/), [expand-eval-coverage](openspec/changes/archive/2026-07-29-expand-eval-coverage/), [polish-style-and-evals](openspec/changes/archive/2026-07-29-polish-style-and-evals/), [upgrade-dev-runner](openspec/changes/archive/2026-07-29-upgrade-dev-runner/))
- CI runs ruff, the L0 tests, the generated-copy drift check and strict OpenSpec validation, without model calls or secrets. ([lint-ci-drift](openspec/changes/archive/2026-07-29-lint-ci-drift/))

## Before the skills: LaTeX template (legacy-latex-template)

The project started on 2026-03-03 as a LaTeX template for Bachelor's and Master's thesis proposals in computer science, in English or German: the document class `compactarticle.cls`, a sample `proposal.tex` with `literature.bib`, and an `AGENTS.md` that told GitHub Copilot in VS Code how to draft and check a proposal. That guidance fixed four sections, four methodologies with their subsections, and the content a proposal must leave out, and it seeded the rules of the later skills. The last state, from 2026-03-11, is preserved at the tag `legacy-latex-template` (2dee235).

- `AGENTS.md` requires the sections Introduction to the Topic, Contribution to the State-of-the-Art, Research Focus and Research Questions, and Methodology for Research with one of Prototype Implementation, Theoretical Analysis, Systematic Literature Review or User Study, and excludes work plans, timelines and milestones, supervisor names, expected results, deliverables and personal data (7a5413a).
- Author-in-text citations (`\citeauthor`) name only the first author, followed by "et al." when a source has more than one (00c0840).
- The `embedsources` class option embeds `proposal.tex`, `literature.bib`, `AGENTS.md` and `compactarticle.cls` into the PDF, and the sample `proposal.tex` turns it on (2dee235).
